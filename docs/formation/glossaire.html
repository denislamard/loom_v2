Glossaire

Les mots de loom, expliqués en une ou deux phrases et regroupés par thème. Chaque terme renvoie au module qui le présente.

Thèmes : les bases, la boucle d'un run, les outils, conversations et mémoire, délégation, fiabilité, exécution durable, résilience et coûts, ouvrir et automatiser, clients et sécurité, observabilité et qualité

Les bases

Agent
Ce que vous construisez : un modèle, des consignes et des outils, réunis sous un nom et décrits dans un fichier du dossier agents/. Un projet peut en héberger plusieurs. Module 1.
Modèle
Le modèle de langage (LLM) qui fait réfléchir l'agent : Claude, GPT, un modèle local. loom n'en contient aucun ; il se branche sur ceux des fournisseurs, déclarés dans models. Module 1.
Modèle simulé
Un faux modèle fourni par loom (sdk: fake) qui joue un script de réponses, sans clé ni réseau. Il sert à apprendre et à tester : même sortie à chaque fois, sans frais. Module 1.
Orchestrateur, main
Le modèle principal de l'agent : il lit la demande et décide de répondre ou d'appeler un outil. Dans le fichier d'agent, il s'appelle main. Module 1.
Prompt système
Les consignes données au modèle : qui il est, comment répondre. En ligne (system) ou dans un fichier Markdown de prompts/ (system_file). Module 1.
Extra
Une option du paquet loom-ia qui ajoute une dépendance : anthropic, openai, mcp, http, sqlite… On l'installe avec uv add "loom-ia[anthropic]", en redonnant la liste complète. Module 1.
Variable de prompt
Un emplacement {{ nom }} dans un prompt, rempli par une valeur déclarée pour le client (tenants[].variables). Module 3.
Profil
Un mode de fonctionnement, dev ou prod, qui ajuste la configuration et la sévérité des contrôles : en prod, certains avertissements deviennent des erreurs. Module 3.
Secret
Une valeur à ne jamais écrire dans la configuration (clé d'API, mot de passe). La configuration ne donne que le nom de la variable d'environnement qui la porte, souvent lue dans le fichier .env. Module 3.

La boucle d'un run

Run
Une exécution de l'agent pour une demande : vous posez une question, l'agent travaille, il répond. Chaque run a un identifiant. Module 1.
Boucle agentique
Le va-et-vient d'un run : le modèle demande un outil, loom l'exécute et lui rend le résultat, le modèle recommence, jusqu'à répondre sans outil. Module 1.
Itération
Un appel du modèle de l'orchestrateur dans la boucle. max_iterations en fixe le nombre maximal. Module 1.
Étape
Une unité de la trace d'un run : un appel de modèle, ou un lot d'appels d'outils. loom inspect les affiche dans l'ordre. Module 1.
Réponse forcée
Quand le run atteint une limite (itérations, budget), loom demande au modèle une dernière réponse en lui interdisant les outils, au lieu de couper net. Module 2.
Statut d'un run
Où en est le run : completed (terminé), failed (échoué), paused (en attente d'une approbation), cancelled (annulé). Module 1, module 8.

Les outils

Outil
Une action que le modèle peut demander : lire une page, calculer un prix, chercher un devis. C'est loom qui l'exécute et rend le résultat au modèle. Module 1.
Outil fourni
Un outil livré avec loom-ia, désactivé tant qu'un agent ne le demande pas, par exemple loom.fetch_page qui lit une page web publique. Module 1.
Outil Python
Une fonction de votre code décorée par @tool ; loom en déduit le schéma des arguments, et la docstring devient la description lue par le modèle. Module 2.
Lot
Plusieurs appels d'outils demandés dans une même réponse du modèle : ils s'exécutent ensemble, et les résultats repartent dans l'ordre des appels. Module 2.
Surcharge d'outil
Un réglage d'un outil (délai, approbation, seuil de mise de côté…) redéfini dans la configuration de l'agent, sans toucher au code de l'outil. Module 2.
Artefact
Un fichier rangé à part du journal, qui n'en garde qu'une référence (URI) : une pièce jointe, une image rendue par un outil, un gros résultat mis de côté. Module 2.
Serveur MCP
Un programme qui expose des outils selon le protocole MCP. loom peut s'y brancher (mcp_servers) ; ses outils apparaissent préfixés par le nom du serveur. Module 5.
Source d'outils
Un paquet Python qui fournit des outils à loom par un point d'entrée (tool_sources), importé seulement si un agent la cite. Présenté au module 15.
Sandbox forge
La source d'outils fournie par loom qui fait exécuter, dans une microVM Firecracker isolée, des outils que l'agent écrit lui-même ; un outil accepté rejoint le catalogue du client. Présenté au module 15.

Conversations et mémoire

Journal
La suite ordonnée et immuable des événements d'une session, écrite au moment où ils se produisent. Tout le reste (état, historique, coûts, traces) s'en déduit. Module 1.
Événement
Une ligne du journal : début du run, message, appel de modèle, appel d'outil, décision, fin. Chacun a un type (run.started, tool.called…). Module 4, module 10.
Session
Une conversation : plusieurs runs qui partagent le même journal, nommés par --session. Le run suivant reprend l'historique. Module 4.
Snapshot
Une photo de l'historique écrite régulièrement dans le journal, pour ne pas tout relire à chaque run. Module 4.
Compaction
Le résumé automatique du début d'une conversation devenue trop longue, fait par un modèle dédié ; les derniers tours restent intacts. Module 4.
State de session
Quelques valeurs typées que la session garde d'un run à l'autre (le devis en cours, le ton), posées par l'application ou par un outil, et que la compaction ne touche pas. Module 4.
Backend de journal
L'endroit où le journal est rangé : en mémoire, en fichiers JSONL, en SQLite ou en Postgres. Module 4.
Mémoire long terme
Des notes conservées hors des sessions et retrouvées par recherche, ici avec le serveur MCP loom-notes. Module 5.
Pièce jointe
Une image envoyée avec la demande (--attach). loom la reconnaît à son contenu et contrôle sa taille et leur nombre avant le run. Module 6.

Délégation

Rôle
Un modèle spécialisé, avec son propre prompt, que l'orchestrateur appelle comme un outil. Il ne reçoit que ses arguments et le contexte déclaré, pas toute la conversation. Module 6.
Rôle terminal
Un rôle dont la sortie devient directement la réponse du run, sans repasser par l'orchestrateur. Module 6.
Rôle vision
Un rôle qui reçoit les images jointes au run ; il n'est proposé à l'orchestrateur que si le run a une pièce jointe. Module 6.
Sous-agent
Un agent complet, avec ses outils et sa boucle, appelé par un autre agent comme un outil ; il tourne dans un run enfant. Module 6.

Fiabilité

Contrat de sortie
Une règle de forme vérifiée par du code sur une sortie : schéma JSON, motif, longueur maximale, non vide. Module 7.
Réparation
Quand une sortie ne tient pas son contrat ou son juge, loom la renvoie à son auteur avec le diagnostic, pour qu'il la corrige. Module 7.
Juge
Un modèle qui note une sortie sur des critères écrits (fidélité, ton…) ; sous le seuil d'un critère bloquant, la sortie est refusée. Module 7.
Juge corrélé
Un juge qui utilise le même modèle que la sortie qu'il juge : loom avertit, et refuse en profil prod. Module 7.
Politique
Une fonction Python branchée à un point précis de la boucle (avant un appel de modèle, avant un outil…), qui laisse passer, corrige, refuse, fait réessayer ou met en pause. Module 7.

Exécution durable

Approbation
L'accord d'un humain exigé avant un appel d'outil sensible : le run se met en pause (paused) jusqu'à loom approve ou loom reject. Module 8.
Effet de bord
Ce qu'un outil change dans le monde : un e-mail envoyé, un fichier écrit. Un outil déclaré irreversible n'est jamais relancé à l'aveugle. Module 8.
Idempotence
La garantie qu'une action n'est faite qu'une fois même si on la redemande : l'outil reçoit une clé, et un appel déjà fait n'est pas refait. Module 8.
Reprise
Relancer un run interrompu (plantage, pause tranchée) là où il en était, grâce au journal : loom resume. Module 8.
Concession
Le droit temporaire qu'un process prend sur le run qu'il mène, et qu'il renouvelle tant qu'il tourne. Passé son échéance, un autre process peut reprendre le run. Module 8.
Annulation
L'arrêt volontaire d'un run en cours, par Python, REST ou MCP ; le journal reçoit run.cancelled. Module 8.

Résilience et coûts

Retry
Une nouvelle tentative automatique après une erreur passagère du fournisseur (surcharge, réseau), avec une attente croissante. Module 9.
Modèle de secours
Un modèle utilisé à la place du modèle principal quand celui-ci est en panne (fallbacks). Module 9.
Disjoncteur
Après plusieurs échecs de suite, loom écarte un modèle un moment et passe directement au secours. Module 9.
Token
L'unité de texte que comptent et facturent les fournisseurs, en entrée, en sortie, en lecture et écriture de cache. Module 9.
Cache de prompt
Chez Anthropic, la mise en cache du début d'une requête (prompt, outils, historique) pour la facturer moins cher aux appels suivants. Module 3.
Ledger
Le registre de consommation déduit du journal, qui ventile tokens et coûts par run, rôle, modèle, session et client ; loom report l'affiche. Module 9.
Budget
Un plafond de coût, de tokens ou d'appels, par run, session ou client ; atteint, loom avertit ou force la réponse. Module 9.

Ouvrir et automatiser

Librairie Python
L'accès à loom depuis votre code (Loom.from_config(), run, stream…), sans passer par la commande loom. Module 10.
API REST
L'accès à loom par HTTP, servi par loom serve, pour une application web ou mobile. Module 10.
Clé d'API, portée
Le jeton qu'un appelant présente à l'API, et les droits qu'il donne (run, read, read_content, approve, admin). La configuration n'en garde que l'empreinte. Module 10.
Streaming, SSE
La réponse ou les événements envoyés au fil de l'eau, plutôt qu'en une fois à la fin ; en HTTP, par un flux SSE (Server-Sent Events). Module 10, module 10.
Run en arrière-plan
Un run lancé sans attendre sa fin : l'appelant reçoit son identifiant et suit son statut plus tard. Module 10.
Porte, déclencheur
Une adresse POST /v1/hooks/<nom> qui ouvre un run à partir d'un message envoyé par un autre logiciel (CRM, planificateur), sans qu'il connaisse l'API de loom. Module 11.
File de tâches
La liste des travaux de fond à faire (runs soumis, reprises, résumés) : dans le process (asyncio) ou partagée entre plusieurs process (RabbitMQ). Module 11.
Worker
Un process (loom worker) qui prend des tâches dans la file partagée et les exécute ; si l'un tombe, un autre reprend. Module 11.
Bus
Le canal par lequel un process annonce à un autre qu'il a écrit dans le journal, pour qu'un serveur puisse suivre en direct un run mené ailleurs (Postgres ou Redis). Module 11.

Clients et sécurité

Client (tenant)
Un espace isolé pour une entreprise servie par la même instance : ses variables, secrets, modèles, budgets et journaux. Sans liste de clients, seul default existe. Module 3, module 12.
Quota
Une limite de débit par client (runs par minute) ou par clé d'API (requêtes par minute). Présenté au module 12.
Chiffrement du journal
Le contenu des événements et des fichiers scellé avec une clé par client ; effacer cette clé rend ses données illisibles, sauvegardes comprises. Présenté au module 12.
Rétention
La durée au-delà de laquelle une session dormante peut être effacée par loom retention --yes ; rien ne s'efface tout seul. Présenté au module 12.

Observabilité et qualité

Trace, span
La trace d'un run est son arbre : run, étapes, appels de modèle et d'outils, sous-runs. Chaque nœud est un span, avec son parent, sa durée, son statut et son coût. Présenté au module 13.
Logs techniques
Les messages de fonctionnement de loom (niveau INFO, WARNING…), distincts du journal, réglés par telemetry.logging. Module 1.
Rejeu
Rejouer un run fini à partir du journal, à l'identique sans appeler de modèle, ou en variante avec un autre modèle ; les outils à effet de bord ne sont jamais réexécutés. Présenté au module 13.
Éval
Une suite de cas avec leurs attendus, jouée sur l'agent (et ses variantes) par loom eval, pour vérifier qu'un changement n'a rien cassé. Présenté au module 14.
Doublure
Un faux outil utilisé à la place du vrai pendant un test ou un rejeu, pour ne rien envoyer pour de bon. Présenté aux modules 13 et 14.
Non-régression
Des journaux de runs enregistrés, rejoués à chaque changement du code ou de la configuration : une divergence est un échec. Présenté au module 14.
