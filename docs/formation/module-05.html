Module 5 : Outils MCP et mémoire long terme

Jusqu'ici, les outils de l'agent étaient écrits en Python dans le projet, ou livrés avec loom. Beaucoup d'outils existent déjà ailleurs, sous forme de serveurs MCP : un catalogue de fournisseur, un CRM, un agenda, une mémoire. Ce module vous fait écrire un petit serveur MCP, le brancher sur l'agent, puis donner à l'agent une mémoire qui dure au-delà d'une conversation.

5.1 MCP en deux mots, et un premier serveur

D3

Pourquoi

Jean veut que l'assistant puisse donner le prix d'un chauffe-eau chez son fournisseur. Le fournisseur pourrait publier son catalogue sous forme de serveur MCP : n'importe quel agent pourrait alors l'interroger, sans que chacun réécrive l'outil.

Ce qu'est MCP

MCP (Model Context Protocol) est un protocole standard entre une application IA et un programme qui lui propose des outils. Le programme s'appelle un serveur MCP ; l'application est le client. Claude Desktop, Claude Code et loom sont des clients MCP. Un outil publié par un serveur MCP sert donc partout.

Concrètement, loom :

  1. lance le serveur (ou s'y connecte s'il tourne déjà) ;
  2. lui demande la liste de ses outils, avec leur description et leurs arguments ;
  3. les propose au modèle, comme ses outils Python ;
  4. quand le modèle en appelle un, transmet l'appel au serveur et rend le résultat au modèle.

Le serveur et loom se parlent de deux façons, appelées transports : stdio, où loom lance le serveur comme un sous-programme et lui parle par son entrée et sa sortie standard ; http, où le serveur tourne de son côté, éventuellement sur une autre machine, et loom s'y connecte par une adresse web.

Mise en place

Pour écrire un serveur et pour que loom parle MCP, il faut le SDK MCP, fourni par l'extra mcp. Redonnez la liste complète des extras :

$ uv add "loom-ia[anthropic,openai,sqlite,postgres,mcp]"
Resolved 46 packages in 116ms
Installed 15 packages in 23ms
 + mcp==1.30.0
…

Écrivez le serveur du catalogue, avec des données fictives, dans un dossier serveurs/ :

$ mkdir serveurs
FastMCP("catalogue", …)Le serveur, avec son nom. host et port ne servent qu'en HTTP (exercice 5.5). log_level="WARNING" le rend discret.
@serveur.tool()Publie la fonction comme outil MCP. Comme @tool dans loom (module 2), la signature donne le schéma des arguments et la docstring la description lue par le modèle.
raise ValueError(…)Une erreur dans un outil revient au client comme un résultat d'erreur.
serveur.run(…)Démarre le serveur : en stdio par défaut, en HTTP avec l'option --http.

Vous ne lancez pas ce serveur vous-même : en stdio, c'est loom qui le démarre à chaque commande, et l'arrête à la fin.

5.3 Choisir les outils exposés : include, exclude, alias

D3

Pourquoi

Un serveur MCP peut proposer des dizaines d'outils, dont certains n'ont rien à faire dans les mains de cet agent. Chaque outil proposé occupe aussi de la place dans chaque requête. On choisit donc ce que l'agent voit.

Mise en place et exécution

Ces réglages se mettent sous la ligne - mcp: catalogue de l'agent. Essayez-les un par un :

ligne ajoutée

$ loom validate | grep MCP
    MCP : catalogue__rechercher_article, catalogue__prix_article

ligne ajoutée

$ loom validate | grep MCP
    MCP : catalogue__rechercher_article, catalogue__prix_article

ligne ajoutée

$ loom validate | grep MCP
    MCP : fournisseur__rechercher_article, fournisseur__prix_article, fournisseur__stock_article
include: […]Seuls ces outils sont proposés (noms courts, sans préfixe).
exclude: […]Ces outils sont retirés ; les autres sont proposés.
alias: fournisseurUn autre préfixe que le nom du serveur. Utile pour un nom plus parlant pour le modèle, ou pour brancher deux fois le même serveur avec des réglages différents.

Piège : include et exclude ensemble

C'est l'un ou l'autre :

Configuration : /home/jean/plomberie-dupont/agents/assistant.yaml: tools.4.mcp — Serveur MCP 'catalogue' : 'include' ou 'exclude', pas les deux

Et avec un alias, les noms d'outils changent : un script ou un prompt qui cite catalogue__prix_article ne correspond plus.

Remettez la ligne - mcp: catalogue seule avant la suite.

5.5 Un serveur en HTTP, et la vie d'une connexion

D3

Pourquoi

Un vrai fournisseur ne vous donnerait pas son code à lancer : il ferait tourner son serveur chez lui et vous donnerait une adresse. C'est le transport http.

Mise en place

Lancez le serveur du catalogue en HTTP dans un second terminal (il reste au premier plan ; Ctrl+C l'arrête) :

$ python serveurs/catalogue.py --http

Il écoute sur http://127.0.0.1:8765/mcp. Dans loom.yaml, le serveur change de transport :

transport: httploom se connecte à un serveur qui tourne déjà.
url:Son adresse. command et args n'ont plus de sens et sont refusés.

Exécution

$ loom validate | grep MCP
    MCP : catalogue__rechercher_article, catalogue__prix_article, catalogue__stock_article
$ loom run assistant "Quel est le prix du chauffe-eau thermodynamique chez le fournisseur ?" --session catalogue-http
Le chauffe-eau thermodynamique 200 L (référence CE-THERMO-200) coûte 1 290 € HT chez le fournisseur, et il en reste 3 en stock.

Statut     : completed · itérations : 3 · tokens : 4029/251 · coût : 0.0000 $
Run        : 01a16e10-2300-70c1-a635-287e782867f0

Même résultat qu'en stdio : pour l'agent, seul le chemin change. Un serveur HTTP protégé demande en général un jeton : on le passe par headers_env, qui nomme la variable d'environnement contenant l'en-tête (headers_env: {Authorization: CATALOGUE_JETON}), jamais le jeton lui-même.

Arrêtez le serveur HTTP (Ctrl+C) et remettez la déclaration stdio de l'exercice 5.2 : c'est elle que garde la suite de la formation.

La vie d'une connexion

Quelques réglages du serveur dans mcp_servers décident quand loom ouvre et ferme la connexion :

scope: sharedDéfaut. Une connexion pour tout le process loom, partagée par les runs. Fermée après idle_timeout secondes sans usage (300 par défaut).
scope: tenantUne connexion par client, chacune avec les secrets de son client (module 12). C'est ce qui isole les données de deux entreprises dans un même serveur lancé deux fois.
scope: runUne connexion ouverte au début du run et fermée à sa fin : rien ne passe d'un run à l'autre.
connect_timeoutDélai pour établir la connexion (10 s par défaut). À augmenter pour un serveur lent à démarrer.
env, env_fromVariables passées au serveur stdio : en clair (env), ou recopiées d'une variable de loom (env_from), pour un secret. loom ne lui transmet que celles-là et quelques variables de base.

Avec loom run, chaque commande est un process court : la connexion vit le temps de la commande, quelle que soit la portée. Les portées comptent pour un process qui dure, comme le serveur loom serve (module 10). Là, loom vérifie la santé d'une connexion avant de s'en servir : si le serveur MCP est mort entre deux runs, il est relancé (ou rejoint) automatiquement au run suivant. C'est la reconnexion.

5.6 Une mémoire long terme : loom-notes

F6

Pourquoi

Jean dit à l'assistant : « Mme Martin préfère qu'on l'appelle le matin. » La semaine suivante, dans une autre conversation, l'assistant ne s'en souvient pas : une session (module 4) n'est pas une mémoire. Il faut un carnet de notes durable, où l'agent cherche librement, mais où il n'écrit qu'avec l'accord de Jean.

loom-notes est un serveur MCP de mémoire, publié sur PyPI : on y range des textes, des pages web ou des fichiers, et l'agent les retrouve par une recherche par le sens (on parle de RAG : l'agent retrouve des documents avant de répondre). Il se branche comme le catalogue.

Mise en place : installer loom-notes

loom-notes ne s'ajoute pas aux dépendances du projet : ses propres dépendances entrent en conflit avec celles de loom-ia. On l'installe à part, comme un outil isolé, avec uv tool install. En usage réel, il lui faut ses modèles d'intelligence artificielle (l'extra models, qui tire PyTorch et télécharge environ 5 Go au premier usage) :

$ uv tool install "loom-notes[models]"

Pour la formation, la version sans modèles suffit : loom-notes propose des modèles factices (variable LOOM_NOTES_FAKE_MODELS), qui permettent d'écrire, de lire et de chercher sans rien télécharger. La recherche n'y est pas « par le sens », mais le branchement, les écritures et les approbations sont réels.

$ uv tool install loom-notes
…
Installed 2 executables: loom-notes, loom-notes-mcp
$ which loom-notes-mcp
/home/jean/.local/bin/loom-notes-mcp

Le serveur s'appelle loom-notes-mcp. Ses neuf outils : quatre lectures (search, get, list_docs, projects) et cinq écritures (add_text, add_url, add_file, update, delete).

Mise en place : la configuration

lignes ajoutées

LOOM_NOTES_WARMUP_ON_START: "false"Ne pas précharger les modèles au démarrage (inutile avec des modèles factices).

Les valeurs de env sont entre guillemets quand elles ressemblent à un nombre ou à un booléen : une variable d'environnement est toujours du texte.

Ce qu'il faut comprendre

  • La note a traversé les sessions : elle vit dans la mémoire, pas dans le journal d'une conversation.
  • Le contrôle des écritures est du code : sans l'accord de Jean, rien n'est écrit, quoi que le modèle décide.
  • Avec les vrais modèles, search retrouve aussi une note formulée autrement (« joindre la cliente avant midi ») ; les modèles factices ne le font pas.

Piège : un seul process à la fois

Sans autre réglage, loom-notes range sa base (Qdrant) dans son dossier de données, et un seul process peut l'ouvrir. Deux commandes loom lancées en même temps sur le même dossier se gênent. Pour un usage partagé (Claude Desktop, un serveur), le README de loom-notes explique comment lancer Qdrant à part (variable LOOM_NOTES_QDRANT_URL). Pour deux entreprises, donnez à chacune son dossier et scope: tenant (module 12).

Variante vrai modèle

Avec HAIKU, Claude décide seul de chercher dans la mémoire avant de répondre sur un client, et n'appelle add_text que quand Jean le demande, comme le dit le prompt. Si une écriture est refusée, il reçoit le refus et le dit.

Bilan du module

L'agent consulte le catalogue du fournisseur par MCP. Pour la suite, on garde le serveur du catalogue, en stdio, et on retire la mémoire loom-notes, qui demande une installation à part : remettez loom.yaml, l'agent et le prompt de l'exercice 5.2. Si vous voulez garder la mémoire, laissez sa configuration : la suite fonctionne aussi avec elle.

Le paquet a maintenant les extras anthropic, mcp, openai, postgres et sqlite. Au module 6, l'agent apprend à déléguer : la rédaction des relances à un modèle plus léger, la lecture d'une photo à un modèle qui voit.
