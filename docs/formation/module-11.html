Module 11 : Automatiser : webhooks, workers, bus

Jusqu'ici, quelqu'un lançait chaque run : Jean au terminal, l'application par l'API. Mais le CRM de Jean sait quand un devis reste sans réponse, et la tournée des relances pourrait partir seule chaque matin. Dans ce module, l'agent se fait déclencher par d'autres logiciels, et ses runs peuvent être menés par plusieurs process qui se tiennent au courant.

Agent
assistant, dans le dossier plomberie-dupont/
Départ
la fin du module 10 : l'agent est servi par une API REST protégée par une clé et par un serveur MCP
Arrivée
le CRM et un planificateur déclenchent les relances par une porte d'entrée ; vous savez répartir les runs entre plusieurs process
Fonctions
H6H7I4
Point de départ : les fichiers au début du module

Extras installés : anthropic, http, mcp, openai, postgres, sqlite. La clé d'API app-dupont du module 10 est dans la variable CLE du terminal.

Et pyproject.toml, écrit par uv, qui dit quels extras de loom-ia sont installés (pour repartir de ce point : uv sync) :

Trois briques, trois questions. Qui ouvre le run ? Une porte d'entrée, appelée par un autre logiciel (exercices 11.1 et 11.2). Qui le mène ? Une file de tâches et des workers (11.3 et 11.4). Comment les autres process le voient-ils passer ? Un bus (11.5).

11.1 Une porte d'entrée pour le CRM

H6

Pourquoi

Le CRM de la Plomberie Dupont repère les devis sans réponse depuis trois semaines. Il sait appeler une adresse web quand cela arrive : c'est un webhook, une requête HTTP qu'un logiciel envoie à un autre pour le prévenir d'un événement. Mais le CRM ne connaît ni loom, ni ses agents, ni la façon de formuler une demande. Et comme tout émetteur de webhooks, il réessaie s'il n'est pas sûr que sa requête est arrivée : une même alerte peut arriver deux fois. Il ne faut pourtant qu'une relance.

Mise en place

Une porte d'entrée (trigger) transforme la requête du CRM en run. L'appelant ne fournit que des données (le numéro du devis, le nom du client) ; l'agent, la phrase envoyée à l'agent et la session sont fixés par la configuration. C'est ce qui permet de donner une clé à un logiciel qu'on ne maîtrise pas.

D'abord, une clé pour le CRM, qui ne peut que lancer des runs, et seulement sur l'agent assistant :

$ loom keys create crm --scope run --agent assistant
Clé        : lk_SuBsOAVIlymXo7fHQwD_fpczzz3syOCqK23GYM76oIs
Elle n'est affichée qu'ici : la config ne garde que son empreinte.

À ajouter dans la configuration :

security:
  api_keys:
    - id: crm
      hash: sha256:1140119cfef0082aef0f5b7bd331d2e168cf3a37e026252dc631b534af1e5afb
      scopes: [run]
      agents: [assistant]

On ajoute cette clé à la liste, et la porte d'entrée à la fin de loom.yaml. Seule la fin du fichier change ; le reste est celui du point de départ :

lignes ajoutées

agents: [assistant]Les agents sur lesquels la clé agit (l'option --agent de keys create) : ici, la clé du CRM ne peut rien faire sur un autre agent.
triggers:La liste des portes d'entrée.
name: devis-a-relancerLe nom de la porte, qui forme son adresse : POST /v1/hooks/devis-a-relancer. Minuscules, chiffres, - et _.
agent: assistantL'agent lancé.
message: "…"La demande envoyée à l'agent : un gabarit, où {{ payload.… }} est remplacé par le champ du même nom dans le corps JSON reçu. Les guillemets sont nécessaires : le texte contient des accolades.
session: "devis-{{ payload.numero }}"Le nom de la session, construit de la même façon : toutes les relances d'un devis vont dans la même session. Sans cette clé, chaque appel ouvre sa propre session.
delivery_header: X-Delivery-IdL'en-tête HTTP dans lequel l'émetteur envoie son identifiant de livraison, le même à chaque nouvel essai d'une même alerte. Il devient l'identifiant du run : une alerte livrée deux fois retombe sur le même run.
 
$ loom validate
…
Portes     : devis-a-relancer
    POST /v1/hooks/devis-a-relancer → agent assistant
        session devis-{{ payload.numero }}, livraison sur X-Delivery-Id
    crm : client default, portées run, agents assistant
…

Exécution

Lancez loom serve dans le premier terminal ; la porte est annoncée au démarrage :

$ loom serve
Profil     : aucun (ni --profile, ni LOOM_PROFILE, ni 'profile:') ; surcharges : aucune
Env        : aucun (/home/jean/plomberie-dupont/.env)
API REST   : http://127.0.0.1:8000/v1
Docs       : http://127.0.0.1:8000/docs (sans clé)
Agents     : assistant
MCP HTTP   : http://127.0.0.1:8000/mcp
Outils MCP : assistant
Ressources : loom://runs, loom://sessions, et 6 gabarits
Porte      : POST http://127.0.0.1:8000/v1/hooks/devis-a-relancer

Dans le second terminal, jouez le CRM. Gardez sa clé dans une variable (la vôtre sera différente), puis envoyez l'alerte :

$ CRM=lk_SuBsOAVIlymXo7fHQwD_fpczzz3syOCqK23GYM76oIs
$ curl -s -i -X POST http://127.0.0.1:8000/v1/hooks/devis-a-relancer \
    -H "Authorization: Bearer $CRM" -H 'Content-Type: application/json' \
    -H 'X-Delivery-Id: crm-0001' \
    -d '{"numero":"D-2026-042","client":"Mme Martin"}'
HTTP/1.1 202 Accepted
{"trigger":"devis-a-relancer","run_id":"crm-0001","session_id":"devis-D-2026-042","status":"ready_for_model","repeated":false}

202 Accepted : le run est pris en charge et tourne en arrière-plan, sous l'identifiant crm-0001 fourni par le CRM, dans la session devis-D-2026-042. Le CRM n'a pas reçu la réponse (une coupure réseau) : il renvoie la même alerte.

$ curl -s -i -X POST http://127.0.0.1:8000/v1/hooks/devis-a-relancer \
    -H "Authorization: Bearer $CRM" -H 'Content-Type: application/json' \
    -H 'X-Delivery-Id: crm-0001' \
    -d '{"numero":"D-2026-042","client":"Mme Martin"}'
HTTP/1.1 200 OK
{"trigger":"devis-a-relancer","run_id":"crm-0001","session_id":"devis-D-2026-042","status":"paused","repeated":true}

200 et "repeated": true : la livraison est reconnue, aucun second run n'est ouvert, et la réponse donne l'état du run existant, en pause sur l'envoi de l'e-mail. Un identifiant déjà utilisé avec une autre charge est refusé, pour que deux alertes différentes ne se confondent pas :

$ curl -s -i -X POST http://127.0.0.1:8000/v1/hooks/devis-a-relancer \
    -H "Authorization: Bearer $CRM" -H 'Content-Type: application/json' \
    -H 'X-Delivery-Id: crm-0001' \
    -d '{"numero":"D-2026-050","client":"M. Bernard"}'
HTTP/1.1 422 Unprocessable Content
{"detail":"Identifiant de livraison 'crm-0001' déjà utilisé par un run du déclencheur 'devis-a-relancer' (session devis-D-2026-042) : une même livraison doit donner la même session, et celle-ci donnerait devis-D-2026-050"}

La clé du CRM ne sert qu'à cela. Elle ne lit rien, et une porte inconnue est signalée avec la liste des portes déclarées :

$ curl -s -i http://127.0.0.1:8000/v1/agents -H "Authorization: Bearer $CRM"
HTTP/1.1 403 Forbidden
{"detail":"Clé sans la portée 'read'"}
$ curl -s -i -X POST http://127.0.0.1:8000/v1/hooks/devis-signe -H "Authorization: Bearer $CRM" -H 'Content-Type: application/json' -d '{}'
HTTP/1.1 404 Not Found
{"detail":"Déclencheur 'devis-signe' non déclaré (déclencheurs : devis-a-relancer)"}

Ce que l'agent a reçu, lu dans le journal :

$ jq -r 'select(.type=="message.user") | .payload.message.blocks[0].text' data/default/devis-D-2026-042.jsonl
Relance Mme Martin pour le devis D-2026-042, sur un ton cordial.
$ jq -c 'select(.type=="run.started") | .payload | {trigger, context}' data/default/devis-D-2026-042.jsonl
{"trigger":"devis-a-relancer","context":{"tenant_id":"default","user_id":null,"metadata":{"trigger":"devis-a-relancer"}}}

La phrase est celle de votre gabarit, remplie avec les données du CRM, et le run porte le nom de sa porte (trigger) : on retrouvera plus tard tous les runs venus du CRM.

Le run attend l'accord de Jean, comme n'importe quelle relance (module 8) : 202 veut dire « pris en charge », pas « e-mail parti ». loom sessions show donne la commande à lancer :

$ loom sessions show devis-D-2026-042

  envoyer_email (fake_2_0) — run crm-0001, expire le 25/10 16:04
    loom approve crm-0001 --call fake_2_0 --session devis-D-2026-042
$ loom approve crm-0001 --call fake_2_0 --session devis-D-2026-042 --by jean
Accordé : fake_2_0
L'e-mail de relance est parti chez Mme Martin.

Run        : crm-0001
Juge       : rediger_relance (rôle rediger_relance, appel 1), tentative 1 — acceptée : fidele 1,00, ton 0,90
$ jq -c 'select(.type=="idempotency.reused") | .payload | {tool_name, key}' data/default/devis-D-2026-042.jsonl
{"tool_name":"envoyer_email","key":"default:envoyer_email:email:martin@example.fr:Votre devis D-2026-042"}

Comme au module 10, l'e-mail à Mme Martin était déjà parti : la clé d'idempotence métier l'empêche de repartir, même déclenché par le CRM.

Piège : un champ absent devient un texte vide

Si le CRM oublie un champ, le gabarit ne bloque pas : la variable devient une chaîne vide, et le run part avec une phrase trouée.

$ curl -s -X POST http://127.0.0.1:8000/v1/hooks/devis-a-relancer \
    -H "Authorization: Bearer $CRM" -H 'Content-Type: application/json' \
    -H 'X-Delivery-Id: crm-0002' -d '{"numero":"D-2026-099"}'
{"trigger":"devis-a-relancer","run_id":"crm-0002","session_id":"devis-D-2026-099","status":"ready_for_model","repeated":false}
$ jq -r 'select(.type=="message.user") | .payload.message.blocks[0].text' data/default/devis-D-2026-099.jsonl
Relance  pour le devis D-2026-099, sur un ton cordial.

Ici, le modèle simulé n'a aucune réponse prévue pour cette phrase : le run échoue, et le terminal du serveur le dit ((heure) ERROR loom_ia.engine.loop — Échec de l'appel au modèle SIMULE : model.invalid_request — Script du modèle 'SIMULE' épuisé : réponse n°1 demandée, 0 prévue(s) avec ces outils [run_id=crm-0002 span_id=01a16e71-9009-7174-9320-09aeaa410ae0]). Un vrai modèle, lui, ferait de son mieux avec une demande incomplète. Faites en sorte que vos gabarits ne dépendent que de champs que l'émetteur envoie toujours.

À retenir

  • Sans delivery_header, chaque appel ouvre un nouveau run : une alerte livrée deux fois donnerait deux runs. Si l'émetteur ne sait pas fournir d'identifiant, c'est la clé d'idempotence métier (module 8) qui évite le double envoi.
  • Le même déclenchement existe en Python, sans HTTP : await loom.trigger("devis-a-relancer", {"numero": …, "client": …}, delivery_id="crm-0001").

11.2 Une tournée planifiée

H6

Pourquoi

Jean veut que la relance du devis de M. Bernard parte chaque matin à 7 h 30, tant qu'il n'a pas répondu. loom n'a pas d'horloge : ce qui doit partir à heure fixe est lancé par un planificateur extérieur, qui appelle la même porte d'entrée que le CRM. Sous Linux, le planificateur standard est cron.

Mise en place

Le script tournee.sh appelle la porte. Son identifiant de livraison porte la date du jour : si cron le lance deux fois le même jour (une reprise après une panne, une ligne en double), un seul run est ouvert.

$LOOM_CRM_CLELa clé du CRM, lue dans une variable d'environnement : elle n'est pas écrite dans le script.
$(date +%F)La date du jour au format 2026-10-24 : l'identifiant change chaque jour.
 
$ chmod +x tournee.sh

Exécution

Lancez-le deux fois, comme le ferait un cron qui se répète :

$ export LOOM_CRM_CLE=$CRM
$ ./tournee.sh
{"trigger":"devis-a-relancer","run_id":"tournee-2026-10-24","session_id":"devis-D-2026-050","status":"ready_for_model","repeated":false}
$ ./tournee.sh
{"trigger":"devis-a-relancer","run_id":"tournee-2026-10-24","session_id":"devis-D-2026-050","status":"paused","repeated":true}
$ loom sessions show devis-D-2026-050
Session    : devis-D-2026-050 · 36 événements · 2026-10-24 17:05
Runs       :
  tournee-2026-10-24  assistant    paused            3 itération(s)  0.0283 $
En attente :
  envoyer_email (fake_2_0) — run tournee-2026-10-24, expire le 25/10 16:05
    loom approve tournee-2026-10-24 --call fake_2_0 --session devis-D-2026-050

Un seul run, nommé d'après le jour, en attente de l'accord de Jean. Il reste à confier le script à cron. crontab -e ouvre la liste des tâches planifiées de votre compte ; on y ajoute une ligne :

Les cinq premiers champs disent quand : minute 30, heure 7, tous les jours du mois, tous les mois, du lundi (1) au vendredi (5). La ligne LOOM_CRM_CLE=… donne la variable aux tâches qui suivent. Cette ligne de crontab n'a pas été mise en place pendant la rédaction (il aurait fallu attendre 7 h 30) : le script qu'elle lance est celui qui vient de tourner.

À retenir

Ce qui part à heure fixe se règle dans la plateforme (cron, planificateur du cloud, tâche planifiée d'un serveur), jamais dans loom. L'identifiant de livraison daté rend la tournée sans danger si elle est lancée deux fois.

Arrêtez le serveur avant l'exercice suivant.

11.3 La file de tâches

H7

Pourquoi

Quand l'API reçoit une relance en arrière-plan, quand une approbation relance un run, quand un résumé de session est dû (module 4), loom ne fait pas le travail au milieu de la requête : il le pose dans une file de tâches, et quelqu'un le prend. Ce « quelqu'un » dépend de la file choisie.

Ce qu'il faut comprendre

La file se règle dans storage.queue. Vous ne l'avez jamais écrite : elle vaut asyncio par défaut.

FileQui mène les tâchesPour qui
asyncio (défaut)Le process qui les met en file, en tâches de fond : loom serve, le script Python qui appelle submit(), ou la commande loom approve qui relance le run après l'accord. max_running (16 par défaut) borne le nombre de tâches menées de front.Un seul process : la machine de Jean.
rabbitmqDes process à part, les workers (loom worker), qui prennent les tâches dans un courtier de messages partagé, RabbitMQ.Un service : plusieurs serveurs et plusieurs workers, qui se remplacent si l'un tombe.

C'est pourquoi, à l'exercice 11.1, l'approbation donnée par loom approve a fait repartir le run dans la commande elle-même : la file asyncio de la commande a pris la reprise. Avec cette file, un worker n'a rien à prendre, et loom le refuse :

Exécution

$ loom worker
Config   : loom.yaml
File     : asyncio
Configuration : Un worker demande une file servie par un courtier ('storage.queue.backend: rabbitmq'), pas 'asyncio' — qui exécute déjà ses tâches dans le process qui les met en file
$ echo $?
2

11.4 Des workers avec RabbitMQ

H7

Pourquoi

Le jour où la Plomberie Dupont sert plusieurs entreprises (module 12), un seul process ne suffit plus : l'API doit rester rapide pendant que des runs de plusieurs minutes tournent, et un process qui tombe ne doit rien faire perdre. On sépare alors les rôles : loom serve reçoit les requêtes et met les runs en file ; un ou plusieurs loom worker les mènent.

Mise en place

RabbitMQ n'était pas disponible dans l'environnement de rédaction : cet exercice montre la configuration et tout ce que loom contrôle avant de parler au courtier, mais le fonctionnement avec un vrai courtier n'a pas été exécuté. Chez vous, le plus simple est de lancer RabbitMQ dans un conteneur Docker :

$ docker run -d --name loom-rabbit -p 5672:5672 rabbitmq:4

Le pilote RabbitMQ est l'extra rabbitmq ; on ajoute aussi redis, qui servira à l'exercice suivant :

$ uv add "loom-ia[anthropic,http,mcp,openai,postgres,rabbitmq,redis,sqlite]"
…
 + multidict==7.2.0
 + pamqp==4.0.1
 + propcache==0.5.4
 + redis==8.1.0
 + yarl==1.25.1

Dans loom.yaml, la file passe au courtier. Seul le bloc storage change ; le reste du fichier est celui de l'exercice 11.1 :

ligne ajoutée

queue: {backend: rabbitmq, url_env: AMQP_URL}La file est servie par RabbitMQ, dont l'adresse est dans la variable AMQP_URL. Comme toujours, la configuration ne contient que le nom de la variable.

Exécution

Sans la variable, la configuration est refusée :

$ loom validate
…
Configuration : File 'rabbitmq' : la variable 'AMQP_URL' est vide ou absente — c'est elle qui porte l'URL du courtier

On donne l'adresse du courtier dans le .env (module 3). guest:guest est le compte par défaut de l'image Docker :

$ loom validate
Env        : /home/jean/plomberie-dupont/.env (par défaut) — lues : AMQP_URL
Journal    : jsonl (/home/jean/plomberie-dupont/data)
Artefacts  : local (/home/jean/plomberie-dupont/data/.artifacts)
Idempotence: sqlite (/home/jean/plomberie-dupont/data/idempotence.db)
File       : rabbitmq (URL dans AMQP_URL : renseignée)
Bus        : memory (les nouvelles ne sortent pas de ce process)
    Stockage : file servie par un courtier et artefacts 'local' (/home/jean/plomberie-dupont/data/.artifacts) — les process doivent partager ce dossier, sinon un run repris ailleurs ne retrouvera ni ses pièces jointes ni ses résultats déportés

validate ne se connecte à rien : il décrit l'architecture. Il prévient aussi que les fichiers (pièces jointes, résultats déportés, module 2) ne voyagent pas par la file : si les workers tournent sur d'autres machines, le dossier data/.artifacts doit leur être commun (un volume partagé). On lance un worker, qui mène deux tâches de front :

$ loom worker --jobs 2
Config   : loom.yaml
File     : rabbitmq (URL dans AMQP_URL : renseignée)
Agents   : assistant, traducteur
Clients  : default
Délai    : un travail plus long que le consumer_timeout du courtier (30 min par défaut) lui est redélivré — le régler au-delà du run le plus long
(heure) WARNING  loom_ia.runtime.wiring — Stockage : file servie par un courtier et artefacts 'local' (/home/jean/plomberie-dupont/data/.artifacts) — les process doivent partager ce dossier, sinon un run repris ailleurs ne retrouvera ni ses pièces jointes ni ses résultats déportés
error when creating transport: <AMQPConnectionError: (111, "Connect call failed ('127.0.0.1', 5672)")>
Erreur d'entrée-sortie : [Errno 111] Connect call failed ('127.0.0.1', 5672)

Sans courtier en écoute, le worker s'arrête (code 2) sur l'échec de connexion. Avec RabbitMQ démarré, il affiche ensuite « Reprise : … run(s) remis en file » et « En écoute, 2 tâche(s) de front », et attend.

Ce que l'on observerait avec le courtier

D'après la documentation du dépôt (docs/howto/03-production.md, chapitre 23), non rejoué ici :

  • Au démarrage, un worker reprend les runs interrompus (la reprise du module 8) avant de consommer la file.
  • loom serve ne mène plus aucun run : il les met en file. Un serveur sans worker derrière laisse tout attendre.
  • Une tâche n'est retirée de la file qu'une fois finie : si un worker meurt en pleine tâche, le courtier la redonne à un autre, qui reprend le run là où le journal l'a laissé.
  • Ctrl+C ou un arrêt du service : le worker ne prend plus de tâche et finit celles en cours.
  • Comme le dit le worker au démarrage, une tâche plus longue que le consumer_timeout de RabbitMQ (30 minutes par défaut) lui est redonnée : réglez ce délai au-delà de votre run le plus long.

À retenir

Le journal, la file et le bus doivent être partagés par tous les process. Un journal en fichiers JSONL convient à une machine ; un service réparti sur plusieurs machines prend un journal Postgres (module 4). Pour la suite de la formation, revenez à la file par défaut : retirez la ligne queue de loom.yaml et la ligne AMQP_URL du .env.

11.5 Le bus : suivre un run mené par un autre process

I4

Pourquoi

Avec plusieurs process, l'application peut être branchée sur un serveur pendant que le run est mené par un autre (un autre loom serve, un worker). Pour que son flux d'événements (SSE, module 10) reste en direct, il faut que le process qui écrit prévienne les autres. C'est le rôle du bus. Il ne transporte pas les événements : il dit « du neuf dans tel journal », et ceux qui écoutent relisent le journal.

Exécution

Pour le voir sur une seule machine, on lance deux serveurs sur le même projet : A sur le port 8000, B sur le port 8001. Ils partagent le journal (le dossier data/). Dans deux terminaux :

$ loom serve
$ loom serve --port 8001

Dans un troisième terminal, on lance une relance de M. Bernard sur A, en arrière-plan. Elle s'arrête sur l'approbation. On ouvre le flux SSE du run sur B, en tâche de fond (& en fin de ligne), puis on approuve sur A :

$ R=$(curl -s -X POST http://127.0.0.1:8000/v1/agents/assistant/runs \
    -H "Authorization: Bearer $CLE" -H 'Content-Type: application/json' \
    -d '{"message":"Relance M. Bernard pour le devis D-2026-050.","session_id":"bus-memoire","background":true}' \
    | jq -r .run_id)
$ curl -s -N --max-time 15 -H "Authorization: Bearer $CLE" \
    "http://127.0.0.1:8001/v1/runs/$R/events?session_id=bus-memoire&after_seq=35" \
    | grep -E "^(id|event):" | paste - - &
$ curl -s -X POST "http://127.0.0.1:8000/v1/runs/$R/approve?session_id=bus-memoire" \

À retenir

  • Le bus ne transporte rien : il prévient. Un bus en panne ne fait donc jamais échouer une écriture ; au pire, un flux manque une nouvelle, et un client qui rouvre son flux avec after_seq relit le journal sans rien rater.
  • Dès que plusieurs process partagent un journal (serveurs, workers), déclarez un bus redis ou postgres.
  • Pour la suite de la formation, un seul process suffit : arrêtez les deux serveurs, retirez la ligne bus de loom.yaml et les lignes REDIS_URL et LOOM_DSN du .env.
