Module 15 : Sources d'outils et sandbox forge

Jusqu'ici, un outil était une fonction du projet (module 2) ou un serveur MCP (module 5). Il existe une troisième voie : une source d'outils, un paquet Python installé qui fournit ses outils à chaque run. Jean l'utilise pour partager un calendrier des jours ouvrés entre ses projets. Loom livre aussi sa propre source, forge : l'agent y écrit lui-même un petit outil, que loom exécute dans une machine virtuelle isolée, jamais sur le serveur de Jean.

Agent
assistant, dans le dossier plomberie-dupont/, et un agent atelier dans le sous-projet atelier/
Départ
la fin du module 14 : l'agent a une suite d'évaluations, des tests pytest et des journaux de référence
Arrivée
l'assistant consulte le calendrier de l'entreprise, fourni par un paquet ; l'atelier est prêt à forger des outils dès qu'une VM est disponible
Fonctions

Point de départ : les fichiers au début du module

Le dossier contient aussi les deux journaux de référence (evals/journaux/) et les deux journaux exportés au module 13.

Ce qui a tourné pendant la rédaction

Les exercices 15.1 à 15.4 ont tourné en entier. Pour la sandbox (15.5 à 15.7), tout a tourné sauf ce qui demande une machine virtuelle : la machine de rédaction n'a pas KVM. Vous verrez donc les vrais messages d'une VM absente. L'exercice 15.8 décrit ce que donne une vraie VM, d'après les essais de loom sur une machine équipée, et le signale.

15.1 Écrire une source d'outils dans un paquet

D12

Pourquoi

Jean veut que l'assistant sache si un jour est ouvré avant de proposer une date de relance : pas de relance un dimanche, un jour férié ou pendant la fermeture de fin d'année. Il aura besoin du même calendrier dans d'autres projets (le planning des chantiers, les rendez-vous). Copier un outil dans chaque projet, c'est le corriger partout le jour où il change. Il en fait un paquet Python, calendrier-artisan, installé là où il sert.

Mise en place

Le paquet est un projet à part, à côté de plomberie-dupont/. Placez-vous dans le dossier parent et créez-le avec uv init --lib :

$ cd ..
$ uv init --lib --python 3.14 calendrier-artisan
Initialized project `calendrier-artisan` at `/home/jean/calendrier-artisan`
$ ls -A calendrier-artisan calendrier-artisan/src/calendrier_artisan
calendrier-artisan:
.git
.gitignore
.python-version
README.md
pyproject.toml
src

calendrier-artisan/src/calendrier_artisan:
__init__.py
py.typed

--lib prépare une bibliothèque (un paquet que d'autres projets installent), avec son code dans src/calendrier_artisan/. uv a aussi créé un dépôt Git et un .gitignore. Remplacez le pyproject.toml du paquet (gardez vos propres authors, que uv a remplis d'après votre identité Git) :

dependencies = ["loom-ia>=2.0.11"]Le paquet importe loom (@tool, les types d'une source).
[project.entry-points."loom_ia.tools"]Un point d'entrée : une annonce que le paquet fait à l'installation, dans le groupe loom_ia.tools. C'est là que loom cherche les sources.
calendrier = "calendrier_artisan:fabrique"Le nom du point d'entrée (calendrier), et ce qu'il désigne : la fonction fabrique du module calendrier_artisan.

Remplacez ensuite src/calendrier_artisan/__init__.py :

Le haut du fichier est du Python ordinaire : la date de Pâques, et les jours fériés qui en dépendent. Le contrat avec loom tient en trois pièces.

fabrique(*, name, params, secrets, base_dir)La fabrique, désignée par le point d'entrée. loom l'appelle quand il monte un agent qui utilise la source, avec des arguments nommés : name (le nom de la source dans la configuration), params (ses paramètres, tels quels), secrets (les secrets du client, module 12) et base_dir (le dossier de la configuration, pour les chemins relatifs). Elle vérifie ses paramètres et rend la source, sans rien lire ni ouvrir. Une ValueError levée ici refuse la configuration, avec son message.
class CalendrierLa source : un name, un booléen required (c'est la configuration qui décide, voir 15.3) et une méthode open(context).
open(context)Un gestionnaire de contexte asynchrone, ouvert au début de chaque run. Il reçoit le run (context.tenant_id, session_id, run_id, agent) et rend la liste des outils du run (yield). Ce qui suit le yield s'exécute à la fin du run.
SourceUnavailable(source, message)L'exception à lever dans open() quand la source ne peut pas fournir ses outils : ici, un fichier de congés illisible.
aclose()Facultative : appelée quand l'instance loom se ferme.
@toolLes outils sont ceux du module 2. Définis dans open(), ils utilisent ce que open() a préparé pour ce run (la zone, les congés relus). Ils portent leur nom court : loom les préfixera.

La fonction _dire écrit sur la sortie d'erreur quand la variable CALENDRIER_TRACES est définie : elle servira à voir quand loom appelle chaque pièce.

Revenez dans le projet et installez le paquet :

$ cd plomberie-dupont
$ uv add --editable ../calendrier-artisan
Resolved 79 packages in 189ms
   Building calendrier-artisan @ file:///home/jean/calendrier-artisan
      Built calendrier-artisan @ file:///home/jean/calendrier-artisan
Prepared 1 package in 14ms
Installed 1 package in 2ms
 + calendrier-artisan==0.1.0 (from file:///home/jean/calendrier-artisan)

lignes ajoutées par uv add

--editableInstalle le paquet en place : une modification de calendrier-artisan/src/… compte au run suivant, sans réinstaller. Sans cette option, uv en installerait une copie figée.
[tool.uv.sources]Dit à uv où trouver calendrier-artisan : dans le dossier voisin. Quand le paquet sera publié (sur PyPI ou un dépôt privé), cette ligne disparaîtra.

À retenir

  • Une source, c'est un paquet installé dans l'environnement du projet, qui annonce un point d'entrée du groupe loom_ia.tools. Le projet n'importe rien lui-même.
  • La fabrique ne travaille pas : elle est appelée à chaque chargement de la configuration, y compris par loom validate. Le travail (lire un fichier, ouvrir une connexion) se fait dans open(), à chaque run.
  • Un secret (clé d'API, mot de passe) ne s'écrit jamais dans params : la fabrique reçoit les secrets du client dans secrets.

À retenir

  • Trois conditions pour qu'un agent reçoive les outils d'une source : le paquet est installé dans l'environnement du projet, la source est déclarée dans tool_sources, et l'agent la référence dans tools (- source: calendrier).
  • La source est ouverte à chaque run : le fichier des congés est relu à chaque fois. Une modification compte au run suivant, même pour un loom serve qui tourne depuis des jours.

Piège : un paquet installé mais non référencé

Un paquet que personne ne référence n'est pas importé, donc ses erreurs (une faute de frappe, une dépendance manquante) passent inaperçues, même à loom validate. Référencez la source dans un agent, même minimal, pour que validate la charge.

15.3 Quand la source fait défaut

D12

Pourquoi

Une source peut manquer de deux façons : la configuration est fausse (avant tout run), ou la source ne peut pas fournir ses outils au moment d'un run. Jean veut reconnaître les deux, et décider si l'assistant peut se passer du calendrier.

Mise en place

Deux erreurs de configuration, dans des copies de loom.yaml. Un point d'entrée que personne n'annonce :

$ sed 's/entry_point: calendrier/entry_point: calendrier-artisan/' loom.yaml > loom-essai.yaml
$ loom --config loom-essai.yaml validate
…
Configuration : Point d'entrée 'calendrier-artisan' absent du groupe loom_ia.tools : aucun paquet installé ne le déclare (installés : calendrier, forge)

Un paramètre que la fabrique ne connaît pas :

$ sed 's/conges: conges.json/conge: conges.json/' loom.yaml > loom-essai.yaml
$ loom --config loom-essai.yaml validate
…
Configuration : Agent 'assistant', source 'calendrier' (calendrier-artisan 0.1.0, calendrier_artisan:fabrique) : refusée par sa fabrique — paramètres inconnus : conge (attendus : zone, conges)
$ rm loom-essai.yaml

Les deux sortent en code 2 : la configuration est en cause, aucun run n'a lieu. Le second message est celui de votre fabrique, précédé de l'agent, de la source, du paquet et de sa version.

Exécution

Maintenant, une source qui ne peut pas s'ouvrir : déplacez le fichier des congés, et reposez la question.

La référence d'une source accepte les mêmes réglages que celle d'un serveur MCP (module 5) : alias (un autre préfixe : alias: agenda donne agenda__jour_ouvre), include ou exclude (noms courts), et tools (surcharges pour cet agent, qui l'emportent sur celles de tool_sources).

À retenir

  • Configuration fausse : code 2 à validate comme au run, rien au journal. Source indisponible : un événement au journal, puis le run continue, ou échoue si la source est requise.
  • Dans open(), levez SourceUnavailable avec un message qui dit la cause : c'est lui qu'on lit dans le log, dans inspect et dans l'erreur du run.

15.5 Préparer la sandbox : KVM et make_vm.sh

D9

Pourquoi

Un chantier de rénovation énergétique mélange deux taux de TVA : 5,5 % sur une partie des travaux, 20 % sur le reste. L'assistant n'a pas d'outil pour ça. Jean aimerait qu'un agent écrive lui-même la petite fonction qui manque, la vérifie sur des exemples et la garde pour la prochaine fois, sans que du code écrit par un modèle tourne jamais sur son serveur.

C'est le rôle de la source forge, livrée avec loom. L'agent forge un outil : un nom, une description, un schéma d'entrée, le code d'un module Python qui définit une fonction du même nom, et des exemples. L'hôte vérifie la forme du code, puis l'envoie à execd, un service qui tourne dans une microVM Firecracker : une machine virtuelle minimale, sans réseau, qui démarre en moins de deux secondes. execd exécute chaque exemple sous limites de ressources ; si tous donnent le résultat attendu, l'outil est rangé dans un catalogue, et l'agent peut l'appeler. La VM ne garde rien : chaque appel transporte son code.

Mise en place

Les prérequis. Firecracker demande Linux (x86_64 ou aarch64) avec la virtualisation matérielle, exposée par le fichier spécial /dev/kvm, des droits sudo pour construire l'image, et quatre outils :

$ ls -l /dev/kvm
ls: cannot access '/dev/kvm': No such file or directory
$ sudo apt install -y curl jq squashfs-tools e2fsprogs

Sur la machine de rédaction, /dev/kvm n'existe pas. Chez vous, s'il est absent, la virtualisation est désactivée dans le BIOS, ou votre machine est elle-même une VM (chez un hébergeur, il faut une offre avec virtualisation imbriquée). S'il existe mais que vous n'avez pas le droit d'y écrire : sudo usermod -aG kvm $USER, puis reconnectez-vous.

Le script de construction. Il n'est pas dans le paquet PyPI, mais dans le dépôt de loom. Récupérez seulement son dossier firecracker/, dans la version de votre loom, à côté de vos projets :

À retenir

  • loom démarre la VM tout seul, au premier appel qui exécute du code, et l'arrête avec l'instance. loom validate et le rejeu ne la démarrent jamais. Le démarrage est attendu 60 secondes au plus.
  • Le code forgé n'a ni réseau ni bibliothèque tierce : la bibliothèque standard de Python seulement.

Pourquoi

Jean ne veut pas donner forge à l'assistant qui relance ses clients : un agent qui écrit du code est un outil d'atelier, qu'il veut garder à part et surveiller. Et il y a une raison technique, que l'encadré ci-dessous montre.

  • input_schema et examples peuvent aussi arriver en texte JSON : certains fournisseurs de modèles déforment les objets libres d'un appel d'outil, alors qu'une chaîne arrive intacte.

Relevé lors des essais de loom, non rejoué pendant la rédaction

Ces résultats viennent des essais de recette de loom (docs/loom_testing.md du dépôt, fiche D9, 19 octobre 2026), sur une machine avec KVM, avec un vrai modèle (Claude Haiku) et limits: {wall_ms: 9000}. Ce sont des constats résumés, pas des sorties copiées.

  • Première forge d'un run : forge__forge démarre la VM, exécute les deux exemples de l'outil carre (3 → 9, -4 → 16) et l'accepte en 1,8 s, démarrage compris. forge__call rend ensuite 144 en 115 ms : la VM est déjà démarrée. Le catalogue contient catalogue/default/carre/, avec carre.py et outil.json. La VM est arrêtée à la fin du processus.
  • Au run suivant, forge__carre est un outil à part entière, appelé directement (49, en 1,6 s démarrage compris).
  • Un exemple faux : « Outil double refusé — exemple 1 {"n": 3} : attendu 7, obtenu 6 », et rien au catalogue.
  • Un code qui veut le réseau : erreur Temporary failure in name resolution, avec la trace Python ; l'outil est refusé.
  • Un calcul trop long, appelé par forge__call : « Échec dans la VM (timeout) : depassement de wall_ms (9000 ms) {"limit": "wall_ms", "elapsed_ms": 9021} ». Le run se termine, la VM survit, et l'outil suivant fonctionne.
  • Un autre client (dupont) ne voit que forge__forge et forge__call : son catalogue, catalogue/dupont/, est vide.

À retenir

  • Le catalogue est rangé par client : un outil forgé pour la Plomberie Dupont n'existe pas pour le Chauffage Martin.
  • Pour la production : lancez la VM sous jailer (jailer-run.sh), gardez l'approbation sur forge, versionnez le catalogue, et faites relire chaque outil avant de le promouvoir.

Bilan du module

L'assistant consulte le calendrier de l'entreprise, fourni par un paquet que d'autres projets peuvent installer. L'atelier a sa configuration, son catalogue et son approbation ; il ne lui manque qu'une VM.

Bilan de la formation

Parti d'un dossier vide et d'un modèle simulé, l'assistant de la Plomberie Dupont est devenu, module après module, un agent complet :

ModulesCe que l'agent a appris
1 à 3Tourner, avec ses outils Python et plusieurs modèles, sans clé puis avec.
4 et 5Se souvenir d'une conversation et de son state, et utiliser des outils MCP.
6 et 7Déléguer à des rôles et à un sous-agent, et livrer des sorties vérifiées par contrat et par juge.
8 et 9Demander l'accord de l'artisan, reprendre après une panne sans envoyer deux fois, tenir un budget.
10 et 11S'ouvrir à d'autres programmes (Python, REST, MCP) et se déclencher tout seul.
12Servir plusieurs clients sans mélanger leurs données.
13 et 14Être observé, rejoué, évalué et protégé contre les régressions.
15Recevoir des outils d'un paquet, et en forger dans une VM isolée.

Toutes les fonctions de loom ont été vues au moins une fois ; la matrice des fonctions dit où retrouver chacune, et l'annexe de référence rassemble les commandes et les clés de configuration.

Pour aller plus loin

  • Passer aux vrais modèles. Chaque module a un encadré « Variante vrai modèle » (rappel). Rejouez vos suites d'évaluations avec de vrais modèles et repeat avant de changer de modèle en production (module 14).
  • Publier la source. uv build dans calendrier-artisan/ produit un paquet installable ; publié sur un dépôt privé, il remplace la ligne [tool.uv.sources] de chaque projet.
  • Construire la VM. Sur une machine avec KVM, terminez l'exercice 15.8, puis faites forger un outil à l'atelier avec un vrai modèle, approbation comprise.
  • Lire la documentation du dépôt. docs/configuration.md décrit chaque clé de configuration ; les guides docs/howto/ reprennent ces fonctions sous d'autres angles.
