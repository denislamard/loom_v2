Module 1 : Les bases de l'agent

Vous partez de rien. Vous installez loom-ia avec uv, vous écrivez les deux fichiers qui décrivent un agent, et vous le lancez en ligne de commande. Puis l'agent se présente, passe sur un vrai modèle, garde la trace de ce qu'il fait et va lire un taux de TVA sur le site des impôts.

Agent
assistant, dans le dossier plomberie-dupont/
Départ
rien : un terminal sous Linux
Arrivée
se présente, garde une trace, lit une page web

1.1 Installer loom-ia avec uv

uv est l'outil qui installe Python et les paquets d'un projet. Si vous ne l'avez pas encore :

$ curl -LsSf https://astral.sh/uv/install.sh | sh

Fermez puis rouvrez le terminal pour que la commande uv soit trouvée.

Créez le dossier du projet, puis installez-y le paquet loom-ia, seul, sans option :

$ uv init --bare --python 3.14 plomberie-dupont
$ cd plomberie-dupont
$ uv add loom-ia
  • uv init --bare crée le dossier plomberie-dupont et un fichier pyproject.toml, qui liste les paquets du projet.
  • --python 3.14 : loom-ia demande Python 3.14 ou plus récent. uv le télécharge s'il ne le trouve pas : vous n'avez pas à l'installer vous-même.
  • uv add loom-ia installe loom dans un environnement propre au projet, le dossier .venv/. Rien n'est installé ailleurs sur la machine.

Activez cet environnement, pour pouvoir taper directement la commande loom :

$ source .venv/bin/activate
$ loom --version
loom 2.0.11

L'activation vaut pour le terminal ouvert : dans un nouveau terminal, revenez dans le dossier et relancez source .venv/bin/activate. Toute la formation suppose l'environnement activé. Sans l'activer, on peut aussi écrire uv run loom ….

1.2 Les deux fichiers d'un agent

Pour loom, un agent n'existe que s'il est décrit dans des fichiers. Il en faut deux :

Les deux sont écrits en YAML : chaque ligne est une clé, deux-points, une valeur ; les espaces en début de ligne indiquent ce qui est rangé dans quoi (jamais de tabulation) ; un tiret commence un élément de liste.

Le premier fichier : loom.yaml

Un agent a besoin d'un modèle de langage (un LLM, comme Claude ou GPT) pour comprendre la demande et répondre. loom ne contient aucun LLM : il se branche sur ceux des fournisseurs. Pour apprendre, il fournit un modèle simulé, qui répond sans compte, sans clé et sans réseau. C'est lui qu'on déclare.

Créez loom.yaml dans le dossier du projet, avec votre éditeur ou en copiant ce bloc dans le terminal :

$ cat > loom.yaml <<'EOF'
version: 1

models:
  - id: SIMULE
    sdk: fake
    model: fake-1
EOF
version: 1La version du format de configuration. Toujours 1, et obligatoire.
models:La liste des modèles que vos agents pourront utiliser.
- id: SIMULELe nom que vous donnez à ce modèle. Les agents le désigneront par ce nom.
sdk: fakeLe type de modèle : fake est le modèle simulé de loom. Plus loin, vous utiliserez anthropic pour Claude.
model: fake-1Le nom du modèle chez le fournisseur. Pour le modèle simulé, n'importe quel nom convient.

Le second fichier : agents/assistant.yaml

Chaque fichier du dossier agents/ décrit un agent. Créez le dossier, puis le fichier de l'assistant :

$ mkdir agents
$ cat > agents/assistant.yaml <<'EOF'
name: assistant

main:
  model: SIMULE
  system: Tu es l'assistant de la Plomberie Dupont. Tu réponds en français.
EOF
name: assistantLe nom de l'agent : celui que vous taperez pour le lancer.
main:Le modèle principal de l'agent, qui lit la demande et répond. loom l'appelle l'orchestrateur, parce que c'est lui qui décidera plus tard d'utiliser des outils. Les deux lignes suivantes, décalées de deux espaces, le décrivent.
model: SIMULELe modèle à utiliser, désigné par le nom donné dans loom.yaml.
system: …Le prompt système : les consignes données au modèle, qui lui disent qui il est et comment répondre.

1.4 Le premier run

A1

loom run prend le nom de l'agent, puis la demande entre guillemets :

$ loom run assistant "Bonjour, qui es-tu ?"
2026-10-24 09:29:23 INFO     loom_ia.engine.loop — Modèle SIMULE (rôle main) : 0.00 s, 109 tokens, 0.00000 $ […]
2026-10-24 09:29:23 INFO     loom_ia.engine.loop — Transition ready_for_model → completed (agent assistant) […]
Écho : Bonjour, qui es-tu ?

Statut     : completed · itérations : 1 · tokens : 77/32 · coût : 0.0000 $
Run        : 01a16cd0-7595-70ae-af87-81374451caeb

L'agent a tourné. Un run, c'est une exécution de l'agent pour une demande. De haut en bas :

  • Deux lignes INFO : loom raconte ce qu'il fait. Il a appelé le modèle SIMULE en tant que main, puis le run est passé à l'état completed, terminé.
  • Écho : Bonjour, qui es-tu ? : la réponse de l'agent. Le modèle simulé ne réfléchit pas : tant qu'on ne lui a pas écrit de réponse, il renvoie la demande.
  • Le bilan : le statut, le nombre d'appels au modèle (itérations), les tokens consommés (en entrée et en sortie), le coût, nul ici, et l'identifiant du run.

1.5 Faire répondre le modèle simulé

Pourquoi

L'écho prouve que tout fonctionne, mais l'assistant devrait se présenter. On en profite pour ranger son prompt système dans un fichier à part : un prompt s'allonge vite, et il se relit mieux dans un fichier Markdown que sur une ligne de YAML.

Mise en place

Il y a trois choses à faire : écrire le prompt dans un fichier, dire à l'agent de le lire, puis donner au modèle simulé une réponse à jouer.

1. Écrire le prompt système dans prompts/system.md. Créez le dossier prompts/ à côté de loom.yaml, puis le fichier system.md :

$ mkdir prompts
$ cat > prompts/system.md <<'EOF'
Tu es l'assistant de la Plomberie Dupont, une entreprise de plomberie et de
chauffage. Tu réponds en français, en deux ou trois phrases.
N'invente jamais un taux, un montant ni une date.
EOF

Le fichier contient le texte du prompt, tel quel : pas de clé, pas de guillemets, pas d'indentation à respecter. L'extension .md indique du Markdown : vous pouvez y mettre des titres, des listes ou du code, et le modèle les lit comme du texte mis en forme.

2. Dire à l'agent de lire ce fichier. Dans agents/assistant.yaml, la ligne system:, qui contenait le prompt, est remplacée par system_file:, qui donne le nom du fichier :

ligne modifiée (elle remplace system: Tu es l'assistant…)

system_file: system.mdLe fichier qui contient le prompt système. loom le cherche dans le dossier prompts/, à côté de loom.yaml : c'est son dossier par défaut, il n'y a rien à déclarer. On écrit donc system.md, pas prompts/system.md.

Votre projet contient maintenant trois fichiers :

Vérifiez que loom trouve le prompt :

$ loom validate
…
1 agent(s) monté(s) sans erreur.

Si le nom du fichier est faux, loom le dit, avec le chemin où il a cherché :

Configuration : /home/jean/plomberie-dupont/agents/assistant.yaml: main.system_file — prompt introuvable : /home/jean/plomberie-dupont/prompts/systeme.md

3. Donner une réponse au modèle simulé. Le modèle simulé ne lit ni la question ni le prompt : il joue les réponses qu'on lui écrit, dans l'ordre. Ces réponses s'appellent son script. Ajoutez-le dans loom.yaml :

lignes ajoutées

params:Les réglages propres à ce modèle.
script:Pour le modèle simulé : la liste des réponses à jouer.
- text: …Une réponse, et son texte.

Exécution

$ loom run assistant "Bonjour, qui es-tu ?"
(les deux lignes INFO ne sont pas reproduites)
Bonjour, je suis l'assistant de la Plomberie Dupont. Que puis-je pour vous ?

Statut     : completed · itérations : 1 · tokens : 133/44 · coût : 0.0000 $
Run        : 01a16d14-8b45-765c-9ed7-54fa29a70415

À retenir

  • Le prompt système vit dans prompts/system.md ; l'agent le désigne par system_file. Pour changer les consignes, on modifie ce fichier, sans toucher à la configuration.
  • Le modèle simulé, lui, ignore le prompt : il récite son script. Il sert à apprendre et à tester, parce qu'il donne la même sortie à chaque fois, sans frais. Pour que le prompt compte vraiment, il faut un vrai modèle : c'est l'exercice suivant.

1.6 Passer à un vrai modèle

Cet exercice sert de rappel pour toute la formation : chaque fois qu'un module propose une variante « vrai modèle », il renvoie ici.

Pourquoi

Avec un vrai modèle, l'agent lit vraiment la demande et suit son prompt. On garde quand même le modèle simulé pour les exercices, qui restent ainsi gratuits et reproductibles.

Mise en place

Il vous faut une clé d'API Anthropic (créée dans la console d'Anthropic). Trois étapes :

1. Installer le SDK d'Anthropic. Le paquet loom-ia seul ne contient que le modèle simulé ; chaque fournisseur s'ajoute à part, sous forme d'« extra » :

$ uv add "loom-ia[anthropic]"

2. Déclarer le modèle dans loom.yaml, à la suite de SIMULE :

lignes ajoutées

id: HAIKULe nom que vous donnez à ce second modèle.
sdk: anthropicC'est un modèle Claude, appelé par le SDK d'Anthropic.
model: claude-haiku-5-5Le modèle exact chez Anthropic : Claude Haiku, rapide et peu cher.
api_key_env: ANTHROPIC_API_KEYLe nom de la variable d'environnement qui contient la clé. La clé elle-même n'est jamais écrite dans la configuration.

3. Donner la clé dans un fichier .env, à côté de loom.yaml. La commande loom le lit à chaque démarrage :

Ce fichier contient un secret : il ne doit jamais partir dans git. Si le projet est un dépôt git, ajoutez-le au .gitignore :

Il ne reste qu'à dire à l'agent d'utiliser HAIKU. Une seule ligne change :

ligne modifiée

Exécution

$ loom validate
…
Env        : /home/jean/plomberie-dupont/.env (par défaut) — lues : ANTHROPIC_API_KEY
Modèles    : SIMULE, HAIKU
…
  assistant : modèle HAIKU, 0 outil(s) Python

1 agent(s) monté(s) sans erreur.
$ loom run assistant "Bonjour, qui es-tu ?"

La ligne Env confirme que la clé a été lue (sa valeur n'est jamais affichée). La réponse vient maintenant de Claude, qui se présente à partir du prompt système : elle change d'un run à l'autre.

Si quelque chose manque, loom le dit :

MessageCause
le SDK 'anthropic' n'est pas installé (installer l'extra : loom-ia[anthropic])L'étape 1 a été oubliée.
la variable d'environnement ANTHROPIC_API_KEY est absente ou videLe fichier .env manque, n'est pas à côté de loom.yaml, ou le nom de la variable diffère.
Error code: 401 … invalid x-api-key (au run)La clé est fausse ou révoquée.

À retenir

  • Les deux modèles restent déclarés ; l'agent utilise celui que cite sa ligne model:. Passer de l'un à l'autre, c'est changer cette ligne.
  • Pour la suite de la formation, remettez model: SIMULE : les exercices donnent les scripts du modèle simulé, et leurs sorties sont celles que vous obtiendrez. Avec HAIKU, les exercices fonctionnent aussi, mais les réponses, les tokens et le nombre d'itérations varient. Le coût, lui, reste affiché à 0 $ tant que le modèle n'a pas de tarif (module 9).

1.7 Garder une trace des runs

K1

Pourquoi

Jean veut pouvoir relire ce que l'agent a fait. Or, pour l'instant, rien n'est gardé : sans configuration, loom tient son journal (le récit de chaque run) en mémoire, et il disparaît à la fin de la commande.

Mise en place

Ajoutez deux blocs à la fin de loom.yaml :

lignes ajoutées

storage:Où loom range ce qu'il doit garder.
events: {backend: jsonl, path: data}Le journal est écrit dans des fichiers JSONL (un événement par ligne), dans le dossier data/. Les accolades sont une autre façon d'écrire deux clés sur une ligne.
telemetry:Ce que loom affiche et exporte sur son fonctionnement.
logging: {level: WARNING}N'afficher que les avertissements : les lignes INFO disparaissent de la console, puisque le journal garde tout.

Exécution

L'option --session donne un nom au run : c'est le nom du fichier où il sera écrit.

$ loom run assistant "Bonjour, qui es-tu ?" --session premier-essai
Bonjour, je suis l'assistant de la Plomberie Dupont. Que puis-je pour vous ?

Statut     : completed · itérations : 1 · tokens : 133/44 · coût : 0.0000 $
Run        : 01a16cc3-b4b8-70a2-b8d5-05193e5ca393
$ ls data/default/
premier-essai.jsonl

Pour relire le run, loom inspect prend son identifiant (la ligne Run) et le nom de la session :

$ loom inspect 01a16cc3-b4b8-70a2-b8d5-05193e5ca393 --session premier-essai
Run        : 01a16cc3-b4b8-70a2-b8d5-05193e5ca393 (agent assistant, client default)
Session    : premier-essai
Statut     : completed, 1 itération(s)
Usage      : 133 → 44 tokens, 0.000000 $, 4 ms de pilotage

run assistant — completed, 21 ms, 0.000000 $
  étape 1
    modèle SIMULE (fake-1) (main) — 1 ms, 133 → 44 tokens, 0.000000 $
      · répond    : Bonjour, je suis l'assistant de la Plomberie Dupont. Que puis-je pour vous ?

Réponse finale :
  Bonjour, je suis l'assistant de la Plomberie Dupont. Que puis-je pour vous ?
Bilan      : 1 appel(s) de modèle, 0 appel(s) d'outil

Ce qu'il faut comprendre

  • Le run s'est fait en une étape : un appel au modèle SIMULE, utilisé comme main, qui a répondu.
  • default, dans le chemin data/default/, est le nom du client. Un projet loom peut servir plusieurs entreprises ; il n'y en a qu'une pour l'instant.
  • Ajoutez data/ au .gitignore : le journal n'a pas sa place dans git.

1.8 Donner un outil à l'agent

D13A2

Pourquoi

Les taux de TVA des travaux changent. Jean ne veut pas d'un taux récité de mémoire par le modèle : l'agent doit lire la page officielle.

Mise en place

loom fournit quelques outils prêts à l'emploi, désactivés tant qu'un agent ne les demande pas. loom.fetch_page lit une page web publique et en rend le titre, le texte et les liens. On l'ajoute à l'agent avec une liste tools :

lignes ajoutées

On dit au modèle quand s'en servir, dans le prompt :

lignes ajoutées

Enfin, le modèle simulé doit savoir jouer cette nouvelle scène. Son script a maintenant deux scénarios, et with_text choisit le bon : une réponse avec with_text: TVA ne sert que si la question contient « TVA ».

lignes ajoutées

Le scénario TVA joue deux réponses : la première demande l'outil fetch_page avec l'adresse de la page (tool_calls), la seconde donne la réponse finale.

Piège : le deux-points dans un texte

La dernière réponse est entre guillemets parce qu'elle contient « Source : ». Sans guillemets, YAML prendrait ce deux-points suivi d'une espace pour une nouvelle clé, et loom refuserait le fichier : YAML invalide : mapping values are not allowed here.

Exécution

Cette sortie a été relevée sur une machine sans accès web, d'où l'erreur à l'étape 2. Chez vous, la ligne résultat montrera le titre et le texte de la page.

Ce qu'il faut comprendre

C'est la boucle de l'agent :

  1. étape 1 : le modèle lit la question et demande l'outil fetch_page ;
  2. étape 2 : loom exécute l'outil et rend le résultat au modèle ;
  3. étape 3 : le modèle, avec ce résultat, donne sa réponse finale.

Le modèle a été appelé deux fois : itérations : 2. Pour une question plus difficile, la boucle continue tant que le modèle demande des outils.

Piège : une source citée n'est pas une source lue

La page n'a pas pu être lue, et pourtant la réponse cite « Source : impots.gouv.fr ». Le modèle simulé suit son script sans regarder le résultat de l'outil. Un vrai modèle peut faire la même erreur. Le module 7 montre comment loom l'en empêche par du code, plutôt que par une consigne dans le prompt.

Variante vrai modèle

Avec model: HAIKU (rappel), le script ne sert plus : Claude décide lui-même d'appeler fetch_page, choisit l'adresse, et rédige sa réponse à partir de ce qu'il a lu.

Bilan du module

Votre projet ressemble maintenant à ceci :

Vous savez écrire les fichiers d'un agent, le vérifier, le lancer, relire ce qu'il a fait, le brancher sur un vrai modèle et lui donner un outil. Au module 2, il reçoit un outil que vous écrivez vous-même en Python : un calcul de prix TTC.
