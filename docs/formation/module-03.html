3.1 Déclarer un deuxième modèle Claude

B1

Pourquoi

Tous les modèles ne se valent pas. Claude Haiku est rapide et peu cher ; Claude Opus raisonne mieux mais coûte plus. Jean voudra le premier pour les questions simples, le second pour les tâches délicates. Les deux se déclarent côte à côte dans loom.yaml.

Mise en place

Deux changements dans loom.yaml. D'abord, ce module n'a besoin que de deux scénarios du modèle simulé : son script est remplacé par une version courte. Ensuite, on ajoute Claude Opus :

lignes ajoutées ou remplacées

id: OPUSLe nom que vous donnez au modèle dans la configuration.
model: claude-opus-5-5Le modèle chez Anthropic.
api_key_env: ANTHROPIC_API_KEYLa même variable que pour Haiku : une seule clé Anthropic sert pour tous ses modèles.
capabilities: {…}Ce que le modèle sait faire, ou ne sait pas faire. loom en tient compte pour construire ses requêtes.
forced_tool_choice: falseClaude Opus 5.5 refuse qu'on lui impose l'appel d'un outil (erreur 400). loom s'en sert dans deux cas vus plus loin, les juges et une politique qui exige un outil (module 7) : ce réglage lui dit de s'en passer avec ce modèle.

Les autres capacités, avec leur valeur par défaut, sont décrites dans docs/configuration.md du dépôt. Celles que vous rencontrerez : vision (le modèle voit les images, module 6) et context_window (la taille de sa fenêtre, exercice 3.6).

Exécution

$ loom validate | grep -E 'Modèles|monté'
Modèles    : SIMULE, HAIKU, OPUS
1 agent(s) monté(s) sans erreur.

Déclarer un modèle ne l'utilise pas : l'agent reste sur SIMULE. C'est la ligne model: de l'agent qui choisit (rappel).

3.2 Un modèle d'un autre fournisseur, ou local

B1

Pourquoi

loom n'est pas lié à Anthropic. Il parle aussi à OpenAI et à tous les services qui imitent son API : Together, Mistral, et surtout les modèles que l'on fait tourner sur sa propre machine avec Ollama ou vLLM. Pour des données sensibles, un modèle local évite d'envoyer quoi que ce soit à l'extérieur.

Mise en place

On déclare un modèle servi par Ollama sur la machine. Il n'est pas nécessaire qu'Ollama soit installé pour suivre l'exercice.

lignes ajoutées

sdk: openaiLe modèle parle le protocole d'OpenAI (son API « Chat Completions »). Avec api: responses, loom utiliserait l'autre API d'OpenAI, « Responses ».
base_url: http://localhost:11434/v1L'adresse du service. Sans elle, loom appelle OpenAI. Ici, c'est l'adresse par défaut d'Ollama sur la machine.
model: qwen3:8bLe nom du modèle tel que le service le connaît.
params: {temperature: 0.2}Des réglages transmis tels quels au fournisseur (exercice 3.5).

Pas de api_key_env : un service local ne demande pas de clé.

$ loom validate
…
Demande refusée : Modèle 'LOCAL' : le SDK 'openai' n'est pas installé (installer l'extra : loom-ia[openai])

Comme pour Anthropic au module 1, chaque fournisseur s'installe à part, sous forme d'extra. Donnez à uv add la liste complète des extras voulus, pour garder celui d'Anthropic :

$ uv add "loom-ia[anthropic,openai]"
Resolved 28 packages in 23ms
Installed 1 package in 24ms
 + openai==3.37.0
$ grep loom-ia pyproject.toml

$ loom validate | grep -E 'Modèles|monté'
Modèles    : SIMULE, HAIKU, OPUS, LOCAL
1 agent(s) monté(s) sans erreur.

Exécution

Passez l'agent sur LOCAL (ligne model: LOCAL dans agents/assistant.yaml) et lancez-le. Sans Ollama démarré, voici ce qui se passe :

$ loom run assistant "Bonjour, qui es-tu ?" --session essai-local
2026-10-24 14:51:52 WARNING  loom_ia.engine.model_call — Tentative 1/3 du modèle LOCAL ratée (transient) : nouvel essai dans 0.6 s
2026-10-24 14:51:52 WARNING  loom_ia.engine.model_call — Tentative 2/3 du modèle LOCAL ratée (transient) : nouvel essai dans 1.4 s
—

Statut     : failed · itérations : 0 · tokens : 0/0 · coût : 0.0000 $
Run        : 01a16df7-ae79-7048-afb5-9814a3e6a0f9
Erreur     : Connection error. (model.transient)

Personne ne répond à l'adresse : loom considère l'erreur comme passagère (transient), réessaie deux fois en espaçant les tentatives, puis abandonne. Le module 9 montre comment régler ces nouvelles tentatives et basculer sur un modèle de secours.

Avec Ollama

Si Ollama tourne sur votre machine (ollama pull qwen3:8b, puis ollama serve), le même run reçoit une vraie réponse du modèle local, sans clé et sans réseau extérieur.

Remettez model: SIMULE dans l'agent avant la suite.

3.3 Voir ce que loom envoie au modèle

B2

Pourquoi

Anthropic et OpenAI n'attendent pas les messages sous la même forme. Pourtant, Jean peut passer d'un modèle à l'autre en changeant une ligne. Comment ? loom garde les messages sous une forme neutre, et ne les traduit dans le format du fournisseur qu'au moment de l'appel. Pour le voir, on demande à loom de garder les requêtes telles qu'il les envoie.

Mise en place

ligne ajoutée

capture: {raw_exchanges: true}Garde au journal chaque requête envoyée au modèle et sa réponse, telles quelles (événement model.exchanged). Les clés d'API y sont masquées. C'est un outil de mise au point : le journal grossit vite.

Exécution

1. Le format neutre. Avec le modèle simulé, regardez le message de l'utilisateur tel que le journal le garde, puis la requête transmise au modèle :

$ loom run assistant "Bonjour, qui es-tu ?" --session format-neutre
Bonjour, je suis l'assistant de la Plomberie Dupont. Que puis-je pour vous ?

Statut     : completed · itérations : 1 · tokens : 645/44 · coût : 0.0000 $
Run        : 01a16df7-c5f9-7376-aafa-17886d55a597
$ jq -c 'select(.type=="message.user") | .payload.message' data/default/format-neutre.jsonl

$ jq -r 'select(.type=="model.exchanged") | .payload.request_body' data/default/format-neutre.jsonl | jq '{model_id, messages}'
{
  "model_id": "fake-1",
  "messages": [
    {
      "role": "user",
      "blocks": [
        {
          "cache_breakpoint": false,
          "provider_meta": {},
          "type": "text",

Le message est une suite de blocs typés (ici un bloc text). Les images, les appels d'outils et leurs résultats, le raisonnement d'un modèle sont d'autres types de blocs. Le modèle simulé n'a pas de format propre : il reçoit cette forme neutre.

2. Le format d'Anthropic. Passez l'agent sur HAIKU. Pas besoin d'une vraie clé : avec une clé bidon, donnée pour cette seule commande, la requête part, Anthropic la refuse, et le journal la garde quand même.

Ce qu'il faut comprendre

  • La même demande, le même prompt, les mêmes outils, et trois formes différentes. Pour Anthropic, le prompt système est un champ à part (system) et le message une liste de blocs. Pour OpenAI, le prompt système devient un message de rôle system, et le texte une simple chaîne.
  • Le journal, lui, garde toujours la forme neutre. C'est pourquoi une conversation commencée avec un modèle peut continuer avec un autre, et pourquoi un run se rejoue avec un autre modèle (module 13).
  • Seul le code qui parle à un fournisseur, son adaptateur, connaît son format. Ajouter un fournisseur ne change rien au reste de loom.

Remettez model: SIMULE dans l'agent avant la suite. Gardez raw_exchanges pour les exercices suivants.

3.4 Le cache de prompt

B5

Pourquoi

À chaque tour, l'agent renvoie au modèle le même prompt système, les mêmes outils et toute la conversation. Anthropic peut garder ce début de requête en cache : relu plutôt que retraité, il coûte environ dix fois moins cher et répond plus vite. Encore faut-il marquer dans la requête jusqu'où mettre en cache.

Mise en place

lignes ajoutées

max_tokens: 4096Le nombre maximal de tokens que le modèle peut écrire dans une réponse. Anthropic l'exige ; sans cette ligne, loom envoie 4096 (exercice 3.5).
cache: {system: true, tools: true, messages: true}Pose un point de cache sur le prompt système, sur le dernier outil, et sur le dernier message de la conversation. Réservé à sdk: anthropic : loom le refuse pour OpenAI.

Exécution

Agent sur HAIKU, avec la clé bidon :

$ ANTHROPIC_API_KEY=cle-bidon loom run assistant "Bonjour, qui es-tu ?" --session cache
(refus 401, comme à l'exercice 3.3)
$ jq -r 'select(.type=="model.exchanged") | .payload.request_body' data/default/cache.jsonl | jq '{max_tokens, system, messages, dernier_outil: .tools[-1] | {name, cache_control}}'
{
  "max_tokens": 4096,
  "system": [
    {
      "type": "text",
      "text": "Tu es l'assistant de la Plomberie Dupont, une entreprise de plomberie et de\nchauffage. Tu réponds en français, en deux ou trois phrases.\nN'invente jamais un taux, un montant ni une date.\nPour une question de TVA, lis la page officielle avec l'outil `fetch_page`\net cite ta source.\nPour tout calcul de prix, appelle l'outil `prix_ttc` au lieu de calculer\ntoi-même, et reprends les montants qu'il renvoie.\nPour une question sur un devis, appelle l'outil `chercher_devis` avec son\nnuméro.\n",
      "cache_control": {
        "type": "ephemeral"
      }
    }
  ],
  "messages": [
    {
      "role": "user",
      "content": [
        {
          "type": "text",
          "text": "Bonjour, qui es-tu ?",
          "cache_control": {
            "type": "ephemeral"
          }
        }
      ]
    }
  ],
  "dernier_outil": {
    "name": "etiquette_devis",
    "cache_control": {
      "type": "ephemeral"
    }
  }
}

Ce qu'il faut comprendre

Les trois marques cache_control sont les points de cache. Tout ce qui les précède peut être relu depuis le cache d'Anthropic au tour suivant. C'est l'adaptateur Anthropic qui les pose ; le modèle simulé et OpenAI n'en reçoivent pas.

Variante vrai modèle

L'effet du cache ne se voit qu'avec une vraie clé. Dans le bilan d'un run et dans loom inspect, les tokens se répartissent alors entre l'entrée normale, l'écriture en cache (cache_write, au premier appel) et la lecture en cache (cache_read, aux appels suivants). Un prompt trop court pour le minimum du modèle n'est simplement pas mis en cache, sans erreur.

3.5 Régler chaque appel

B6

Pourquoi

Une réponse de l'assistant tient en trois phrases : inutile de lui laisser 4 096 tokens. Les réglages d'appel se fixent sur le modèle, et chaque agent peut les ajuster pour lui-même.

Mise en place

Trois niveaux :

max_tokens (modèle)Dans loom.yaml, la longueur maximale d'une réponse, pour tous les agents qui utilisent ce modèle (exercice 3.4).
params (modèle)Dans loom.yaml, des réglages transmis tels quels au fournisseur, qui seul juge ce qu'il accepte : temperature, thinking… Vous l'avez vu sur LOCAL : "temperature": 0.2 figure dans sa requête (exercice 3.3).
llm (agent)Dans le fichier de l'agent, sous main : ses propres max_tokens et params, qui remplacent ceux du modèle pour lui seul.

Réduisez la longueur des réponses de l'assistant, sur HAIKU :

lignes ajoutées (et le modèle passé sur HAIKU)

Exécution

$ ANTHROPIC_API_KEY=cle-bidon loom run assistant "Bonjour, qui es-tu ?" --session reglages
(refus 401)
$ jq -r 'select(.type=="model.exchanged") | .payload.request_body' data/default/reglages.jsonl | jq '{model, max_tokens}'
{
  "model": "claude-haiku-5-5",
  "max_tokens": 1000
}

À retenir

  • Les clés de llm.params se fusionnent une à une sur celles de params du modèle. Une clé qui contient elle-même un bloc (comme thinking) est remplacée en entier, pas mélangée.
  • loom ne vérifie pas le contenu de params : c'est le fournisseur qui refuse ce qu'il ne connaît pas. Les modèles Claude 5.5, par exemple, refusent temperature (erreur 400).
  • Le module 6 reprend llm pour les rôles, des modèles secondaires de l'agent.
  • Retirez le bloc llm et remettez model: SIMULE avant la suite.

3.6 La fenêtre de contexte

B7

Pourquoi

Chaque modèle a une fenêtre de contexte : la taille maximale d'une requête, réponse comprise, en tokens. Une conversation qui grossit finit par la dépasser, et le fournisseur refuse alors la requête. loom peut vérifier la taille avant d'envoyer.

Mise en place

On donne au modèle simulé une fenêtre minuscule, 600 tokens :

ligne ajoutée

context_window: 600La fenêtre du modèle, en tokens. Sans elle, loom ne vérifie rien. Pour Claude, elle se compte en centaines de milliers de tokens (par exemple context_window: 200000).

Exécution

$ loom run assistant "Où en est le devis D-2026-042 ?" --session fenetre
—

Statut     : failed · itérations : 1 · tokens : 648/66 · coût : 0.0000 $
Run        : 01a16df8-07c6-70a5-b31f-88080ff3bcb5
Erreur     : Requête estimée à 801 tokens, plus 0 en sortie : dépasse la fenêtre de 600 tokens du modèle SIMULE (model.context_overflow)

Ce qu'il faut comprendre

  • Le premier appel passe. Il demande chercher_devis, dont le résultat s'ajoute à la conversation. Le deuxième appel ferait alors 801 tokens : loom le refuse avant de l'envoyer, et le run échoue avec model.context_overflow.
  • loom estime la taille à environ un token pour quatre caractères, et ajoute le max_tokens du modèle (« en sortie »), puisque la réponse doit aussi tenir dans la fenêtre. Le modèle simulé n'a pas de max_tokens, d'où le « plus 0 ».
  • Dans une longue conversation, ce n'est pas la seule protection : le module 4 montre comment loom résume les anciens échanges pour rester dans la fenêtre.
  • Retirez la ligne capabilities du modèle simulé avant la suite.

3.7 Les secrets et le fichier .env

M3M6

Pourquoi

Une clé d'API dans un fichier de configuration finit toujours dans git, dans une sauvegarde ou dans une capture d'écran. Avec loom, la configuration ne contient jamais de secret : seulement le nom de la variable d'environnement qui le porte. Reste à savoir d'où viennent ces variables.

Ce qu'il faut comprendre d'abord

Toutes les clés de configuration qui finissent par _env désignent une variable d'environnement : api_key_env pour la clé d'un modèle, et d'autres plus loin pour l'adresse d'une base de données ou d'un service. Au démarrage, la commande loom peut charger ces variables depuis un fichier. Elle en choisit un seul, dans cet ordre :

OrdreFichier luLigne Env de loom validate
1l'option --env-file FICHIER(par option)
2la clé env_file: de loom.yaml(par config)
3le fichier .env à côté de loom.yaml, s'il existe(par défaut)

L'option --no-env-file n'en lit aucun.

Exécution

Le .env voisin, celui du module 1 :

$ loom validate | grep Env
Env        : /home/jean/plomberie-dupont/.env (par défaut) — lues : ANTHROPIC_API_KEY

Un autre fichier, donné par l'option. Créez un fichier de test dans un dossier secrets/ :

$ mkdir secrets
$ printf 'ANTHROPIC_API_KEY=clé-de-test\nOPENAI_API_KEY=autre-clé\n' > secrets/test.env
$ loom validate --env-file secrets/test.env | grep Env
Env        : /home/jean/plomberie-dupont/secrets/test.env (par option) — lues : ANTHROPIC_API_KEY, OPENAI_API_KEY

Un fichier désigné dans la configuration, avec la clé env_file, en tête de loom.yaml :

$ loom validate | grep Env
Env        : /home/jean/plomberie-dupont/secrets/test.env (par config) — lues : ANTHROPIC_API_KEY, OPENAI_API_KEY

Le chemin est relatif au dossier de loom.yaml. Si le fichier n'existe pas, loom s'arrête (code 2) : Configuration : Fichier d'environnement introuvable (env_file) : /home/jean/plomberie-dupont/secrets/absent.env. Retirez la ligne env_file et le dossier secrets/ après l'essai.

Une variable déjà définie l'emporte sur le fichier :

$ ANTHROPIC_API_KEY=clé-exportée loom validate | grep Env
Env        : /home/jean/plomberie-dupont/.env (par défaut) — déjà définies, gardées : ANTHROPIC_API_KEY
$ loom validate --no-env-file | grep Env
Env        : non lu (--no-env-file)

À retenir

  • Une variable déjà présente dans l'environnement (un export dans le terminal, la configuration d'un service), même vide, n'est jamais remplacée par le fichier. C'est ce qui permet, en production, de fournir les secrets autrement.
  • loom affiche les noms des variables lues, jamais leurs valeurs, ni ici, ni dans les logs, ni dans les erreurs.
  • Le fichier est lu tel quel : B=${A} donne la valeur littérale ${A}, sans remplacement.
  • Ces règles valent pour la commande loom. Une application Python qui utilise loom comme librairie ne lit aucun fichier d'elle-même : elle appelle load_env_file(), ou fournit ses secrets par un SecretProvider, qui peut les tirer d'un coffre-fort de secrets. Les deux sont vus au module 10.

3.8 Des variables dans le prompt

M7

Pourquoi

Le nom « Plomberie Dupont » est écrit en dur dans le prompt. Quand le même agent servira une autre entreprise (module 12), il faudra un autre prompt… ou une variable. loom remplace {{ nom }} par sa valeur au moment de construire la requête.

Mise en place

Remplacez le nom de l'entreprise par une variable :

ligne modifiée

$ loom validate
…
Configuration : /home/jean/plomberie-dupont/loom.yaml: Agent 'assistant', main.system_file (prompts/system.md) — {{ entreprise }} : variable non définie pour le client 'default' (tenants[].variables)

loom refuse un prompt qui cite une variable sans valeur, dès le chargement. Le message dit où la déclarer : dans tenants[].variables. Un client (tenant) est une entreprise servie par loom. Il y en a toujours au moins un, default, celui qu'on voit dans les chemins data/default/ depuis le module 1. On lui donne sa valeur :

lignes ajoutées

tenants:La liste des clients et de ce qui leur est propre. Le module 12 l'utilise pour un second client.
- id: defaultLe client par défaut.
variables:Les valeurs des variables citées par les prompts, pour ce client.
entreprise: Plomberie DupontLa valeur de {{ entreprise }}.

Exécution

Ce qu'il faut comprendre

3.9 Profils de développement et de production

M4

Pourquoi

Sur son poste, Jean veut des logs bavards et des règles souples. Sur le serveur, il veut l'inverse : des logs au format JSON pour un outil de supervision, et aucune approximation tolérée. Plutôt que deux fichiers de configuration, loom propose des profils.

Mise en place

Ajoutez à la fin de loom.yaml :

lignes ajoutées

profile: devLe profil actif : dev ou prod. L'option --profile, puis la variable LOOM_PROFILE, l'emportent sur cette ligne.
profiles:Ce que chaque profil modifie dans loom.yaml. Les blocs se fusionnent avec la configuration (une liste, elle, est remplacée en entier).
dev: telemetry: …En développement, les logs reviennent au niveau INFO.
prod: telemetry: …En production, seulement les avertissements, au format JSON.

Exécution

$ loom validate | grep -E 'Profil|Télémétrie'
Profil     : dev (par config) — assoupli ; surcharges : dev, prod
Télémétrie : logs INFO (console) ; exports sans contenu (metadata) ; échanges bruts au journal (256 Kio par corps au plus)
$ loom --profile prod validate | grep -E 'Profil|Télémétrie|Avert'
Avertissement : variables lues dans /home/jean/plomberie-dupont/.env (ANTHROPIC_API_KEY) — en prod, préférer l'environnement du service
Profil     : prod (par option) — les avertissements sont des erreurs ; surcharges : dev, prod
Télémétrie : logs WARNING (json) ; exports sans contenu (metadata) ; échanges bruts au journal (256 Kio par corps au plus)
$ LOOM_PROFILE=prod loom validate | grep -E 'Profil'
Avertissement : variables lues dans /home/jean/plomberie-dupont/.env (ANTHROPIC_API_KEY) — en prod, préférer l'environnement du service
Profil     : prod (par LOOM_PROFILE) — les avertissements sont des erreurs ; surcharges : dev, prod

Les options générales comme --profile ou --env-file s'écrivent avant ou après la commande (loom --profile prod validate ou loom validate --profile prod).

Ce que la production durcit. En prod, les avertissements deviennent des erreurs, et certains assouplissements sont interdits. Par exemple, l'option --judges skip de loom run, qui saute les juges (module 7), est refusée :

$ loom --profile prod run assistant "Où en est le devis D-2026-042 ?" --judges skip
Avertissement : variables lues dans /home/jean/plomberie-dupont/.env (ANTHROPIC_API_KEY) — en prod, préférer l'environnement du service
Configuration : Profil prod : judges='skip' retire un contrôle et n'y est pas permis
$ echo $?
2

Autre exemple : retirez la ligne api_key_env du modèle OPUS, et passez profile: prod dans le fichier. En dev, loom avertit ; en prod, il refuse :

$ loom --profile dev validate | grep -E "Profil|OPUS|monté"
Profil     : dev (par option) — assoupli ; surcharges : dev, prod
    Modèle 'OPUS' : sdk anthropic vers l'API officielle sans api_key_env — aucune clé d'API n'est envoyée, chaque appel sera refusé (401) ; déclarer api_key_env: ANTHROPIC_API_KEY
1 agent(s) monté(s) sans erreur.
$ loom validate
…
Configuration : Profil prod : Modèle 'OPUS' : sdk anthropic vers l'API officielle sans api_key_env — aucune clé d'API n'est envoyée, chaque appel sera refusé (401) ; déclarer api_key_env: ANTHROPIC_API_KEY
$ echo $?
2

À retenir

  • dev assouplit (certains refus deviennent des avertissements, vous en croiserez au module 8) ; prod durcit : tout avertissement arrête le chargement, et les raccourcis de développement sont refusés (--judges skip, le rechargement automatique du serveur du module 10).
  • Sans profil, loom ne durcit ni n'assouplit rien.
  • Un profil ne peut pas changer de fichier .env : env_file est refusé dans profiles.
  • Remettez api_key_env sur OPUS, puis retirez profile et profiles : la suite de la formation s'en passe.

3.10 Les contrôles de cohérence

M5

Pourquoi

Une erreur de configuration découverte au milieu d'un run, chez un client, coûte cher. loom vérifie donc la cohérence de toute la configuration au chargement, avant le moindre appel, et refuse de démarrer si quelque chose cloche.

Exécution

Un agent qui cite un modèle inconnu (model: SONNET) :

$ loom validate
