Module 13 : Observabilité et rejeu

L'assistant tourne pour deux entreprises, et il envoie des e-mails à leurs clients. Quand Jean se demande « qu'a fait l'agent mardi, et pourquoi ? », la réponse est dans le journal. Ce module apprend à le lire sous toutes ses formes, à n'en laisser sortir que ce qu'il faut, et à rejouer un run passé pour vérifier qu'une modification ne change rien, ou pour essayer un autre modèle sans renvoyer un seul e-mail.

13.1 L'arbre complet d'un run

K1

Pourquoi

Au module 1, loom inspect montrait un run d'une seule étape. Une relance, elle, passe par un outil, un rôle, un juge, une approbation et un envoi idempotent. Jean veut voir tout cela d'un coup d'œil, dans l'ordre, avec ce que chaque étape a coûté.

Ce qu'il faut comprendre

L'arbre suit le run étape par étape. Chaque ligne en retrait est un nœud, avec sa durée, ses tokens et son coût :

Un sous-agent (module 6) apparaît de la même façon, avec son propre run enfant rattaché à l'étape qui l'a appelé.

La ligne Usage donne la durée de pilotage (le temps passé à travailler, ici 72 ms environ), alors que la ligne run assistant donne la durée totale, qui comprend la pause d'approbation.

13.3 Ce qui est capturé, et ce qui est montré

K3

Pourquoi

Le journal garde tout : la demande, les arguments des outils, le texte de l'e-mail. C'est indispensable pour reprendre ou rejouer un run. Mais l'outil de supervision que Jean veut brancher n'a besoin que de savoir si les relances partent : il ne doit pas lire le texte des e-mails.

Ce qu'il faut comprendre

loom distingue trois choses, réglées dans le bloc telemetry de loom.yaml :

capture.raw_exchangesGarder en plus, dans le journal, la requête HTTP exacte envoyée au fournisseur et sa réponse (événement model.exchanged, vu au module 3). Pour déboguer ; désactivé par défaut. La clé d'API y est toujours remplacée par [retiré].
capture.raw_max_bytesLa taille maximale gardée pour chacun de ces corps bruts (256 Kio par défaut).
capture.exportsCe qui part vers un collecteur extérieur : la forme seule (metadata, par défaut) ou aussi le contenu, masqué (content). Exercice 13.5.

Quoi qu'il arrive, le journal garde tout. Ce qui change, c'est ce qu'on montre : à un collecteur (13.5), ou à une application qui lit l'API. Pour l'API, c'est la portée de la clé qui décide : une clé sans la portée read_content lit les runs sans leur contenu.

Mise en place

Créez une clé de supervision qui ne peut que lire (module 10) :

À ajouter dans la configuration :

    - id: lecture-dupont
      hash: sha256:7bd8c52cfc7666305c7fe50c972a1b019dd85afb8906946fd0d0166ba6a073ef
      scopes: [read]

Déclarez-la dans loom.yaml. Seul le bloc security change ; le reste du fichier est celui du point de départ :

À retenir

13.4 Lire les traces par l'API, par Python et par MCP

K5

Mise en place : OpenTelemetry

OpenTelemetry (OTel) est le format standard des traces. Les outils de supervision (Jaeger, Grafana Tempo, Datadog…) reçoivent les spans en OTLP, le protocole d'OTel, d'un process appelé collecteur. loom envoie ses spans à la fin de chaque run. Il faut l'extra otel ; redonnez toute la liste des extras :

$ uv add "loom-ia[anthropic,crypto,http,mcp,openai,otel,postgres,rabbitmq,redis,sqlite]"

 + opentelemetry-sdk==1.45.1
    "loom-ia[anthropic,crypto,http,mcp,openai,otel,postgres,rabbitmq,redis,sqlite]>=2.0.11",

Pour recevoir les spans, le plus simple sur votre machine est Jaeger, dans un conteneur Docker. Son interface est sur http://localhost:16686, et il reçoit l'OTLP sur le port 4318 :

13.6 Rejouer un run à l'identique

K6

Pourquoi

Jean veut retoucher le prompt de l'assistant. Avant, il aimerait savoir si l'agent se comporterait encore exactement comme lors de la relance de Mme Martin. Mais pas question de la relancer pour de vrai.

Ce qu'il faut comprendre

Le journal contient tout ce que le run a reçu : les réponses du modèle, les résultats des outils, les décisions d'approbation. loom peut donc le rejouer : refaire tourner l'agent pas à pas, en lui resservant ces réponses au lieu d'appeler le modèle et les outils. À chaque appel de modèle, il compare la requête qu'il construit aujourd'hui avec celle du journal (par une empreinte). Si tout concorde, le run est « identique ». Rien n'est envoyé, rien n'est exécuté, rien n'est dépensé.

13.8 Les logs techniques

K7

Pourquoi

Quand le serveur de l'atelier tourne depuis trois semaines, personne ne lance loom inspect : on lit les logs, souvent dans un outil qui les collecte. Ils doivent être dans un format que cet outil comprend.

Ce qu'il faut comprendre

Les logs sont des messages techniques, écrits sur la sortie d'erreur par le module logging de Python. Ils sont distincts du journal : ils ne font pas foi, ne se rejouent pas, et peuvent être perdus sans conséquence. Depuis le module 1, loom.yaml les limite aux avertissements (level: WARNING).

Mise en place

Seule la ligne logging du bloc telemetry change :

ligne modifiée

level: INFOLe niveau minimal affiché : DEBUG, INFO, WARNING, ERROR. À INFO, une ligne par appel de modèle, par appel d'outil et par transition d'état.
format: jsonUne ligne JSON par message, pour un outil de collecte de logs. Par défaut : console, lisible à l'écran.
