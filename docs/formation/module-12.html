Module 12 : Plusieurs clients et données sensibles

Paul Martin, chauffagiste dans le quartier voisin, a vu l'assistant de Jean et en veut un. Plutôt qu'une seconde installation, la même instance va servir les deux entreprises. Chacune aura son espace : son journal, ses données, ses outils, ses secrets, ses limites. Puis on protège ce qu'elles confient à loom : chiffrement, effacement, isolation dans la base.

Agent
assistant, dans le dossier plomberie-dupont/
Départ
la fin du module 11 : l'agent est servi par une API protégée par des clés, et le CRM le déclenche par une porte d'entrée
Arrivée
la même instance sert la Plomberie Dupont et le Chauffage Martin, chacun dans son espace ; vous savez chiffrer, effacer et isoler leurs données
Fonctions

Point de départ : les fichiers au début du module

Extras installés : anthropic, http, mcp, openai, postgres, rabbitmq, redis, sqlite. La clé d'API app-dupont du module 10 est dans la variable CLE du terminal.

Et pyproject.toml, écrit par uv, qui dit quels extras de loom-ia sont installés (pour repartir de ce point : uv sync) :

Dans loom, une entreprise servie par l'instance s'appelle un client (tenant en anglais). Depuis le module 1, tout se passait chez un client unique, nommé default : c'est le default que vous voyez dans data/default/. Ce module en ajoute un second, martin-chauffage. Les exercices 12.1 à 12.6 construisent son espace ; les exercices 12.7 à 12.9 protègent les données des deux clients.

12.1 Un second client sur la même instance

L1

Pourquoi

Paul Martin veut le même assistant que Jean, avec le nom de son entreprise. Les deux ne doivent jamais voir les conversations l'un de l'autre.

Mise en place

Depuis le module 3, loom.yaml se termine par une liste tenants qui ne contenait que default. On y ajoute le Chauffage Martin. Pour les trois premiers exercices, on remet aussi la capture des requêtes envoyées au modèle (vue au module 3), pour voir ce que chaque client lui envoie. Seuls les blocs telemetry et tenants changent ; le reste du fichier est celui du point de départ.

lignes ajoutées

capture: {raw_exchanges: true}Garder au journal la requête exacte envoyée au modèle (événement model.exchanged). On la retirera à la fin de l'exercice 12.3.
- id: martin-chauffageUn second client. L'identifiant sert partout : option --tenant, clés d'API, dossier du journal.
variables:Les valeurs des variables {{ }} des prompts pour ce client (module 3).

Exécution

Ce qu'il faut comprendre

  • Le journal de Martin vit dans data/martin-chauffage/, à côté de data/default/. Chaque commande ne voit que les sessions du client au nom duquel elle agit : la session essai-martin n'apparaît pas chez Dupont.
  • Dès qu'une liste tenants existe, elle est fermée : un client qui n'y est pas est refusé (code 2), au lieu d'ouvrir un espace par erreur.
  • Les deux clients partagent tout le reste : les mêmes agents, les mêmes prompts, les mêmes outils, le même processus.

Piège : regardez la réponse faite à Martin

Martin a obtenu le montant d'un devis de la Plomberie Dupont. loom a bien rangé son run dans son espace, mais l'outil chercher_devis lit un carnet unique, celui de Dupont. loom isole ce qu'il garde lui-même (journal, fichiers, secrets) ; vos outils doivent isoler vos données. C'est l'exercice 12.2.

12.2 Des outils qui savent pour qui ils travaillent

L1

Pourquoi

Chaque entreprise a ses devis. L'outil doit lire le carnet du client pour qui le run tourne.

Mise en place

Un outil Python peut recevoir un paramètre ctx: ToolContext (vu au module 10 pour envoyer_email). Son attribut ctx.tenant_id donne le client du run. Le carnet unique DEVIS devient un carnet par client, CARNETS, et les deux outils qui le lisent passent par la fonction carnet(ctx). Le Chauffage Martin a un devis, M-2026-017 (entretien de chaudière chez Mme Petit, 189 € TTC).

lignes ajoutées ou modifiées

Le paramètre ctx n'apparaît pas dans le schéma que voit le modèle : loom le remplit lui-même. Un client absent de CARNETS obtient un carnet vide, jamais celui d'un autre.

Reste le modèle simulé : son script joue les scènes de Dupont. Martin aura le sien. Plutôt que de toucher à l'agent, on déclare que, pour ce client, le modèle SIMULE est remplacé par SIMULE_MARTIN. On déclare ce modèle à la suite de SIMULE dans models, puis la correspondance dans le bloc du client :

lignes ajoutées

models:Remplacement de modèles pour ce client : {modèle de la config: modèle de ce client}. Il vaut partout où le modèle est cité : orchestrateur, rôles, juges, modèles de secours, compaction. Les deux doivent être déclarés dans models. En vrai, c'est ainsi qu'un client paie un modèle plus cher, ou moins cher, que les autres.

12.3 Ce que chaque client peut changer, et les outils qu'il voit

L1D7

Pourquoi

Le catalogue du fournisseur (module 5) est celui de Dupont : Martin n'y a pas de compte. Et Martin n'a pas de clients anglophones : la traduction ne lui sert à rien.

Ce qu'un client peut surcharger

Un client partage la configuration commune, et ne peut en changer qu'une liste fermée d'éléments. Les prompts n'en font pas partie : seules leurs variables changent d'un client à l'autre, ce qui garde la logique métier en un seul endroit.

agentsLes agents que ce client peut lancer (vide : tous).
tools_denyLes outils retirés à ce client, sous le nom que voit le modèle : outil Python, outil MCP (préfixe compris), rôle ou sous-agent.
modelsLe remplacement de modèles (exercice 12.2).
approvalsUne approbation imposée par outil (never, always, policy), quoi qu'en dise l'outil : c'est le client qui sait ce qui l'engage (module 8).
secretsSes secrets à lui (exercice 12.4).
variablesLes valeurs des variables des prompts (exercice 12.1).
budgetsSes budgets, dont les plafonds par jour ou par mois (module 9).
quotasSon débit de runs (exercice 12.6).
storageUn journal à lui, dans une autre base ou un autre dossier : l'isolation physique. Le bloc doit alors déclarer events.
retentionSa durée de conservation (exercice 12.8).
telemetryCe qui est capturé de ses runs (module 13).

Ce qu'il faut comprendre

Les outils proposés au modèle sont choisis à chaque run. Trois filtres s'appliquent, et vous les avez tous vus :

  1. le client : tools_deny retire les outils du catalogue et traduire pour Martin ;
  2. la demande et les capacités du modèle : decrire_photo manque dans les deux listes, parce que le run n'a pas de pièce jointe (module 6) ;
  3. la source : include et exclude d'un serveur MCP (module 5).

Un outil retiré n'est pas seulement caché : le modèle ne peut pas l'appeler, même s'il en devinait le nom.

Piège : le prompt parle encore du catalogue

Le prompt commun dit d'utiliser les outils du catalogue. Pour Martin, ils n'existent pas : un vrai modèle lit une consigne sur des outils qu'il n'a pas, et au mieux il fait sans. Les prompts n'étant pas surchargeables, écrivez-les pour qu'ils restent justes quand un outil manque, ou passez la consigne par une variable du client.

12.4 Chaque client ses secrets

L2

Pourquoi

Martin veut payer lui-même sa consommation chez Anthropic : ses runs doivent partir avec sa clé, jamais avec celle de Jean.

Mise en place

La configuration ne nomme que des variables d'environnement (api_key_env: ANTHROPIC_API_KEY, module 1). Un client peut rediriger ce nom vers une variable à lui. Pour l'essai, Martin passe aussi sur le vrai modèle HAIKU :

lignes modifiées ou ajoutées

secrets:Les redirections de ce client : {nom attendu par la config: variable de ce client}. Ce qui n'y est pas reste lu dans l'environnement commun.
ANTHROPIC_API_KEY: MARTIN_ANTHROPIC_KEYPour Martin, la clé d'Anthropic se lit dans MARTIN_ANTHROPIC_KEY.

La clé de Martin irait dans le fichier .env, à côté de celle de Jean : MARTIN_ANTHROPIC_KEY=…. Pour l'essai, ne la mettez pas.

À retenir

  • Toute clé nommée par la configuration se redirige ainsi : clé d'un modèle, DSN d'une base, et, pour un serveur MCP, les variables de env_from et headers_env (avec la portée tenant du module 5, chaque client a sa propre connexion et ses propres secrets).
  • Remettez le bloc de Martin comme avant l'essai : models: {SIMULE: SIMULE_MARTIN}, sans secrets.

Variante vrai modèle

Avec une vraie clé dans MARTIN_ANTHROPIC_KEY (rappel), les runs de Martin sont facturés sur son compte Anthropic, ceux de Jean sur le sien.

12.5 Le client vient de la clé d'API

L1

Pourquoi

Martin utilisera l'assistant depuis son application, par l'API REST (module 10). Ce n'est pas à l'application de dire « je suis Martin » : c'est sa clé qui en décide.

Mise en place

loom keys create prend l'option --tenant : la clé agira au nom de ce client.

$ loom keys create app-martin --tenant martin-chauffage --scope run --scope read --scope read_content
Clé        : lk_YCB_CC…
Elle n'est affichée qu'ici : la config ne garde que son empreinte.

À ajouter dans la configuration :

security:
  api_keys:
    - id: app-martin
      hash: sha256:a6f53eb35aa119e3d51310ac7316564db661d58075c859975f2f208d622f9510
      tenant: martin-chauffage
      scopes: [run, read, read_content]

(La clé est abrégée ici.) Gardez-la dans une variable du terminal, CLE_MARTIN, comme CLE au module 10, et ajoutez le bloc proposé dans security.api_keys :

12.6 Quotas et débit

L3

Pourquoi

Une application qui boucle par erreur pourrait lancer des centaines de runs et ralentir le service des deux entreprises. On limite le débit de chaque client, et celui de chaque clé.

Mise en place

lignes ajoutées

quotas: {runs_per_minute: 2}Martin peut lancer 2 runs par minute, quel que soit l'accès (REST, MCP, porte d'entrée, librairie). Au-delà : refus.
rate_limit: {per_minute: 3}La clé app-martin peut faire 3 requêtes par minute, quelles qu'elles soient. Au-delà : refus 429. C'est l'option --rate-limit de loom keys create.

Exécution

Relancez le serveur, puis envoyez quatre demandes de suite avec la clé de Martin. On n'affiche que le code HTTP et le statut, ou le motif du refus :

$ loom serve &

12.7 Chiffrer le journal, une clé par client

P1

Pourquoi

Le journal contient les noms, les adresses e-mail et les montants des clients de Jean et de Paul. Un disque volé, une sauvegarde égarée ne doivent rien livrer. Et si Martin quitte le service, ses données doivent pouvoir devenir illisibles pour de bon.

Mise en place

Le chiffrement demande l'extra crypto. Comme toujours, redonnez la liste complète des extras :

$ uv add "loom-ia[anthropic,crypto,http,mcp,openai,postgres,rabbitmq,redis,sqlite]"

On déclare le sceau dans storage, et chaque client redirige le nom du secret vers sa variable :

lignes ajoutées

Une clé est faite de 32 octets tirés au hasard, écrits en base64. Fabriquez les vôtres, directement dans le fichier .env (ne les recopiez jamais ailleurs, et ne réutilisez pas celles d'un exemple) :

$ echo "MARTIN_JOURNAL_KEY=$(openssl rand -base64 32)" >> .env

Ces clés sont aussi précieuses que les données : perdues, le journal est perdu. En production, elles vivent dans un gestionnaire de secrets, sauvegardées à part du journal.

12.9 Isoler les clients dans PostgreSQL

P3

Pourquoi

Avec un journal partagé, loom ajoute « pour ce client seulement » à chacune de ses lectures. Mais un script d'exploitation qui lirait la table directement, ou une requête qui l'oublierait, verrait les deux clients. Avec PostgreSQL, on place la barrière dans la base : une politique de lignes refuse de montrer ou d'écrire une ligne d'un autre client.

Mise en place

Reprenez le serveur PostgreSQL du module 4 (sinon : docker run -d --name loom-pg -e POSTGRES_PASSWORD=admin -p 15432:5432 postgres:16). Pièges

  • L'oubli est silencieux, et c'est voulu. Un script d'exploitation qui ne pose pas loom.tenant_id ne trouve rien, au lieu de tout voir. S'il « ne trouve rien », c'est qu'il n'a pas dit pour quel client il lit.
  • La sauvegarde. Il faut un rôle d'exploitation qui échappe aux politiques, ou une sauvegarde physique, et tester la restauration.
  • Rôle déjà existant. Les rôles PostgreSQL valent pour tout le serveur. Si loom_app a été créé par un autre utilisateur (au module 4, par loom_login), seul lui ou un superutilisateur peut l'accorder : appliquez le script avec un rôle qui en a le droit.

À retenir

La table d'idempotence n'a pas de politique de lignes : ses clés sont préfixées par le client. Et pour une séparation complète, un client peut avoir sa propre base (storage dans son bloc, exercice 12.3).
