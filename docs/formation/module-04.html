Module 4 : Conversations, mémoire et state

Jusqu'ici, chaque run repartait de zéro : l'agent oubliait tout entre deux questions. Ce module lui donne la mémoire d'une conversation. Vous verrez ce que loom renvoie au modèle d'un run à l'autre, comment il résume une conversation devenue trop longue, où il range ce journal (fichiers, SQLite, Postgres), comment on supprime les données d'un client, et comment l'agent garde en tête le devis dont on parle.

se souvient du chantier d'un run à l'autre et retient le devis en cours dans son state

4.1 Deux questions, deux runs : l'agent oublie

F1

Pourquoi

Jean demande une relance pour le devis D-2026-042, puis, juste après : « Et quel était le montant ? ». Pour lui, c'est la même conversation. Pour loom, pour l'instant, ce sont deux runs sans rapport.

Mise en place

Pour ce module, remplacez le script du modèle simulé par celui-ci, et remettez raw_exchanges, vu au module 3 : il garde au journal chaque requête envoyée au modèle, et c'est elle qui montre ce que le modèle « se rappelle ».

lignes ajoutées ou modifiées

Exécution

$ loom run assistant "Relance le devis D-2026-042"
Voici une relance pour Mme Martin : « Bonjour Madame, nous revenons vers vous au sujet de notre devis D-2026-042 du 3 septembre 2026 pour le remplacement de votre chauffe-eau. Souhaitez-vous que nous planifiions l'intervention ? »

Statut     : completed · itérations : 2 · tokens : 1574/148 · coût : 0.0000 $
Run        : 01a16e05-9679-74dc-be0e-622355edd9b2
$ loom run assistant "Et quel était le montant ?"
Le devis D-2026-042 s'élève à 1 840 € TTC.

Statut     : completed · itérations : 1 · tokens : 667/35 · coût : 0.0000 $
Run        : 01a16e05-9c64-74a8-b1d8-51b93513ac50
$ ls data/default/
01a16e05-9679-74dc-be0e-622355edd9b2.jsonl
01a16e05-9c64-74a8-b1d8-51b93513ac50.jsonl

Deux runs, deux fichiers de journal : sans indication, chaque run est sa propre session, nommée comme le run. Regardez ce que le second run a envoyé au modèle. Deux commandes : la première extrait du journal la dernière requête envoyée (événement model.exchanged) et l'écrit dans requete.json ; la seconde liste ses messages, avec le rôle de chacun et le type de ses blocs.

$ jq -r 'select(.type=="model.exchanged") | .payload.request_body' data/default/01a16e05-9c64-74a8-b1d8-51b93513ac50.jsonl | tail -1 > requete.json
$ jq -r '.messages[] | "\(.role) : \([.blocks[].type] | join(", "))"' requete.json
user : text

Ce qu'il faut comprendre

  • La requête ne contient qu'un message : la question. Rien de la relance demandée juste avant. Un vrai modèle ne pourrait pas savoir de quel devis on parle.
  • Le modèle simulé répond quand même « 1 840 € TTC » : il récite son script, sans rien lire. C'est la requête, pas sa réponse, qui dit ce que le modèle a reçu.

4.2 Une conversation : --session

F1

Pourquoi

Pour que le second run reprenne la conversation, il faut dire à loom que les deux runs vont ensemble.

Exécution

L'option --session, vue au module 1 pour nommer un run, sert à cela : tous les runs qui portent le même nom de session écrivent dans le même journal, et chacun relit ce qui précède.

$ loom run assistant "Relance le devis D-2026-042" --session chantier-martin
Voici une relance pour Mme Martin : « Bonjour Madame, nous revenons vers vous au sujet de notre devis D-2026-042 du 3 septembre 2026 pour le remplacement de votre chauffe-eau. Souhaitez-vous que nous planifiions l'intervention ? »

Statut     : completed · itérations : 2 · tokens : 1574/148 · coût : 0.0000 $
Run        : 01a16e05-a160-72fc-a843-bf076a2f3b56
$ loom run assistant "Et quel était le montant ?" --session chantier-martin
Le devis D-2026-042 s'élève à 1 840 € TTC.

Statut     : completed · itérations : 1 · tokens : 1020/35 · coût : 0.0000 $
Run        : 01a16e05-a6dc-7337-84ec-19c0b96b291c
$ ls data/default/
01a16e05-9679-74dc-be0e-622355edd9b2.jsonl
01a16e05-9c64-74a8-b1d8-51b93513ac50.jsonl
chantier-martin.jsonl
$ jq -r 'select(.type=="model.exchanged") | .payload.request_body' data/default/chantier-martin.jsonl | tail -1 > requete.json
$ jq -r '.messages[] | "\(.role) : \([.blocks[].type] | join(", "))"' requete.json
user : text
assistant : text, tool_call
tool : tool_result
assistant : text
user : text

Ce qu'il faut comprendre

  • Les deux runs sont dans un seul fichier, chantier-martin.jsonl.
  • La requête du second run contient maintenant toute la conversation : la demande de relance (user), la réponse du modèle avec son appel d'outil (assistant : text, tool_call), le résultat de chercher_devis (tool), la relance rédigée, puis la nouvelle question. Un vrai modèle y trouve le devis et son montant.
  • Les tokens d'entrée passent de 667 à 1 020 : se souvenir a un coût, puisque tout l'historique repart à chaque appel. L'exercice 4.4 montre comment loom le contient.

Variante vrai modèle

Avec HAIKU (rappel), faites la même chose sans --session : Claude répond qu'il ne sait pas de quel devis vous parlez. Avec --session, il retrouve 1 840 € TTC dans le résultat de l'outil. Le cache de prompt (module 3) prend ici tout son sens : l'historique déjà envoyé est relu depuis le cache.

4.3 D'où vient l'historique : le journal

F2

Pourquoi

loom ne garde pas « la conversation » à part : il la reconstruit à partir du journal. Comprendre ce mécanisme explique la suite du module, et pourquoi un run peut reprendre après un plantage (module 8).

Exécution

Chaque ligne du journal est un événement, numéroté dans l'ordre (seq). Listons-les :

$ jq -r '"\(.seq) \(.type)"' data/default/chantier-martin.jsonl
1 run.started
2 message.user
3 run.claimed
4 step.started
5 model.exchanged
6 model.responded
7 step.completed
8 run.transitioned
9 step.started
10 tool.called
11 tool.completed
12 step.completed
13 run.transitioned
14 step.started
15 model.exchanged
16 model.responded
17 step.completed
18 run.transitioned
19 run.completed
20 run.started
21 message.user
22 run.claimed
23 step.started
24 model.exchanged
25 model.responded
26 step.completed
27 run.transitioned
28 run.completed

Ce qu'il faut comprendre

  • Le premier run va de 1 (run.started) à 19 (run.completed), le second de 20 à 28. On y retrouve le message de l'utilisateur (message.user), chaque réponse du modèle (model.responded), l'appel et le résultat de l'outil (tool.called, tool.completed).
  • Pour construire la requête d'un run, loom relit ces événements et en tire la liste de messages vue en 4.2. On dit que l'historique est une projection du journal. Il est structuré : un appel d'outil reste un appel d'outil, un résultat reste un résultat, rien n'est aplati en texte. Ce format est le même quel que soit le fournisseur ; l'adaptateur le traduit au moment de l'appel (module 3).

Les snapshots

Relire tout le journal à chaque run coûterait de plus en plus cher. loom écrit donc de temps en temps un snapshot : l'historique déjà calculé, rangé dans le journal. Le run suivant part du snapshot et ne relit que ce qui suit. Par défaut, un snapshot est écrit tous les 50 événements. Pour le voir apparaître, réglez ce seuil à 20, dans un nouveau bloc sessions :

lignes ajoutées

sessions:Les réglages de la vie d'une session : snapshots, résumés, images, state.
snapshot_every: 20Nombre d'événements après lequel un snapshot est écrit. Défaut : 50.

4.4 Résumer une conversation trop longue : la compaction

F3

Pourquoi

Un chantier peut durer des semaines. À force, l'historique dépasserait la fenêtre du modèle (module 3), et chaque appel coûterait de plus en plus cher. La compaction remplace la partie ancienne de la conversation par un résumé, écrit par un modèle dédié, en général moins cher.

Mise en place

Le résumé est écrit par un modèle. Pour l'exercice, on déclare un second modèle simulé, RESUME, dont le script contient le résumé. On règle la compaction avec un seuil volontairement très bas, 300 tokens, pour la déclencher tout de suite :

lignes ajoutées

- id: RESUME …Un second modèle simulé, qui ne sert qu'aux résumés. Son nom chez le « fournisseur », fake-resume, est libre.
compaction:Active la compaction. Sans ce bloc, une session n'est jamais résumée.
model: RESUMELe modèle qui écrit les résumés. En production, un modèle léger comme HAIKU.
over_tokens: 300Taille de l'historique (estimée : caractères divisés par 4) au-delà de laquelle un résumé est fait. Défaut : 12 000.
keep_last: 1Nombre de tours (de runs) les plus récents gardés intacts, sans résumé. Défaut : 6.
blocking: trueLe résumé se fait à l'ouverture du run suivant, qui l'attend. Avec false (défaut), il se fait en tâche de fond après le run : bien pour un serveur, pas pour loom run, qui se ferme aussitôt.

loom monte pour cela un agent interne, _compaction, avec un prompt fourni (on peut le remplacer par system_file) :

$ loom validate | tail -5
    assistant : modèle SIMULE, 4 outil(s) Python
    _compaction : modèle RESUME, 0 outil(s) Python
      politique loom.fidelity : on_output

1 agent(s) monté(s) sans erreur.

Exécution

La session chantier-martin dépasse déjà 300 tokens (485 selon le snapshot). Le run suivant déclenche donc un résumé :

Ce qu'il faut comprendre

  • La ligne Compaction du bilan : l'historique ancien (jusqu'à l'événement 28, soit les deux premiers runs) est passé de 419 à 93 tokens estimés. Le dernier tour est gardé intact (keep_last: 1).
  • La requête commence maintenant par le résumé, présenté comme tel au modèle, suivi du dernier tour gardé, puis de la nouvelle question.
  • Rien n'est effacé : le journal garde tous les anciens événements. La compaction ajoute un marqueur, session.compacted, et l'historique repart du résumé pour tout ce qui précède.
  • loom sessions show (vu en 4.7) montre le run de l'agent _compaction au milieu de la session.
  • Le contrôle de fidélité : loom vérifie que les repères du passage résumé (numéros, montants, dates, adresses e-mail) se retrouvent dans le résumé. Ici, il est passé : fidélité vérifiée.

Piège : un résumé qui perd les montants

Remplacez le résumé de RESUME par un texte vague, deux fois (une pour le premier essai, une pour la réparation) :

        - text: "Jean Dupont a demandé une relance pour Mme Martin, et l'agent l'a rédigée."
        - text: "Jean Dupont a demandé une relance pour Mme Martin, et l'agent l'a rédigée."

Sur une nouvelle session de trois runs, le résumé est refusé une première fois et renvoyé à son modèle, puis accepté avec une alerte :

Compaction : 352 → 42 tokens estimés (jusqu'à l'événement 19, 1 tour(s) gardé(s), fidélité douteuse)
$ jq -c 'select(.type=="guard.checked") | .payload | {outcome, resolution, attempt, reason}' data/default/essai-resume.jsonl
{"outcome":"failed","resolution":"retry","attempt":1,"reason":"repères absents du résumé : D-2026-042, 2026, 042, martin@example.fr, 1533,33, 1840"}
{"outcome":"failed","resolution":"unverified","attempt":2,"reason":"repères absents du résumé : D-2026-042, 2026, 042, martin@example.fr, 1533,33, 1840"}

Le résumé est gardé mais marqué fidélité douteuse : la suite de la conversation a perdu le numéro du devis et son montant. Avec un vrai modèle, gardez le contrôle activé (fidelity_check: true, la valeur par défaut) et surveillez ces alertes.

Avant la suite, retirez le modèle RESUME et le bloc compaction : avec un seuil de 300 tokens, chaque conversation des exercices suivants serait résumée. Le fichier redevient celui de l'exercice 4.3.

4.5 Ce qui est retiré de l'historique

F4

Pourquoi

Tout ne mérite pas d'être renvoyé à chaque appel. Deux choses sont allégées : le raisonnement du modèle (sa réflexion avant de répondre, que Claude produit avec le mode thinking) et les images, lourdes.

Mise en place

Repartez du fichier de l'exercice 4.3 et ajoutez une scène : Jean demande l'étiquette du devis (l'outil etiquette_devis du module 2 rend une image). La première réponse du modèle simulé porte un raisonnement, grâce à la clé reasoning :

lignes ajoutées

4.6 Où vit le journal : mémoire, fichiers, SQLite, Postgres

F5

Pourquoi

Le journal est la mémoire de l'agent : conversations, résultats, coûts. Des fichiers JSONL suffisent sur un poste. Pour un service, on veut une base de données. loom en propose quatre, sans rien changer aux agents : c'est le rôle de storage.events.

backendOùPour quoi
memoryen mémoire, perdu à la fin de la commandetests, scripts jetables (c'est le défaut sans storage)
jsonlun fichier par session dans un dossierun poste, un petit service
sqliteune base SQLite, un seul fichierun service sur une seule machine
postgresun serveur PostgreSQLun service avec plusieurs process ou plusieurs machines

Le journal en mémoire

Changez temporairement la ligne events :

$ loom validate | grep -E 'Journal|Artefacts'

Artefacts  : memory
$ loom run assistant "Et quel était le montant ?" --session en-memoire
Le devis D-2026-042 s'élève à 1 840 € TTC.

Statut     : completed · itérations : 1 · tokens : 742/35 · coût : 0.0000 $

Journal en mémoire : il ne vit que le temps d'un process ; cette commande ne voit pas les runs des autres commandes loom.
Aucune session.

Le run a tourné, mais loom sessions list (une autre commande, donc un autre process) ne le voit pas : le journal en mémoire est mort avec la commande loom run. loom le dit en tête de sortie.

PostgreSQL

Il faut un serveur PostgreSQL. Le plus simple, sur votre poste, est un conteneur Docker :

$ docker run -d --name loom-pg -e POSTGRES_PASSWORD=admin -p 15432:5432 postgres:16

Créez ensuite un utilisateur et une base pour loom (l'outil psql est le client en ligne de commande de PostgreSQL) :

$ psql -h 127.0.0.1 -p 15432 -U postgres -c "create role loom_login login createrole password 'mot-de-passe'" -c "create database loom owner loom_login"
CREATE ROLE
CREATE DATABASE

L'utilisateur loom_login a le droit de créer des rôles (createrole) : au premier run, loom préparera lui-même sa table et le rôle sous lequel il travaille. Le module 12 montre comment confier cette préparation à un administrateur et isoler les clients en base.

Dans la configuration, l'adresse de connexion (le DSN) contient un mot de passe : c'est un secret. Comme la clé d'API, on n'écrit que le nom de la variable qui la contient :

backend: postgresLe journal dans PostgreSQL.
dsn_env: LOOM_DSNLa variable d'environnement qui contient l'adresse de connexion.
artifacts:Où ranger les fichiers (images, gros résultats). Avec SQLite ou JSONL, ils vont par défaut à côté du journal ; avec Postgres, il faut le dire.
{backend: local, path: data/fichiers}Dans un dossier local, data/fichiers.

À retenir

  • Changer de backend ne change rien aux agents : seule la ligne storage.events change. Mais les données ne sont pas migrées d'un backend à l'autre.
  • Pour la suite de la formation, revenez au JSONL : remettez events: {backend: jsonl, path: data}, retirez la ligne artifacts et supprimez le fichier .env qui ne contenait que LOOM_DSN (gardez-y votre clé d'Anthropic si vous en avez une). Les extras sqlite et postgres peuvent rester installés.

4.7 Lister, exporter, supprimer une session

F7

Pourquoi

Le journal contient des données personnelles : noms, adresses e-mail, montants. Le RGPD donne à chacun le droit d'obtenir une copie de ses données et d'en demander l'effacement. Mme Martin pourrait le demander à Jean. La commande loom sessions regroupe ce qu'il faut.

4.8 Le state de session : ce que l'agent doit garder en tête

F8

Pourquoi

Jean demande une relance du devis D-2026-042, puis : « Refais-la, plus ferme. » La seconde demande ne cite plus aucun devis. L'historique le contient, mais un résumé (4.4) pourrait le perdre, et rien n'oblige le modèle à le retrouver. Le state de session règle cela : quelques valeurs typées, déclarées clé par clé, que la session garde d'un run à l'autre et que la compaction ne touche pas.

Mise en place

Le state se déclare dans le fichier de l'agent. Deux clés : le devis en cours, posé automatiquement par l'outil chercher_devis, et le ton des relances, choisi par Jean. On demande aussi que l'orchestrateur reçoive ce state :

lignes ajoutées

context: [session_state]Le contexte donné à l'orchestrateur en plus de la conversation : ici, le state de la session.
state:Les clés du state. Une clé non déclarée est refusée.
devis_courant:Le nom de la clé (lettres, chiffres, _).
schema: {type: string}La forme de la valeur, en JSON Schema : ici, du texte. Une valeur qui ne la respecte pas est refusée.
description:Ce que désigne la clé ; le modèle la reçoit avec la valeur.
from:Les outils dont un résultat réussi pose la clé.
- tool: chercher_devisL'outil.
path: /numeroOù prendre la valeur dans le résultat (un pointeur JSON : /numero est le champ numero). Si le champ manque, l'écriture est refusée et le modèle le sait (on_missing: refuse, par défaut ; ignore pour ne rien faire).
schema: {enum: [cordial, ferme]}Une valeur parmi une liste.
default: cordialLa valeur lue tant que personne n'en a posé. Elle n'est jamais écrite dans le state.

Il existe aussi required: true : le run est refusé tant que la clé n'a pas de valeur (utile pour une signature que l'application doit fournir). Une valeur fait au plus 1 Kio, et tout le state 4 Kio (réglables par sessions.state.max_value_bytes et max_total_bytes) : le state reste petit, car il part avec chaque appel.

Ajoutez au script du modèle simulé la réponse à « Refais-la » :

lignes ajoutées

Exécution

Voici une relance pour Mme Martin : « Bonjour Madame, nous revenons vers vous au sujet de notre devis D-2026-042 du 3 septembre 2026 pour le remplacement de votre chauffe-eau. Souhaitez-vous que nous planifiions l'intervention ? »

loom state affiche le state d'une session : devis_courant a été posé par le résultat de chercher_devis. ton n'y est pas : sa valeur par défaut est lue, jamais écrite. Pour la seconde demande, Jean choisit le ton avec l'option --state CLE=VALEUR :

$ loom run assistant "Refais-la, plus ferme" --session relance-martin --state ton=ferme
Voici une relance plus ferme pour le devis D-2026-042 : « Madame, sans réponse de votre part à notre devis du 3 septembre 2026, nous vous remercions de nous indiquer sous huit jours si vous souhaitez le remplacement de votre chauffe-eau. »

Statut     : completed · itérations : 1 · tokens : 1296/85 · coût : 0.0000 $
Run        : 01a16e06-5fb4-708d-8857-58d082ec8f95
$ loom state relance-martin
{
  "devis_courant": "D-2026-042",
  "ton": "ferme"
}

Voici ce que l'orchestrateur a reçu, à la fin de la dernière requête :

$ jq -r 'select(.type=="model.exchanged") | .payload.request_body' data/default/relance-martin.jsonl | tail -1 > requete.json
$ jq -r '.messages[-1].blocks[-1].text' requete.json
<session_state>
{"devis_courant":"D-2026-042","ton":"ferme"}
</session_state>

loom refuse ce qui ne respecte pas la déclaration, avant d'ouvrir le run (code 2) :

$ loom run assistant "Bonjour" --session relance-martin --state client=Martin
Demande refusée : State refusé : client : clé non déclarée dans 'state'
$ loom run assistant "Bonjour" --session relance-martin --state ton=agressif
Demande refusée : State refusé : ton : ne suit pas son schéma — doit valoir l'une des valeurs ['cordial', 'ferme']

Ce qu'il faut comprendre

  • Le state est ajouté à la fin du dernier message de la requête, à chaque appel. Placé là, il peut changer sans invalider le cache de l'historique qui le précède.
  • Il est mis à jour pendant le run : la première requête du premier run ne contenait que {"ton":"cordial"} ; la deuxième, après l'appel à chercher_devis, contenait déjà "devis_courant":"D-2026-042".
  • Chaque écriture est dans le journal : dans le résultat de l'outil (tool.completed) et dans l'ouverture du run pour --state. Une reprise ou un rejeu retrouve donc le même state.

Variante vrai modèle

Avec HAIKU, la seconde demande « Refais-la, plus ferme » suffit : Claude lit dans le state le devis en cours et le ton demandé, même si la conversation a été résumée entre-temps.

Bilan du module

L'agent tient une conversation et garde le devis en cours dans son state. Pour la suite, on ne garde que ce qui sert : le journal JSONL, le state et son contexte. La compaction, les snapshots fréquents et raw_exchanges étaient des réglages d'exercice : on les retire. En production, activez la compaction avec un modèle léger, par exemple model: HAIKU et les seuils par défaut.

(les lignes raw_exchanges et le bloc sessions sont retirées par rapport à l'exercice 4.8)

prompts/system.md et outils.py n'ont pas changé. Le paquet a maintenant les extras anthropic, openai, postgres et sqlite. Vous pouvez supprimer requete.json et chantier-martin.jsonl, fichiers d'exercice.

Au module 5, l'agent utilisera des outils qui ne sont pas écrits en Python dans le projet : ceux d'un serveur MCP, dont une mémoire qui dure au-delà d'une conversation.
