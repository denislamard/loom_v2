Référence : CLI et configuration

Cette annexe rassemble tout ce que la formation présente au fil des modules : les commandes de loom et les clés de configuration. Elle sert à retrouver une option ou une valeur par défaut. Pour comprendre à quoi sert une fonction, suivez le lien vers le module qui l'explique.

Relevé sur loom-ia 2.0.11 : aide de chaque commande (loom <commande> --help) et schémas publiés (loom schema pour loom.yaml, agent_json_schema() pour les fichiers d'agent).

  • La commande loom : options communes, codes de sortie, puis chaque commande.
  • Le fichier loom.yaml, rubrique par rubrique.
  • Le fichier d'agent (agents/*.yaml).
  • Les blocs partagés : contrat de sortie, surcharges d'outil, réglages llm, budgets.

La commande loom

Forme générale : loom <commande> [options] [arguments]. La commande cherche loom.yaml dans le dossier courant. Sans commande, loom affiche son usage et s'arrête en erreur.

Options communes à toutes les commandes

Elles s'écrivent avant ou après le nom de la commande : loom --profile dev validate et loom validate --profile dev sont équivalents.

OptionEffetVue au
--config FICHIERFichier de configuration à lire. Défaut : loom.yaml du dossier courant.—
--profile dev|prodProfil actif. L'emporte sur la variable LOOM_PROFILE et sur la clé profile.module 3
--env-file FICHIERFichier de variables à lire, à la place de env_file: ou du .env voisin de la config. Une variable déjà définie dans l'environnement l'emporte.module 3
--no-env-fileNe lit aucun fichier de variables.module 3
-h, --helpAide de la commande.—
--versionVersion installée (seulement avant toute commande : loom --version).module 1

Beaucoup de commandes acceptent aussi --tenant CLIENT (le client au nom duquel agir ; défaut : celui de la config, sinon default, voir le module 12), --session SESSION (le journal où chercher le run) et --json (le résultat en JSON, pour un programme).

Codes de sortie

CodeSignification
0Succès : run terminé (completed), configuration valide, commande menée à bien.
1Le run n'a pas abouti : échec (failed), pause en attente d'approbation (paused), annulation.
2Refus avant d'agir : configuration invalide, argument manquant ou faux, demande refusée (state invalide, approbation périmée, plafond atteint…).

Cas particuliers : loom replay rend 1 quand le rejeu exact diverge, ou quand une variante ne va pas au bout ; un journal abîmé rend 1.

loom validate

Charge la configuration, vérifie sa cohérence, monte les agents et affiche ce qu'il a compris. N'appelle aucun modèle. Vu au module 1.

loom validate [--no-keys]
--no-keys, --sans-clesMonte les agents sans créer leurs clients de modèle : une clé d'API ou un SDK absents ne font pas échouer.

loom run

Lance un run de l'agent et attend sa fin. La réponse sort sur la sortie standard, le bilan sur la sortie d'erreur. Vu au module 1.

loom run AGENT "MESSAGE" [options]
OptionEffetVue au
--session SESSIONJournal auquel rattacher le run ; le run suivant de la même session reprend la conversation.module 1, module 4
--streamAffiche la réponse au fil de l'eau, appels d'outils compris.module 10
--jsonTout le résultat en JSON sur la sortie standard.module 7
--attach FICHIERImage jointe à la demande (répétable).module 6
--judges auto|force|skipJuges : selon leur when, tous, ou aucun (skip refusé en profil prod).module 7
--state CLE=VALEURValeur du state de session posée à l'ouverture (répétable) ; la valeur est lue en JSON (3, true, null qui efface, "texte"), sinon telle quelle.module 4
--tenant CLIENTClient au nom duquel agir.module 12
--run-id IDIdentifiant choisi pour le run, à la place de celui que loom génère.—

loom inspect

Relit un run dans le journal et l'affiche en arbre : étapes, appels de modèle et d'outils, sous-runs, réponse et bilan. Vu au module 1.

loom inspect RUN_ID [--session SESSION] [--tenant CLIENT] [--full] [--json]
--fullArguments et résultats en entier, sans coupe.
--jsonLa trace en JSON, la même que GET /v1/traces/{run_id}.

loom state

Affiche le state d'une session : ce que l'application et les outils y ont écrit. Vu au module 4.

loom state SESSION_ID [--tenant CLIENT]

loom resume

Reprend un run interrompu (plantage, pause tranchée, demande expirée) là où il en était. Sur un run déjà clos, dit qu'il n'y a rien à reprendre. Vu au module 8.

loom resume RUN_ID [--session SESSION] [--tenant CLIENT] [--json]

loom approve et loom reject

Accordent ou refusent un appel d'outil qu'un run en pause attend, puis pilotent la reprise du run. Vus au module 8.

loom approve RUN_ID [--call CALL_ID] [--by NOM] [--reason MOTIF] [--arguments JSON] [--session SESSION] [--no-wait] [--json]
loom reject  RUN_ID [--call CALL_ID] [--by NOM] [--reason MOTIF] [--session SESSION] [--no-wait] [--json]
--call CALL_IDAppel visé ; sans lui, tout ce que le run attend est tranché.
--by NOMQui tranche : inscrit au journal, c'est la trace d'audit.
--reason MOTIFMotif de la décision, transmis au modèle en cas de refus.
--arguments JSON(approve seulement) Arguments corrigés de l'appel, en objet JSON complet ; demande --call.
--no-waitÉcrit la décision et sort, sans piloter la reprise.

loom report

Consommation (tokens, coût) d'un run, d'une session, ou d'un client sur la journée ou le mois. Vu au module 9.

loom report [RUN_ID] [--session SESSION] [--period day|month] [--tenant CLIENT] [--json]
RUN_IDLe run à détailler ; avec --session seule, toute la session.
--period day|monthConsommation du client sur la journée ou le mois en cours. --periode, jour et mois restent compris.

loom sessions

Gère les journaux de session : lister, consulter, récupérer les fichiers, exporter, supprimer (droit à l'effacement). Vu au module 4.

Sous-commandeEffetOptions
loom sessions listSessions du journal, la plus récente d'abord.--tenant, --json
loom sessions show SESSION_IDFiche d'une session : ses runs, et les approbations en attente avec la commande prête à lancer.--tenant, --json
loom sessions files SESSION_IDFichiers d'une session (pièces jointes, fichiers rendus par les outils, résultats déportés).--origin attachment|tool_output|offload (répétable), --out DOSSIER (les écrit sous leur vrai nom), --force, --tenant, --json
loom sessions export SESSION_IDÉcrit les événements de la session en JSONL.--out FICHIER (défaut : sortie standard), --tenant
loom sessions delete SESSION_IDSupprime la session : journal, fichiers et clés d'idempotence. Demande confirmation.--yes (sans confirmation), --tenant

Les fichiers d'une session sont aussi présentés au module 2.

loom serve

Sert l'API REST (extra http), et le serveur MCP en HTTP si server.mcp.http est activé. Vu au module 10.

loom serve [--host HOTE] [--port PORT] [--reload]
--host, --portAdresse et port d'écoute ; l'emportent sur server.http. Défaut : 127.0.0.1:8000.
--reloadRelance le serveur quand un fichier de la config change (développement ; refusé en profil prod). Une config cassée est refusée et l'ancien process continue de servir. Vu au module 10.

loom mcp

Sert les agents en MCP sur l'entrée et la sortie standard (stdio) : chaque agent publié devient un outil, accompagné de run_status, run_report et cancel. C'est la commande que lancent Claude Desktop ou Claude Code. Vu au module 10.

loom mcp [--tenant CLIENT]

loom keys create

Fabrique une clé d'API et son empreinte. La clé n'est affichée qu'une fois ; la configuration (security.api_keys) ne garde que l'empreinte. Vu au module 10.

loom keys create ID [--scope PORTEE]... [--agent AGENT]... [--tenant CLIENT] [--expires QUAND] [--rate-limit N]
IDNom de la clé dans la configuration.
--scopePortée accordée, répétable : run, read, read_content, approve, admin. Défaut : run et read.
--agentAgent autorisé, répétable. Défaut : tous.
--tenantClient au nom duquel la clé agit. Défaut : default.
--expiresFin de validité : une date (2027-01-01) ou une durée (90j, 12h).
--rate-limit NRequêtes par minute accordées à cette clé. Défaut : aucune limite.

loom worker

Consomme la file des tâches de fond (runs soumis, reprises, résumés de compaction). Exige une file partagée (storage.queue.backend: rabbitmq) ; refusé avec la file asyncio. Vu au module 11.

loom worker [--jobs N]
--jobs NTâches menées de front. Défaut : 1.

loom replay

Rejoue un run fini, à l'identique sans appeler de modèle, ou en variante (autre modèle, doublure d'outil), et dit où il s'écarte. Les outils à effet de bord ne sont jamais réexécutés. Présenté au module 13.

loom replay [RUN_ID] [--session SESSION] [--journal FICHIER] [--mode exact|variant] [--model ETAPE=MODELE] [--double OUTIL=REF] [--export FICHIER] [--json]
--journal FICHIERRejoue depuis un journal JSONL exporté, hors du journal de la config ; sans RUN_ID, chacun de ses runs finis.
--mode exact|variantexact : tout vient du journal. variant : ce que le journal ne connaît pas part pour de vrai, et les deux runs sont comparés.
--model ETAPE=MODELEVariante : autre modèle déclaré pour une étape (main, un rôle, judge:<nom>).
--double OUTIL=REFVariante : doublure d'un outil (nom enregistré ou module:fonction), appelée à la place d'un appel absent du journal.
--export FICHIERGarde le journal du rejeu en JSONL ; rien n'est écrit dans le journal de la config.

loom eval

Joue une suite d'évals : des cas et leurs attendus, pour chaque variante, en mémoire ; les outils à effets de bord sont doublés ou refusés. Présenté au module 14.

loom eval SUITE.yaml [--case NOM]... [--variant NOM]... [--export DOSSIER] [--json]
--case, --variantNe joue que ce cas, ou cette variante (répétables).
--export DOSSIERGarde le journal de chaque run, un JSONL par run (<variante>--<cas>--<n>.jsonl).

loom retention

Liste les sessions dormantes au-delà de la borne déclarée (storage.retention.events_days) et ne les efface qu'avec --yes. Rien ne s'efface tout seul. Présenté au module 12.

loom retention [--tenant CLIENT] [--yes] [--json]
--tenantUn seul client. Défaut : tous les clients déclarés.
--yesSupprime pour de bon ; sans cette option, rien n'est touché.

loom storage sql

Imprime le SQL à appliquer pour le stockage Postgres déclaré : tables, rôle applicatif, politiques par client. Vu au module 4, et au module 12 pour l'isolation des clients.

loom storage sql

loom schema

Imprime le JSON Schema de loom.yaml, pour la complétion et les erreurs en direct dans un éditeur (première ligne du fichier : # yaml-language-server: $schema=./loom.schema.json). Le schéma des fichiers d'agent s'obtient en Python avec loom_ia.config.agent_json_schema().

loom schema > loom.schema.json

Le fichier loom.yaml

Règles générales, valables pour tous les fichiers de configuration :

  • une clé inconnue est refusée au chargement, avec son chemin (code 2) ; une clé écrite deux fois aussi, avec ses deux lignes ;
  • les chemins sont relatifs au dossier de loom.yaml ; un system_file est relatif à prompts_dir ;
  • la configuration ne contient jamais un secret : les clés en _env donnent le nom de la variable d'environnement qui le porte ;
  • dans la colonne « Défaut », obligatoire veut dire que la clé doit être écrite, et null que la fonction reste inactive tant que la clé n'est pas donnée.
