Module 8 : Actions sensibles et exécution durable

Jusqu'ici, l'agent préparait l'e-mail de relance ; personne ne l'envoyait. Dans ce module, il l'envoie lui-même. Un envoi ne se rattrape pas : il faut l'accord de Jean avant, la garantie qu'il ne part qu'une fois, et un agent qui retombe sur ses pieds si le serveur s'arrête au mauvais moment.

Agent
assistant, dans le dossier plomberie-dupont/
Départ
la fin du module 7 : l'e-mail est rédigé et contrôlé, mais pas envoyé
Arrivée
l'agent envoie l'e-mail après l'accord de Jean, une seule fois, même après un plantage
Fonctions
D10H4H1H2H3D11A6A5
Point de départ : les fichiers au début du module

Extras installés : anthropic, openai, sqlite, postgres, mcp.

Et pyproject.toml, écrit par uv, qui dit quels extras de loom-ia sont installés (pour repartir de ce point : uv sync) :

Trois mots reviennent dans ce module. Un effet de bord, c'est ce qu'un outil change dans le monde extérieur : un e-mail envoyé, un paiement, une ligne écrite dans un CRM. Une approbation, c'est l'accord d'un humain avant qu'un outil ne s'exécute. Un outil idempotent produit son effet une seule fois, même si on l'appelle plusieurs fois pour la même chose.

8.1 Un outil qui agit sur le monde

D10

Pourquoi

Le rédacteur écrit l'e-mail ; il manque un outil pour l'envoyer. Mais Jean ne veut pas qu'un e-mail parte chez un client sans qu'il l'ait relu.

Mise en place

1. L'outil d'envoi. Ajoutez envoyer_email à la fin de outils.py. Pour la formation, l'envoi est simulé : chaque e-mail « envoyé » est écrit dans un fichier du dossier boite-envoi/. La pause de deux secondes imite le temps que prend un vrai envoi ; elle servira à l'exercice 8.5.

Piège : une approbation exige un journal durable

Un run en pause doit survivre à la fin de la commande qui l'a lancé : son journal doit être écrit sur disque. Avec un journal en mémoire (events: {backend: memory}), la configuration est refusée :

$ loom validate
…
Configuration : Agent 'assistant' (client 'default') : outil 'envoyer_email' en approval: always — une approbation exige un journal durable (jsonl ou sqlite ou postgres), pas 'memory' (#28)

Ici, le journal est en JSONL depuis le module 1 : tout va bien.

Ce qu'il faut comprendre

  • Après un accord, l'outil s'exécute et le run continue : l'e-mail est dans boite-envoi/, et l'orchestrateur conclut.
  • Après un refus, l'outil ne s'exécute pas. Sans cette précision, un modèle prend volontiers un refus pour une erreur technique et relance le même appel.
  • Le refus est un résultat d'erreur pour cet appel seul : le run, lui, se termine normalement (completed).
  • grep ne trouve qu'un e-mail dans la boîte d'envoi : celui de Mme Martin.

Variante vrai modèle

Avec HAIKU (rappel), la réponse finale reprend le motif du refus (« le devis est déjà accepté ») au lieu de la phrase toute faite du script.

8.3 Corriger avant d'accorder, et laisser expirer

H4

Pourquoi

Mme Martin a changé d'adresse e-mail, et Jean préfère un texte plus court. Plutôt que de refuser et de tout recommencer, il corrige l'appel au moment de l'accorder. Autre cas : une demande à laquelle personne ne répond ne doit pas rester ouverte indéfiniment.

Ce qu'il faut comprendre

  • Une demande périmée ne peut plus être tranchée : loom approve la refuse (code 2) sans rien écrire, et indique quoi faire.
  • loom resume reprend un run interrompu ou en attente. Ici, il constate l'expiration, l'écrit au journal (approval.expired, action deny), et le modèle reçoit un message qui dit que l'appel n'a pas été approuvé à temps.
  • loom ne surveille pas l'horloge en permanence : l'expiration est constatée au moment où quelqu'un s'occupe du run (resume, approve, ou un worker au module 11).

Avant la suite, retirez le bloc approval de l'agent : on revient au délai de 24 heures.

8.4 Le journal fait foi : l'état d'un run

H1H2

Pourquoi

Comment un run en pause peut-il attendre des heures, puis reprendre dans une autre commande, voire sur un autre serveur ? Parce que tout ce qu'il sait est écrit dans son journal, au fur et à mesure.

À partir de ces événements, loom reconstruit l'état complet du run. On peut le lui demander depuis Python. Créez ce petit script dans le dossier du projet ; la librairie Python sera présentée au module 10, voici juste ce qu'il faut pour le lire :

from loom_ia.access import LoomLa classe qui donne accès à loom depuis Python, comme la commande loom en ligne de commande.

await loom.state(run_id, session_id=…)Relit le journal du run et en déduit son état : statut, étape, messages, consommation, demandes en attente.
asyncio.run(main(…))loom est asynchrone : asyncio.run lance la fonction main. sys.argv contient les deux arguments donnés au script.

Ce qu'il faut comprendre

  • Le run n'existe nulle part ailleurs que dans son journal : pas de mémoire cachée dans un process. L'état affiché est calculé à partir des événements.
  • Chaque étape est écrite au journal avant que la suivante ne commence. Si le process s'arrête brutalement, on ne perd que l'étape en cours ; tout ce qui précède est sur le disque.
  • C'est ce qui permet la pause de l'exercice 8.1, la reprise de l'exercice suivant, et le rejeu du module 13.

Gardez ce run en pause : il ne servira plus, mais il montre qu'une demande peut rester ouverte jusqu'à son échéance sans rien coûter.

8.5 Survivre à un plantage

H3D11

Pourquoi

Le serveur peut s'arrêter n'importe quand : une coupure, une mise à jour, une erreur. Le pire moment, c'est pendant l'envoi de l'e-mail. Au redémarrage, faut-il le renvoyer ? S'il était parti, Mme Martin le recevrait deux fois ; s'il n'était pas parti, elle ne le recevrait jamais.

Exécution : un plantage pendant l'envoi

On lance une relance dans la session plantage, puis on l'accorde en tâche de fond (&) et on tue la commande au bout de trois secondes et demie, pendant que l'outil attend ses deux secondes. kill -9 arrête un process sans lui laisser le temps de rien ranger, comme une coupure de courant :

$ loom run assistant "Relance Mme Martin pour le devis D-2026-042, sur un ton cordial." --session plantage
(le run se met en pause)
$ loom approve <run> --call fake_2_0 --session plantage --by jean &
$ sleep 3.5; kill -9 $!

($! désigne la dernière commande lancée en tâche de fond.) Où en est le run ?

$ jq -r .type data/default/plantage.jsonl | tail -4

run.transitioned
step.started

Le journal s'arrête sur tool.called : l'outil a commencé, et rien ne dit s'il a fini. Le run attend le résultat de ses outils (awaiting_tools).

On reprend le run :

$ loom resume 01a16e40-aadf-759a-b5ee-5616c4a04192 --session plantage

Refusé, et c'est une protection. Un run en cours est tenu par le process qui le mène, grâce à une concession qu'il renouvelle tant qu'il tourne. Tant qu'elle court, loom suppose que ce process est vivant et ne laisse personne d'autre reprendre le run : sinon, deux process pourraient mener le même run en même temps. Ici, le process est mort, mais loom ne peut pas le savoir avant l'échéance : une minute par défaut. Attendez-la, puis :

Aucun nouvel e-mail dans la boîte : celui-ci n'est jamais parti.

Mise en place : rendre l'outil idempotent

Pour que loom puisse relancer l'envoi sans risque, l'outil doit promettre qu'un même appel ne produit son effet qu'une fois. C'est le rôle du décorateur @idempotent :

lignes modifiées

@idempotentPlacé au-dessus de @tool. loom mémorise le résultat de chaque appel sous une clé ; un appel rejoué rend le résultat mémorisé au lieu de refaire l'effet. Sans précision, la clé est celle de l'appel : le même appel, dans le même run.

Exécution : le même plantage

Ce qu'il faut comprendre

  • Cette fois, loom a relancé l'envoi lui-même (resumed: true sur le second tool.called), et l'e-mail est parti : un troisième message dans la boîte, un seul pour ce run.
  • L'étape 7 reste marquée « ouvert » : c'est l'appel interrompu, dont on n'a jamais eu le résultat. L'étape 8 est l'appel relancé.
  • idempotency.recorded : le résultat est mémorisé. Si le process plantait de nouveau après l'envoi, la reprise rendrait ce résultat au lieu de renvoyer l'e-mail.

Piège : la fenêtre résiduelle

Le résultat est mémorisé juste après l'effet. Un plantage pile entre les deux (e-mail parti, résultat pas encore noté) laisse un doute. Avec la clé de cet exercice, gardée dans le journal du run, ce doute ne laisse aucune trace et la reprise renvoie l'e-mail. Avec un magasin partagé (exercice suivant), loom voit la réservation restée sans résultat et répond « état inconnu » au lieu de renvoyer. C'est une fenêtre de quelques millisecondes, mais elle existe : un vrai service d'e-mail qui accepte lui-même une clé d'idempotence la referme complètement.

8.6 N'envoyer qu'une fois, même si on redemande

D11

Pourquoi

La clé de l'exercice précédent protège un appel contre sa propre reprise. Elle ne protège pas contre une demande répétée : si Jean redemande « Relance Mme Martin… » une heure plus tard, c'est un nouveau run, un nouvel appel, une nouvelle clé, et l'e-mail repart. Il faut une clé tirée du contenu de l'appel : une clé métier.

Mise en place

La clé métier est calculée à partir des arguments de l'appel. Ici : le même destinataire et le même objet désignent le même e-mail.

lignes ajoutées ou modifiées

key=lambda a: …Une petite fonction qui reçoit les arguments de l'appel (a, un dictionnaire) et rend la clé, ici email:martin@example.fr:Votre devis D-2026-042. loom la préfixe du client et du nom de l'outil.

Une clé métier doit être retrouvée d'un run à l'autre : le journal d'un run ne suffit plus. loom le vérifie :

$ loom validate
…
Configuration : Agent 'assistant' : outil(s) 'envoyer_email' à clé métier — il leur faut un magasin d'idempotence partagé et durable (sqlite ou postgres ou redis), pas 'journal' (#49)

On lui donne donc un magasin d'idempotence partagé, ici une petite base SQLite dans le dossier data/ (l'extra sqlite est installé depuis le module 4) :

ligne ajoutée

idempotency:Où loom range les clés et les résultats mémorisés. journal (le défaut) : dans le journal de chaque run, clés d'appel seulement. sqlite, postgres ou redis : un magasin partagé par tous les runs, et par plusieurs process.
path: data/idempotence.dbLe fichier de la base SQLite.

8.7 Le délai global du run

A6

Pourquoi

Quand l'agent sera appelé par une application (module 10), l'utilisateur n'attendra pas indéfiniment. On borne la durée totale d'un run, quelles que soient les étapes en cours.

Mise en place

Un délai d'une seconde, exagérément court pour voir ce qui se passe :

ligne ajoutée

timeout: 1Durée maximale du run, en secondes, en temps de travail cumulé : le temps passé en pause à attendre une approbation ne compte pas. Par défaut, pas de limite.

Exécution

La relance de M. Bernard se met en pause (la pause ne compte pas dans le délai), puis on l'accorde : l'envoi prend deux secondes, le délai tombe.

$ loom run assistant "Relance M. Bernard pour le devis D-2026-050." --session delai
$ loom approve <run> --call fake_2_0 --session delai --by jean
Accordé : fake_2_0
—

Statut     : failed · itérations : 3 · tokens : 7471/484 · coût : 0.0000 $
Run        : 01a16e43-5119-7700-8e08-ae171b3c0105
Juge       : rediger_relance (rôle rediger_relance, appel 1), tentative 1 — acceptée : fidele 1,00, ton 0,90
Erreur     : délai maximal de 1.0 s dépassé : l'étape 7 a été interrompue en cours (0.0 s d'étapes déjà terminées) (timeout)
$ loom resume 01a16e43-5119-7700-8e08-ae171b3c0105 --session delai
Rien à reprendre : le run 01a16e43-5119-7700-8e08-ae171b3c0105 est déjà terminé (failed). Pour le relire : loom inspect 01a16e43-5119-7700-8e08-ae171b3c0105 --session delai

Ce qu'il faut comprendre

  • Le run a échoué (failed, code 1) avec une erreur claire : l'étape 7 a été interrompue en cours.
  • Un échec par délai est une clôture : loom resume n'a rien à reprendre, même si l'on relève le délai ensuite.

Piège : un délai rend la main, il n'annule pas ce qui est en cours

$ grep -h '"a"' boite-envoi/*.json
  "a": "martin@example.fr",
  "a": "c.martin@example.fr",
  "a": "martin@example.fr",
  "a": "martin@example.fr",
  "a": "bernard@example.fr",

Le run a échoué… et pourtant l'e-mail de M. Bernard est parti. envoyer_email est une fonction Python synchrone : loom l'exécute dans un fil d'exécution à part (un thread), qu'il ne peut pas interrompre. Le délai rend la main au moteur, qui clôt le run, pendant que la fonction termine son travail. Un délai protège l'utilisateur de l'attente, pas le client d'un envoi : pour un outil irréversible, comptez sur l'approbation et l'idempotence, pas sur le délai.

Retirez la ligne timeout avant la suite.

8.8 Annuler un run

A5

Pourquoi

Jean a lancé une relance de M. Bernard, puis se ravise avant même de la trancher : il veut l'abandonner purement et simplement, demande d'approbation comprise.

Mise en place

La commande loom n'a pas de sous-commande pour annuler : l'annulation passe par la librairie Python, par l'API REST ou par le serveur MCP (module 10). Voici le script Python, sur le modèle de etat.py :

await loom.cancel(run_id, session_id=…, by="jean")Arrête le run et écrit run.cancelled au journal, avec le nom de qui annule. Rend True si le run a été annulé, False s'il était déjà fini.

Ce qu'il faut comprendre

  • Le run passe à cancelled. Une seconde annulation rend False : il n'y a plus rien à annuler.
  • La demande d'approbation est close avec lui : withdrawn nomme l'appel retiré, et plus rien n'attend de décision.
  • Comme un échec par délai, une annulation est définitive : le run ne se reprend pas.
  • On peut aussi annuler un run qui tourne : loom l'interrompt, puis écrit la clôture. Ce qui était fini reste compté (tokens, coût).
