Module 14 : Qualité : évals et non-régression

À chaque retouche du prompt ou de la configuration, Jean se pose les mêmes questions : l'agent cherche-t-il toujours le devis avant d'écrire ? L'e-mail part-il au bon client ? Rien d'autre n'a-t-il bougé ? Ce module écrit ces questions une fois pour toutes, sous trois formes : une suite d'évaluations, des tests pytest et des journaux de référence. Toutes trois tournent en quelques secondes, sans clé, sans réseau et sans envoyer un seul e-mail.

Agent
assistant, dans le dossier plomberie-dupont/
Départ
la fin du module 13 : l'agent est observé, ses runs se rejouent, deux orchestrateurs d'essai et une doublure d'envoi sont prêts
Arrivée
l'agent a une suite d'évaluations, des tests pytest et des journaux de référence ; toute modification visible est détectée
Fonctions
O1O2O3
Point de départ : les fichiers au début du module

Le dossier contient aussi les deux journaux exportés au module 13 (trace-martin.jsonl, variante-bref.jsonl).

Trois outils, trois questions. Une évaluation (14.1 à 14.3) dit si l'agent fait ce qu'on attend de lui, éventuellement en comparant plusieurs configurations. Un test pytest (14.4) garde la même discipline dans le code du projet, avec des réponses de modèle imposées. Un journal de référence (14.3 et 14.5) dit si quoi que ce soit a changé par rapport à un run que vous avez validé.

14.1 Une première suite d'évaluations

O1

Pourquoi

Après chaque modification, Jean relance l'agent à la main et relit. C'est long, et il oublie toujours de vérifier quelque chose. Il veut écrire ses attentes une fois, et les faire vérifier par une commande.

Mise en place

Une suite d'évaluations est un fichier YAML qui liste des cas : une demande, et ce qu'on attend du run qu'elle lance. Créez un dossier evals/ et la première suite :

$ mkdir evals
version: 1, nameLa version du format et le nom de la suite, affiché dans le rapport.
agent: assistantL'agent évalué. La configuration est celle de loom.yaml (une suite peut en désigner une autre avec config:).
doubles:Les doublures des outils à effets de bord, en module:fonction. Un outil à effets de bord n'est jamais exécuté pendant une évaluation : sa doublure répond à sa place, et sans doublure le modèle reçoit une erreur. Les autres outils (chercher_devis) s'exécutent normalement.
cases:Les cas, chacun avec un name, une demande (input) et des attendus (expect).
contains: […]Des textes qui doivent figurer dans la réponse finale (not_contains : qui ne doivent pas y figurer).
called: […]Des outils qui doivent avoir été appelés. Un nom seul suffit ; avec arguments, l'appel doit avoir reçu au moins ces arguments.
not_called: […]Des outils qui ne doivent jamais être appelés : une question de montant ne doit pas envoyer d'e-mail.
state: {…}Les clés du state de la session après le run (module 4) : ici, le devis courant doit être D-2026-042.

Autres attendus possibles : status (par défaut, le run doit finir completed), matches (des expressions régulières), fields (des champs d'une sortie structurée, module 7, par chemin pointé : objet, lignes.0.total).

Exécution

$ loom eval evals/relance.yaml
Suite      : relance — agent assistant, 2 cas, 1 variante(s), 1 répétition(s) par cas

Variante base (config de base) — 2/2 cas réussi(s), 0.050551 $ de runs, 0.000000 $ de juge
  ok       relance-martin (1/1)
  ok       montant (1/1)

Bilan      : 2/2 run(s) réussi(s), 0.050551 $ dépensé(s)
Verdict    : tout passe

Les deux cas passent. Le code de sortie est 0. Rien n'a été écrit dans data/, et la boîte d'envoi n'a pas bougé : une évaluation monte l'agent à part : son journal vit dans un dossier temporaire effacé à la fin, les quotas et plafonds de période des clients ne la voient pas, et la doublure a répondu à la place de l'envoi.

Pour voir un échec, faites une copie cassée de la suite : un autre destinataire attendu et un autre montant.

$ sed -e 's/destinataire: martin@example.fr/destinataire: bernard@example.fr/' -e 's/"1 840 €"/"2 100 €"/' evals/relance.yaml > evals/relance-casse.yaml
$ loom eval evals/relance-casse.yaml

        ✗ appelle envoyer_email avec {"destinataire": "bernard@example.fr"} — arguments reçus : {"destinataire": "martin@example.fr", "objet": "Votre devis D-20…
  ÉCHEC    montant (0/1)

(La ligne des arguments reçus est coupée ici, au « … ».) Chaque contrôle qui tombe est nommé, avec ce qui a été observé à la place : les arguments réellement reçus par l'outil, le texte de la réponse. Le code de sortie est 1.

Pour ne jouer qu'un cas, --case (répétable) :

$ loom eval evals/relance.yaml --case montant
Suite      : relance — agent assistant, 1 cas, 1 variante(s), 1 répétition(s) par cas

Variante base (config de base) — 1/1 cas réussi(s), 0.013512 $ de runs, 0.000000 $ de juge
  ok       montant (1/1)

Bilan      : 1/1 run(s) réussi(s), 0.013512 $ dépensé(s)
Verdict    : tout passe

À retenir

  • Un cas sans attendu est refusé : il ne prouverait rien. Un cas peut aussi fixer son client (tenant) et poser un state d'ouverture (state), comme --state au module 4.
  • --json donne le rapport complet pour un programme.

Piège : un texte exact

contains cherche le texte tel quel. Un vrai modèle écrit parfois « 1 840 € » avec une espace insécable, que "1 840 €" ne reconnaît pas. Pour tolérer les deux : matches: ["1.840"].

14.2 Comparer des variantes, avec un juge

O1

Pourquoi

Au module 13, le rejeu en variante a montré ce que feraient SIMULE_BREF et SIMULE_OUBLIEUR, mais il sortait en code 0 même quand l'e-mail ne partait pas. Jean veut un verdict : quelle configuration peut remplacer l'actuelle sans dégrader la relance ?

Mise en place

Certaines qualités ne se vérifient pas par un contrôle de texte : « la réponse dit-elle clairement à l'artisan que la relance est partie ? ». C'est le travail d'un juge d'évaluation, un modèle qui note la réponse finale de chaque run selon des critères écrits. Il ressemble au juge du module 7, mais il juge après le run, sans le modifier. On lui donne un modèle simulé, inséré avant VISION dans la liste models :

lignes ajoutées

Comme les autres modèles simulés, ce juge ne comprend rien : il répond selon le texte qu'il lit (with_text). Il rend l'exemple reproductible ; avec un vrai juge, c'est la règle écrite qui ferait le travail.

La suite de comparaison :

repeat: 2Chaque cas est joué deux fois par variante, et ne réussit que si toutes les répétitions passent. Avec un vrai modèle, qui ne répond pas deux fois pareil, c'est ce qui distingue un succès de hasard d'un comportement fiable.
max_cost_usd: 1.00Le plafond de dépense de la suite. Une fois atteint, les runs suivants ne partent pas, et le rapport le dit.
judge:Le juge d'évaluation : son modèle et ses critères (name, rule, et min_score, 0,8 par défaut). Avec tool_results: [chercher_devis], il lirait aussi les résultats de cet outil. Un cas peut ajouter ses propres criteria.
variants:Les façons de jouer chaque cas. actuel ne change rien ; bref et oublieur remplacent le modèle de l'étape main. Une variante peut aussi changer le modèle d'un rôle (models: {rediger_relance: …}) ou d'un juge (judge:<nom>), ou désigner un autre fichier de configuration (config:).

  • bref est écartée par un contrôle déterministe : elle envoie l'e-mail sans le faire rédiger par rediger_relance, donc sans son contrat ni son juge (module 7). Le juge d'évaluation, lui, l'aurait laissée passer (note 0,9).
  • oublieur est écartée deux fois : l'e-mail n'est jamais envoyé, et le juge note 0,1 une réponse qui ne parle d'aucun envoi. C'est exactement ce que le rejeu en variante du module 13 laissait passer.

Le même verdict en Python, par exemple pour bloquer un déploiement :

loom.evaluate(suite)Joue la suite et rend le rapport.
rapport.summary(nom)Le bilan d'une variante : cas réussis, coût.
rapport.passedVrai si tout passe.
 
$ python evaluer.py evals/comparaison.yaml
actuel     1/1 cas, 0.0741 $
bref       0/1 cas, 0.0369 $
oublieur   0/1 cas, 0.0218 $
tout passe : False

À retenir

  • Mettez d'abord les contrôles déterministes (called, contains…) : ils sont gratuits et sûrs. Le juge sert pour ce qu'ils ne savent pas dire, au prix d'un appel de modèle par run, compté à part (« de juge »).
  • Le code de sortie de loom eval est 1 dès qu'un attendu tombe : branchez-le tel quel sur votre intégration continue.

Variante vrai modèle

Une évaluation sur modèles simulés vérifie votre configuration, vos outils et vos attendus, pas la qualité d'un vrai modèle. Avant de conclure sur un changement de modèle, rejouez la suite avec de vrais modèles (une variante models: {main: HAIKU}, rappel), un juge réel, et repeat à 3 ou plus. Surveillez « $ dépensé(s) » et gardez max_cost_usd.

14.3 Garder des runs de référence et les rejouer

O3

Pourquoi

Les cas précédents font tourner l'agent à chaque fois. Or Jean a aussi des runs dont il est content, comme la relance de Mme Martin. Il voudrait les garder tels quels, et être prévenu dès qu'une modification ne les reproduit plus, sans payer un seul appel de modèle.

Mise en place

--export DOSSIER écrit le journal de chaque run d'une évaluation, un fichier par variante, cas et répétition (<variante>--<cas>--<n>.jsonl). Gardez la variante qui vous convient :

$ loom eval evals/comparaison.yaml --variant actuel --export evals/journaux && ls evals/journaux
Suite      : comparaison — agent assistant, 1 cas, 1 variante(s), 2 répétition(s) par cas
Juge       : JUGE_EVAL
Plafond    : 1.0000 $

Variante actuel (config de base) — 1/1 cas réussi(s), 0.074078 $ de runs, 0.001740 $ de juge
  ok       relance-martin (2/2)

Bilan      : 2/2 run(s) réussi(s), 0.075818 $ dépensé(s)
Verdict    : tout passe
actuel--relance-martin--1.jsonl
actuel--relance-martin--2.jsonl

Une suite de non-régression rejoue ces journaux. Un cas de type replay n'a ni demande, ni attendus, ni juge : il passe si chaque run de chaque journal se rejoue à l'identique (module 13).

replay: journaux/*.jsonlLe motif des journaux à rejouer, relatif au fichier de la suite. Un motif qui ne trouve aucun fichier fait tomber le cas : un dossier vidé par erreur ne passe pas pour un succès.

Exécution

$ loom eval evals/non-regression.yaml
Suite      : non-regression — agent assistant, 1 cas, 1 variante(s), 1 répétition(s) par cas

Variante base (config de base) — 1/1 cas réussi(s), 0.000000 $ de runs, 0.000000 $ de juge
  ok       journaux-de-reference (2/2 run(s) rejoué(s) à l'identique)

Bilan      : 2/2 run(s) réussi(s), 0.000000 $ dépensé(s)
Verdict    : tout passe

Les deux runs se rejouent à l'identique, sans appeler personne : 0 $. Ajoutez maintenant la consigne du module 13 au prompt, et relancez :

$ printf "Signe toujours tes réponses « L'assistant de {{ entreprise }} ».\n" >> prompts/system.md

À retenir

  • C'est le filet de sécurité le moins cher : aucun modèle, aucun outil, aucune dépense. Il voit tout changement de prompt, d'outils proposés, de modèle ou de réglages.
  • Il ne dit pas qu'un changement est mauvais, seulement qu'il est visible. Quand le changement est voulu, régénérez les journaux (loom eval … --export), après avoir vérifié le comportement par une évaluation à variantes.
  • Un cas replay peut cohabiter avec des cas ordinaires dans la même suite.

14.4 Tester l'agent avec pytest et le banc

O2

Pourquoi

Une évaluation joue le scénario du modèle simulé de loom.yaml. Jean veut aussi tester des comportements que ce scénario ne contient pas, par exemple un orchestrateur qui oublie l'envoi, et les faire tourner avec le reste de ses tests Python, à chaque modification du code.

Mise en place

pytest est l'outil de test le plus répandu en Python, et pytest-asyncio lui permet d'exécuter des tests async. On les ajoute comme dépendances de développement (--dev) : elles servent à tester le projet, pas à le faire tourner.

$ uv add --dev pytest pytest-asyncio
 + pytest==9.1.1
 + pytest-asyncio==1.4.0

Ajoutez la configuration de pytest à la fin de pyproject.toml :

lignes ajoutées (le groupe dev est écrit par uv add --dev)

asyncio_mode = "auto"Exécuter les tests async def sans décorer chacun.
testpaths = ["tests"]Chercher les tests dans le dossier tests/.
pythonpath = ["."]Permettre aux tests d'importer outils.py, à la racine du projet.

Le module loom_ia.testing fournit un banc (Bench) : il monte l'agent de la configuration, à part du journal, avec des modèles et des outils remplacés. Créez tests/test_relance.py :

$ mkdir tests
Bench("loom.yaml", …)Le banc, sur la configuration du projet (ou un objet LoomConfig construit en Python, module 10).
tools={"envoyer_email": faux_envoi}Remplace un outil par sa doublure. Avec une doublure, l'approbation est accordée d'office, puisque rien ne part.
models={"SIMULE": …}Remplace le modèle déclaré sous cet identifiant.
ScriptedModel(…)Un faux modèle écrit en Python, qui rend ses réponses dans l'ordre : tool_call_message((id, outil, arguments)) pour demander un outil, Message.assistant(texte) pour répondre.
banc.run(agent, demande)Joue le run.
banc.expect(resultat, …)Les mêmes contrôles qu'une évaluation (status, contains, called, not_called…). Lève une AssertionError qui dit ce qui est tombé.
banc.calls("outil")Les appels d'un outil : arguments, sort, résultat.

À retenir

  • Un ScriptedModel, comme sdk: fake, ne lit pas le prompt : les tests vérifient vos outils, vos politiques et votre configuration, pas la qualité du prompt.
  • Bench(…, real_models=True) appelle les vrais modèles : réservez-le à un test d'intégration lancé à la main, avec la clé. register={…} rend référençable un objet que la configuration ne trouverait pas dans ses imports.

Piège : sans asyncio_mode = "auto"

Sans ce réglage (ou un décorateur @pytest.mark.asyncio sur chaque test), pytest ne sait pas exécuter les tests async def, et la suite ne teste rien de ce que vous croyez.

14.5 Les journaux de référence dans pytest

O3

Pourquoi

Jean veut que pytest fasse tout en une commande : les tests du banc et le rejeu des runs de référence. Un seul feu, vert ou rouge, à chaque modification.

Mise en place

assert_replays(config, *journaux)Rejoue chaque run fini de chaque journal, et lève une AssertionError au premier écart, avec le journal, le run et la partie de la requête qui a changé.
banc.export(resultat, chemin)Écrit le journal d'un run du banc dans un fichier : une deuxième façon de fabriquer une référence.

À retenir

  • Trois sources de journaux de référence : loom eval … --export (runs d'une évaluation), banc.export() (runs d'un test), loom sessions export (runs réels, module 13).
  • Pour l'intégration continue : uv run pytest et uv run loom eval evals/relance.yaml sortent en code non nul au premier écart.

Piège : des données personnelles dans le dépôt

Un journal de référence contient tout le run : la demande, l'e-mail, le nom et l'adresse de la cliente. Il est destiné à être versionné avec le code. N'y gardez que des cas fictifs, ou exportés d'un environnement de test, jamais les données d'un vrai client.

Bilan du module

Toute modification visible du prompt, des outils, des modèles ou des réglages est maintenant détectée en quelques secondes, et une comparaison de configurations donne un verdict.

Le fichier loom.yaml est celui de l'exercice 14.2. Au dernier module, l'agent reçoit des outils venus d'un paquet, puis apprend à fabriquer les siens, dans une machine virtuelle isolée.
