Un fournisseur de modèles peut tomber en panne, saturer, ou refuser une clé. Et chaque appel se paie. Dans ce module, l'agent apprend à réessayer, à basculer sur un modèle de secours, et à tenir un budget ; Jean, lui, apprend à lire ce que lui coûte son assistant.

Un vrai fournisseur ne tombe pas en panne sur commande. Pour voir ce que fait loom quand un modèle échoue, on fabrique un modèle simulé qui échoue à tous les coups : PANNE. La clé error de son script (présentée au module 1) lève, à la place d'une réponse, une erreur du type choisi.

9.1 Réessayer après une panne passagère

B3

Pourquoi

Une API surchargée répond « réessayez plus tard ». Le plus souvent, un nouvel essai quelques secondes après passe. En revanche, une clé refusée le restera : réessayer ne servirait qu'à perdre du temps.

Mise en place

Pour ce module, le script de SIMULE gagne une question simple (le montant d'un devis) et une réponse forcée sur l'envoi de l'e-mail, qui servira à l'exercice 9.7. On ajoute le modèle PANNE, toujours surchargé :

lignes ajoutées

- error: overloadedLa réponse du modèle simulé est une erreur « fournisseur surchargé », à chaque tentative.
retry:Les nouvelles tentatives sur une erreur passagère, propres à ce modèle.
max_attempts: 3Trois tentatives au total, la première comprise. Défaut : 3.
initial_delay: 0.5L'attente avant la deuxième tentative, en secondes. Défaut : 1.
multiplier: 2L'attente est multipliée par 2 à chaque tentative (c'est le backoff). Défaut : 2. Une autre clé, max_delay (défaut 30 s), plafonne l'attente.

L'orchestrateur utilise PANNE le temps de l'exercice :

ligne modifiée

Exécution

time, placé devant une commande, affiche sa durée à la fin :

Maintenant, une erreur définitive : la clé d'API refusée. Dans le script de PANNE, remplacez overloaded par auth :

$ time loom run assistant "Quel est le montant du devis D-2026-042 ?" --session panne-auth

Statut     : failed · itérations : 0 · tokens : 0/0 · coût : 0.0000 $

$ jq -r .type data/default/panne-auth.jsonl | tr '\n' ' '
run.started message.user run.claimed step.started step.completed run.transitioned run.failed

Ce qu'il faut comprendre

  • Sur la surcharge, loom a réessayé deux fois, avec une attente qui grandit (environ 0,5 puis 1 s, un peu au hasard pour que des clients nombreux ne réessaient pas tous à la même seconde), puis il a abandonné : failed, code 1. Chaque nouvel essai est écrit au journal (model.retried).
  • Sur la clé refusée, aucun nouvel essai : l'échec est immédiat, et le journal ne contient aucun model.retried.
  • loom classe les erreurs des fournisseurs. Passagères, donc réessayées : transient (réseau, erreur 5xx), overloaded (surcharge, 429). Définitives : auth (clé), invalid_request (requête refusée), content_filtered. À part : quota_exhausted (quota du compte épuisé) et context_overflow (fenêtre dépassée, module 3).

Les délais d'un appel se règlent aussi par modèle, dans un bloc timeouts :

timeouts.first_tokenAttente maximale avant le premier morceau de la réponse, en secondes. Défaut : 60.
timeouts.idleSilence maximal entre deux morceaux. Défaut : 60.
timeouts.totalDurée maximale d'un appel complet. Défaut : 300.

Un délai dépassé compte comme une erreur passagère : il est réessayé.

Variante vrai modèle

Le modèle simulé échoue à chaque tentative. Avec un vrai fournisseur (rappel), une surcharge est souvent passagère : le deuxième essai réussit, et le run continue comme si de rien n'était, avec un model.retried au journal. Les délais timeouts ne s'observent qu'avec un vrai fournisseur, qui envoie sa réponse morceau par morceau. Enfin, une tentative coupée en plein envoi est facturée par le fournisseur : loom la compte dans le coût du run.

9.2 Un modèle de secours

B4

Pourquoi

Quand le modèle principal est en panne pour de bon, mieux vaut une réponse d'un autre modèle que pas de réponse du tout.

Mise en place

Remettez overloaded dans le script de PANNE (le loom.yaml de l'exercice 9.1), puis donnez un secours à l'orchestrateur :

lignes modifiées

fallbacks: [SIMULE]Les modèles de secours, dans l'ordre. Se déclare sur main, sur un rôle ou sur un juge.

Ce qu'il faut comprendre

  • loom a d'abord épuisé les tentatives de PANNE, puis a basculé sur SIMULE : model.fell_back au journal, « secours : PANNE → SIMULE » dans l'arbre.
  • À l'étape 3, l'orchestrateur appelle directement SIMULE, sans réessayer PANNE : un run qui a basculé garde son secours jusqu'à la fin.
  • La bascule dépend de l'erreur : après les tentatives pour une erreur passagère, tout de suite pour un quota épuisé, vers un modèle à plus grande fenêtre pour un contexte trop long. Jamais pour une erreur définitive (auth, invalid_request) : un secours n'y changerait rien.

Piège : un secours doit pouvoir démarrer

Un secours sur un vrai modèle (fallbacks: [HAIKU]) exige sa clé dès le chargement : sans ANTHROPIC_API_KEY, loom validate refuse la configuration, même si le secours ne servira peut-être jamais. Et un secours chez le même fournisseur que le modèle principal tombe souvent en même temps que lui : choisissez-le chez un autre fournisseur quand c'est possible.

9.3 Le disjoncteur

B4

Pourquoi

Avec le seul secours, chaque nouveau run perd du temps à réessayer un modèle qu'on sait en panne. Un disjoncteur l'écarte pour un moment, comme celui d'un tableau électrique coupe un circuit défaillant.

Mise en place

ligne ajoutée

failures: 2Après 2 appels ratés de suite (un appel est raté quand toutes ses tentatives ont échoué), le modèle est écarté pour toute l'instance. Défaut : 5.
cooldown: 60Il reste écarté 60 secondes, puis loom le réessaie. Défaut : 60.

Le disjoncteur vit dans la mémoire du process : chaque commande loom run repart d'un disjoncteur fermé. Pour le voir à l'œuvre, il faut plusieurs runs dans le même process, ce qui est le cas d'un serveur (module 10). On le simule avec un script Python, sur le modèle de etat.py, qui lance trois runs de suite :

await loom.run("assistant", "…", session_id=…)Lance un run et attend sa fin, comme loom run. Le résultat donne le statut (status) et la réponse (text).

Exécution

$ python disjoncteur.py
Run 1 : completed — Le devis D-2026-042 s'élève à 1 840 € TTC (1 533,33 € HT).
Run 2 : completed — Le devis D-2026-042 s'élève à 1 840 € TTC (1 533,33 € HT).
Run 3 : completed — Le devis D-2026-042 s'élève à 1 840 € TTC (1 533,33 € HT).
$ jq -c '…' data/default/disjoncteur-1.jsonl
{"type":"model.retried","model":"PANNE","attempt":1,"error_kind":"overloaded","delay_s":0.44567030501070964}
{"type":"model.retried","model":"PANNE","attempt":2,"error_kind":"overloaded","delay_s":0.9741522472125123}
{"type":"model.fell_back","from_model":"PANNE","to_model":"SIMULE","reason":"overloaded"}
$ jq -c '…' data/default/disjoncteur-2.jsonl
{"type":"model.retried","model":"PANNE","attempt":1,"error_kind":"overloaded","delay_s":0.29415194500099284}
{"type":"model.retried","model":"PANNE","attempt":2,"error_kind":"overloaded","delay_s":0.5584874184158293}
{"type":"circuit.opened","target":"PANNE","failures":2,"cooldown_s":60.0}
{"type":"model.fell_back","from_model":"PANNE","to_model":"SIMULE","reason":"overloaded"}
$ jq -c '…' data/default/disjoncteur-3.jsonl
{"type":"model.fell_back","from_model":"PANNE","to_model":"SIMULE","reason":"circuit_open"}

(… : le même filtre jq qu'à l'exercice 9.2, avec en plus circuit.opened.)

Ce qu'il faut comprendre

  • Run 1 : PANNE échoue (un échec), bascule sur SIMULE.
  • Run 2 : PANNE échoue encore (deux échecs de suite) : le disjoncteur s'ouvre (circuit.opened), puis bascule.
  • Run 3 : PANNE n'est même pas appelé. La bascule est immédiate, motif circuit_open : pas une seconde perdue.

Avant la suite : retirez le modèle PANNE de loom.yaml, remettez model: SIMULE sans fallbacks dans l'agent, et supprimez disjoncteur.py.

9.4 Compter les tokens

J1

Pourquoi

Un fournisseur facture au token : un morceau de texte d'environ quatre caractères en français. Avant de parler d'euros, il faut savoir ce qui se compte.

Exécution

$ loom run assistant "Quel est le montant du devis D-2026-042 ?" --session jetons --json | jq '{iterations, usage, cost_usd}'
{
  "iterations": 2,
  "usage": {
    "input_tokens": 3986,
    "output_tokens": 106,
    "cache_read_tokens": 0,
    "cache_write_tokens": 0,
    "reasoning_tokens": 0
  },
  "cost_usd": 0.0
}
$ jq -c 'select(.type=="model.responded") | .payload | {model, usage}' data/default/jetons.jsonl
{"model":"SIMULE","usage":{"input_tokens":1859,"output_tokens":67,"cache_read_tokens":0,"cache_write_tokens":0,"reasoning_tokens":0}}
{"model":"SIMULE","usage":{"input_tokens":2127,"output_tokens":39,"cache_read_tokens":0,"cache_write_tokens":0,"reasoning_tokens":0}}
input_tokensCe que le modèle a lu : prompt système, définitions des outils, conversation, résultats d'outils. C'est souvent le gros de la facture, car tout est relu à chaque appel.
output_tokensCe que le modèle a écrit : texte et appels d'outils.
cache_read_tokens / cache_write_tokensLes tokens relus depuis le cache de prompt, ou écrits dans le cache (module 3). Moins chers à relire, un peu plus chers à écrire.
reasoning_tokensLes tokens de raisonnement d'un modèle qui « réfléchit » avant de répondre (thinking).

Ce qu'il faut comprendre

  • Chaque réponse du modèle (model.responded) porte son usage ; celui du run est la somme. Le second appel lit plus (2 127 tokens contre 1 859) : il relit le premier échange et le résultat de l'outil.
  • Le coût est nul : aucun modèle n'a encore de tarif.
  • Le modèle simulé estime ses tokens (caractères divisés par 4) et n'a ni cache ni raisonnement : ces compteurs restent à 0.

9.5 Mettre un prix sur les tokens

J2

Pourquoi

Pour savoir ce que coûte une relance, et pour pouvoir la plafonner, loom doit connaître le tarif de chaque modèle.

Mise en place

On donne un tarif à chaque modèle. Pour les modèles simulés, c'est un jeu d'essai : des chiffres inventés, de l'ordre de grandeur d'un vrai modèle, pour voir des coûts non nuls. Pour HAIKU, ce sont les valeurs des exemples du dépôt : vérifiez la grille en vigueur sur la page des tarifs d'Anthropic.

lignes ajoutées

pricing:Le tarif du modèle, en dollars par million de tokens.
input / outputPrix d'un million de tokens lus / écrits.
cache_read / cache_writePrix d'un million de tokens relus depuis le cache / écrits dans le cache.

Ce qu'il faut comprendre

Le premier appel coûte 1 859 × 3 / 1 000 000 + 67 × 15 / 1 000 000 = 0,005577 + 0,001005 = 0,006582 $, exactement ce qu'affiche l'arbre. Le coût de chaque appel est calculé au moment où il a lieu, puis écrit au journal : changer un tarif plus tard ne réécrit pas les coûts passés.

Piège : un modèle sans tarif compte 0 $

Sans pricing, les appels d'un modèle comptent pour rien, et un budget en dollars ne les voit pas. loom le signale dès qu'un agent a un tel budget (exercice 9.7) ; voici ce qu'il disait avant l'ajout des tarifs :

$ loom validate 2>&1 | grep -i tarif
(heure) WARNING  loom_ia.runtime.wiring — Agent 'assistant' : budget en dollars, mais sans tarif pour SIMULE, REDACTEUR, VISION, JUGE : leurs appels comptent 0 $

En profil prod (module 3), cet avertissement devient une erreur.

Ce qu'il faut comprendre

9.7 Plafonner la dépense

J4

Pourquoi

Un agent qui boucle, un prompt mal écrit, et la facture s'envole. Jean veut une limite par run, et une par jour pour toute l'entreprise.

Mise en place : un plafond par run

Un plafond très bas, pour le voir tomber pendant une relance (qui coûte environ 0,037 $) :

lignes ajoutées

budget:Les plafonds de cet agent.
run: {max_cost: 0.015}Coût maximal d'un run, en dollars. Les autres plafonds d'un run : max_tokens (utile sans tarif) et max_calls (nombre d'appels de modèle : orchestrateur, rôles et juges).

Ce qu'il faut comprendre

  • Le plafond est vérifié avant chaque appel de l'orchestrateur. Après la rédaction (rédacteur et juge compris), le run avait dépensé 0,01859 $ : plus que le plafond. loom écrit budget.exceeded, passe en finalizing et demande une dernière réponse sans outils : la réponse forcée du module 2. L'e-mail est rédigé, mais pas envoyé.
  • Le coût final (0,0268 $) dépasse le plafond : la dernière étape avant le contrôle et la réponse forcée sont comptées. Un plafond arrête le run au plus tôt, il ne garantit pas le centime près.

Avertir au lieu d'arrêter. Avec on_exceed: warn, le dépassement est seulement signalé :

ligne ajoutée

on_exceed: warnstop (le défaut) arrête le run par une réponse forcée ; warn écrit seulement budget.exceeded, et le run continue.

Mise en place : un plafond par jour

Un plafond quotidien vaut pour tous les runs du client, tous agents confondus. Il se déclare à la racine de loom.yaml, dans un bloc budgets, qui donne aussi les plafonds par défaut de tous les agents. Retirez le bloc budget de l'agent, et ajoutez :

lignes ajoutées

budgets:Les plafonds par défaut, valables pour tous les agents. Un agent peut les surcharger clé par clé dans son budget.
tenant: {max_cost_per_day: 0.05}Dépense maximale du client sur la journée (UTC) : au-delà, tout nouveau run est refusé. Existe aussi par mois (max_cost_per_month) et en tokens (max_tokens_per_day, max_tokens_per_month).
session: {max_cost: …}(non utilisé ici) Plafond d'une session entière : runs précédents et run en cours.
 
$ loom report --period day
Client     : default
Période    : journée en cours, depuis 2026-10-24 00:00 UTC
Runs       : 9
Dépense    : 0.105843 $, 51909 tokens
  plafond max_cost : 0,05000 $ — reste 0,00000 $
Remise à 0 : 2026-10-25 00:00 UTC
$ loom run assistant "Quel est le montant du devis D-2026-042 ?" --session quota
Client 'default' : budget du client atteint pour la journée : 0,10584 $ (plafond 0,05000 $) — réessayer dans 9 h 40 min
$ echo $?
2

Ce qu'il faut comprendre

  • Le plafond quotidien est lu à l'ouverture du run : la dépense du jour dépasse 0,05 $, donc le run est refusé avant même de commencer (code 2), et rien n'est écrit au journal. Le message dit quand réessayer : à minuit UTC.
  • La dépense est relue dans le journal à chaque lancement, runs des autres process compris. Des runs lancés au même instant passent tous avant d'avoir consommé : c'est un garde-fou, pas un compteur au centime.

Retirez le bloc budgets de loom.yaml avant la suite.

Bilan du module

On garde les tarifs (jeu d'essai pour les modèles simulés) et un plafond raisonnable de 0,10 $ par run, qui laisse passer une relance (environ 0,037 $) mais arrêterait un agent qui s'emballe. On retire le modèle PANNE, le secours, disjoncteur.py et le plafond quotidien.
