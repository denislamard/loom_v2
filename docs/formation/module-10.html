Module 10 : Ouvrir l'agent : Python, REST, MCP

Jusqu'ici, Jean parlait à son assistant depuis un terminal. Mais il veut l'utiliser depuis son téléphone, et le brancher sur Claude. Dans ce module, l'agent sort du terminal : un script Python le pilote, une API web le sert à une application, un serveur MCP en fait un outil pour Claude.

assistant, dans le dossier plomberie-dupont/
Départ
la fin du module 9 : l'agent relance après accord, tient malgré les pannes, sous budget
Arrivée
l'agent est appelé par un script, par une application (API REST protégée par une clé) ou par Claude (serveur MCP)

Et pyproject.toml, écrit par uv, qui dit quels extras de loom-ia sont installés (pour repartir de ce point : uv sync) :

Ce module a trois parties. D'abord la librairie Python (exercices 10.1 à 10.5) : la commande loom que vous utilisez depuis le module 1 n'est qu'une façade, et tout ce qu'elle fait, un script Python peut le faire. 10.1 Un premier script Python

N1

Pourquoi

L'application de Jean est écrite en Python. Plutôt que de lancer la commande loom et de lire sa sortie, elle veut appeler l'agent directement et recevoir un résultat qu'elle peut manipuler : le statut, le texte, le coût.

Mise en place

Créez question.py à la racine du projet :

La librairie de loom est asynchrone : ses fonctions s'écrivent avec async def et s'appellent avec await. Cela permet à un même programme de mener plusieurs runs ou requêtes à la fois. Il suffit de retenir la forme : tout le travail se fait dans une fonction async def main(), que la dernière ligne lance.

from loom_ia.access import LoomLa classe qui représente une instance de loom : la même que celle qui tourne derrière la commande loom. Le paquet s'installe sous le nom loom-ia mais s'importe sous le nom loom_ia.
load_env_file("loom.yaml")Lit le fichier .env voisin de loom.yaml, avec les mêmes règles que la commande (module 3). La librairie ne le fait pas d'elle-même : sans cette ligne, un modèle réel ne trouverait pas sa clé.
async with Loom.from_config("loom.yaml") as loom:Charge la configuration et ouvre l'instance. À la sortie du bloc, loom s'arrête proprement : il attend les tâches en cours et ferme les serveurs MCP qu'il a lancés (c'est loom.aclose(), appelée pour vous).
await loom.run("assistant", "…", session_id=…)Lance un run et attend sa fin, comme loom run. Mêmes paramètres que les options de la commande : session_id, run_id, state, judges, tenant, pièces jointes…
resultat.status, .text, .cost_usd, .run_idLe résultat du run (un RunResult) : statut, texte de la réponse, coût, identifiant. Il porte aussi usage, data (sortie structurée, module 7), pending_approvals (module 8), report (module 9)…

Exécution

$ python question.py
Statut  : completed
Réponse : Le devis D-2026-042 s'élève à 1 840 € TTC (1 533,33 € HT).
Coût    : 0.0135 $
Run     : 01a16e62-f59b-73d8-bbcb-896a76ed4c26

La commande python est celle de l'environnement du projet, puisqu'il est activé : c'est là que loom-ia est installé.

À retenir

Chaque commande de la CLI a son équivalent dans la librairie. Les principales :

Méthode de LoomCe qu'elle faitCommande
run(agent, message)Lance un run et attend sa fin.loom run
stream(agent, message)Lance un run et donne son déroulé au fil de l'eau (10.2).loom run --stream
submit(agent, message)Lance un run en arrière-plan et rend tout de suite son identifiant (10.3).—
follow(run_id), result(run_id)Suit les événements d'un run, lit son résultat.loom inspect
approve(run_id), reject(run_id)Tranche une approbation (module 8).loom approve, loom reject
resume(run_id), cancel(run_id)Reprend un run interrompu, annule un run (module 8).loom resume, —

Les scripts etat.py et annuler.py du module 8 utilisaient déjà cette librairie, avec state et cancel.

10.2 Voir la réponse arriver : streaming et événements

B8I1

Pourquoi

Sur un téléphone, attendre en silence la fin d'un run paraît long. Mieux vaut afficher la réponse au fur et à mesure qu'elle s'écrit, et montrer ce que fait l'agent (« je retrouve le devis… »).

Exécution

En ligne de commande, l'option --stream de loom run affiche le texte au fil de l'eau, avec chaque appel d'outil :

$ loom run assistant "Quel est le montant du devis D-2026-042 ?" --session flux-cli --stream
Je retrouve le devis.
· chercher_devis(numero='D-2026-042')
· chercher_devis : fait
Le devis D-2026-042 s'élève à 1 840 € TTC (1 533,33 € HT).

Statut     : completed · itérations : 2 · tokens : 3986/106 · coût : 0.0135 $
Run        : 01a16e62-ff3d-7140-b05f-933903b15718

Dans un script, c'est loom.stream(). Créez flux.py :

async for element in loom.stream(…)Lance le run et donne, l'un après l'autre, des éléments de deux sortes, jusqu'à la fin du run.
TextDeltaUn morceau du texte que le modèle est en train d'écrire (element.text).
EventUn événement du journal, au moment où il est écrit : element.seq (son numéro dans la session), element.type, element.category, et son contenu dans element.payload.

Ce qu'il faut comprendre

  • Les morceaux de texte arrivent avant l'événement model.responded, qui clôt la réponse du modèle : c'est tout l'intérêt du streaming. Le modèle simulé découpe son texte en morceaux de 8 caractères ; un vrai modèle les envoie au rythme où il les écrit.
  • Les événements sont typés : chacun a un type (run.started, tool.called…), une catégorie (run, message, model, tool, et aussi guard, policy, approval…), un statut et un contenu dont la forme dépend du type. Ce sont exactement les lignes du journal data/default/flux-python.jsonl.
  • Une interface choisit ce qu'elle montre : le texte, un indicateur « appel d'outil en cours » sur tool.called, un bouton sur approval.requested.

10.3 Un run en arrière-plan, suivi puis approuvé

H5N1

Pourquoi

Une relance s'arrête sur l'approbation de l'envoi, et peut attendre des heures que Jean la valide. L'application ne peut pas rester bloquée sur run() pendant ce temps : elle lance le run en arrière-plan, suit son déroulé, et propose l'approbation quand le run s'arrête.

Mise en place

await loom.submit(…)Met le run en file et rend tout de suite son identifiant. Le run tourne en tâche de fond, dans ce même process.
loom.follow(run_id, session_id=…)Donne les événements déjà écrits du run, puis les suivants à mesure qu'ils arrivent. L'itération s'arrête d'elle-même à la clôture du run (terminé, échoué, annulé), pas à une pause.
subruns=FalseSans les événements des sous-runs (le sous-agent traduire, module 6).
evenement.payload.to_state == "paused"Le contenu de l'événement run.transitioned : l'état dans lequel le run vient de passer. paused : il attend une décision.
breakOn sort de la boucle : le run est en pause, il n'écrira rien de plus tant que personne n'a tranché.
after_seq=dernierLe second follow ne redonne que les événements écrits après le numéro dernier.
await loom.result(…)Le résultat d'un run, relu dans le journal.

Exécution

$ python arriere_plan.py
Run lancé : 01a16e63-1743-7366-a6ac-077d44f5f774
  9 tool.called
 18 tool.called
 33 approval.requested
 35 en pause
    accordé : ('fake_2_0',)
 37 approval.granted
 41 tool.called
 42 tool.completed
 49 run.completed
Statut  : completed
Réponse : L'e-mail de relance est parti chez Mme Martin.
$ ls boite-envoi
20261024-164912-976920.json

Les deux premiers tool.called sont chercher_devis et le rôle rediger_relance ; le troisième, après l'accord, est l'envoi.

Piège : approuver trop tôt

Pourquoi attendre la transition vers paused au lieu d'approuver dès l'événement approval.requested ? Parce qu'à ce moment-là, le run n'a pas fini de se mettre en pause : la tâche qui le mène écrit encore deux événements. Une approbation donnée dans cet intervalle, depuis le même process, est bien écrite au journal, mais la reprise du run n'est pas relancée : le run reste arrêté juste après l'accord. Attendez paused, ou relancez le run avec loom resume s'il est resté bloqué. Depuis une autre application (l'API REST de l'exercice 10.7, un humain qui clique), le délai est toujours suffisant.

À retenir

Pour décider dans le code sans passer par la pause, il existe aussi l'approbateur en ligne : une fonction que loom appelle au moment de la demande. C'est l'exercice suivant.

10.4 Qui demande ? Le contexte de l'appelant

A8

Pourquoi

Quand l'application lance une relance, elle sait qui est connecté (Jean, ou sa secrétaire) et d'où vient la demande (le téléphone, le site). Cette information doit suivre le run : dans le journal, pour l'audit, et jusqu'à l'outil d'envoi, qui doit noter qui a demandé l'e-mail.

Mise en place

Un outil Python reçoit le contexte de l'appel s'il déclare un paramètre annoté ToolContext. Ce paramètre n'apparaît pas dans le schéma vu par le modèle : c'est loom qui le remplit. Dans outils.py, envoyer_email note l'appelant dans le message envoyé :

lignes ajoutées ou modifiées

ctx: ToolContextLe contexte de l'appel : ctx.tenant_id (le client), ctx.session_id, ctx.run_id, ctx.agent, ctx.state (le state de session) et ctx.caller, l'appelant.
ctx.caller.user_idL'identifiant de l'utilisateur, donné par l'application à l'ouverture du run. None s'il n'a pas été donné.
ctx.caller.metadataUn dictionnaire libre, donné lui aussi par l'application : ici le canal.

Pour ce module, le script de SIMULE change sur un point : la relance de M. Bernard sera accordée cette fois, et sa dernière réponse le dit. Seul ce bloc du script change ; le reste de loom.yaml est celui du point de départ :

lignes modifiées

Le script appelant.py donne le contexte au run et décide lui-même de l'approbation :

CallerContext(user_id=…, metadata=…)Le contexte de l'appelant. Il a aussi un champ tenant_id (le client, module 12), default par défaut.
context=appelantDonne ce contexte au run. Il est écrit dans l'événement run.started et transmis à chaque outil.
approver=accorderL'approbateur en ligne : une fonction async appelée à chaque demande d'approbation. Elle reçoit la demande (PendingApproval : outil, arguments, motif) et rend une décision : Approved(by, reason), éventuellement avec d'autres arguments, ou Rejected(reason, by). Le run ne passe pas par l'état paused.

Exécution

$ python appelant.py

Statut  : completed

À retenir

  • Le contexte de l'appelant se donne par la librairie (context=) ou par l'API REST (champs user_id et metadata, exercice 10.6). La CLI ne le propose pas.
  • Il va au journal et aux outils, pas au modèle : pour qu'un rôle le voie, il faut le déclarer dans son context (caller_context, module 6).
  • L'approbation reste écrite au journal comme une décision ordinaire, avec son auteur et son motif : un approbateur en ligne n'échappe pas à l'audit.

10.5 Construire l'agent sans fichier

M2

Pourquoi

Parfois, aucun fichier YAML n'est souhaitable : un test qui monte un agent jetable, une application qui compose ses agents d'après ses propres réglages. Les fichiers YAML ne sont qu'une façon d'écrire des objets Python : on peut les construire directement.

Mise en place

Le script sans_fichier.py construit une configuration complète, avec un petit agent calcul qui se sert de l'outil prix_ttc :

LoomConfigCe que décrit loom.yaml : mêmes champs, mêmes noms (version, models, storage…). Le champ agents permet d'y mettre les agents directement.
ModelSpecUn modèle de la liste models.
StorageConfig, EventsStorageLe bloc storage et son journal. Sans lui, le journal serait en mémoire et disparaîtrait avec le process.
AgentSpec, MainRole, PythonToolCe que décrit un fichier d'agent : l'agent, son orchestrateur main, un outil - python: ….
Loom(config)Ouvre une instance à partir de cet objet, au lieu de Loom.from_config(chemin).
loom.register("prix_ttc", prix_ttc)Sans fichier, pas de imports: : on enregistre l'outil sous son nom, avant le premier run.

Exécution

$ python sans_fichier.py
completed : 1 250 € HT avec une TVA à 10 % font 1 375 € TTC.

Sans la ligne loom.register(…), l'agent ne peut pas être monté. Le message, en dernière ligne d'une longue trace Python, est celui d'un imports oublié (module 2) :

loom_ia.config.errors.ConfigError: Agent 'calcul', outil 'prix_ttc' : Référence 'prix_ttc' introuvable : aucun objet de ce nom (enregistrés : aucun). Utiliser 'imports' ou un chemin 'module:attr'

À retenir

  • YAML et Python sont deux écritures de la même configuration, validée de la même façon.
  • Le YAML vaut mieux dès qu'une autre personne que le développeur touche à l'agent (un prompt, un modèle) : il se relit et se valide à part (loom validate). Le code convient aux tests et aux agents composés à la volée.

10.6 Ouvrir l'API REST

N2

Pourquoi

L'application mobile de Jean n'est pas écrite en Python : elle parle HTTP. loom serve publie les agents sous forme d'une API REST : des adresses web (des routes) auxquelles on envoie des requêtes, et qui répondent en JSON.

Mise en place

Le serveur web demande l'extra http. Comme au module 3, redonnez la liste complète des extras :

$ uv add "loom-ia[anthropic,http,mcp,openai,postgres,sqlite]"
Installed 3 packages in 7ms
 + annotated-doc==0.0.5
 + fastapi==0.162.0
 + watchfiles==1.3.0

Exécution

Le serveur occupe le terminal tant qu'il tourne. Lancez-le dans un premier terminal :

$ loom serve
Profil     : aucun (ni --profile, ni LOOM_PROFILE, ni 'profile:') ; surcharges : aucune
Env        : aucun (/home/jean/plomberie-dupont/.env)
API REST   : http://127.0.0.1:8000/v1
Docs       : http://127.0.0.1:8000/docs (sans clé)
Agents     : assistant, traducteur
(heure) WARNING  loom_ia.runtime.wiring — API REST sans clé déclarée alors que la config nomme des clients (default) : tout passera par 'default', puisque c'est la clé qui dit au nom de qui elle agit

Il écoute sur http://127.0.0.1:8000, c'est-à-dire sur votre machine seulement. L'avertissement rappelle que l'API est ouverte à qui la contacte : l'exercice 10.8 y met des clés. Dans un second terminal (environnement activé, dans le dossier du projet), interrogez-la avec curl, l'outil en ligne de commande qui envoie des requêtes HTTP, et jq pour mettre le JSON en forme :

$ curl -s http://127.0.0.1:8000/v1/agents | jq .
[
  {
    "name": "assistant",
    "description": ""
  },
  {
    "name": "traducteur",
    "description": "Traduit un texte en anglais, fidèlement, sans rien ajouter."
  }
]

Deux défauts sautent aux yeux. L'assistant n'a pas de description : une application (ou Claude, à l'exercice 10.9) ne saurait pas à quoi il sert. Et le traducteur est publié, alors que c'est un sous-agent qui ne doit servir qu'à l'assistant. On corrige les deux fichiers d'agent :

lignes ajoutées

lignes ajoutées

description: >-La description de l'agent, que l'API et le serveur MCP publient. >- permet d'écrire un long texte sur plusieurs lignes, qui seront réunies en une seule.
expose: {rest: false, mcp: false}Où l'agent est publié : dans l'API REST, dans le serveur MCP. Les deux valent true par défaut. Un agent non publié reste utilisable comme sous-agent.

Arrêtez le serveur (Ctrl+C dans son terminal), relancez loom serve, puis :

$ curl -s http://127.0.0.1:8000/v1/agents | jq .
[
  {
    "name": "assistant",
    "description": "Assistant de la Plomberie Dupont : répond aux questions sur les devis et les prix, et relance les clients par e-mail après accord de l'artisan."
  }
]

Lancer un run, c'est envoyer un POST sur la route de l'agent, avec la demande en JSON :

$ curl -s -X POST http://127.0.0.1:8000/v1/agents/assistant/runs \
    -H 'Content-Type: application/json' \
    -d '{"message":"Quel est le montant du devis D-2026-042 ?","session_id":"rest-montant"}' \
    | jq '{run_id, session_id, status, text, iterations, cost_usd}'
{
  "run_id": "01a16e63-8192-7720-9d64-abf9f7f58044",
  "session_id": "rest-montant",
  "status": "completed",
  "text": "Le devis D-2026-042 s'élève à 1 840 € TTC (1 533,33 € HT).",
  "iterations": 2,
  "cost_usd": 0.013512
}
-X POSTLa méthode HTTP : POST pour créer (ici, un run), GET (par défaut) pour lire.
-H 'Content-Type: application/json'Un en-tête : le corps de la requête est du JSON.
-d '{…}'Le corps : message (obligatoire), et au choix session_id, run_id, user_id et metadata (le contexte de l'appelant, 10.4), judges, background (10.7).
\ en fin de ligneLa commande continue à la ligne suivante.

La requête attend la fin du run et rend le même résultat qu'en Python ; jq n'en garde ici que six champs. Le résultat complet a tous ceux-ci :

agent, artifacts, cost_usd, data, error, error_type, fallback, iterations, output, pending_approvals, redacted, report, run_id, session_id, skipped_judges, status, text, unverified, usage, verdicts

Une erreur est un code HTTP ordinaire, avec un message lisible :

$ curl -s -i -X POST http://127.0.0.1:8000/v1/agents/plombier/runs -H 'Content-Type: application/json' -d '{"message":"Bonjour"}'
HTTP/1.1 404 Not Found
{"detail":"Agent 'plombier' inconnu (agents : assistant)"}

(-i affiche aussi la ligne de statut de la réponse ; les en-têtes sont omis ici.)

Ouvrez enfin http://127.0.0.1:8000/docs dans un navigateur : c'est la documentation interactive de l'API, générée par le serveur. Chaque route y est décrite, avec ses paramètres, et un bouton « Try it out » l'essaie. Les principales :

RouteRôle
GET /v1/agentsLes agents publiés
POST /v1/agents/{nom}/runsLancer un run (JSON, ou formulaire multipart pour joindre des images)
GET /v1/runs, GET /v1/runs/{id}Lister les runs, lire le statut et le résultat d'un run
GET /v1/runs/{id}/eventsSuivre les événements d'un run en direct (10.7)
POST /v1/runs/{id}/approve, /reject, /cancelApprouver, refuser, annuler (10.7)
GET /v1/sessions, GET ou DELETE /v1/sessions/{id}Les sessions, la fiche d'une session, son effacement
GET /v1/sessions/{id}/events, /report, /filesLe journal d'une session, sa consommation, ses fichiers
GET /v1/events, GET /v1/traces/{run_id}Recherche dans le journal, trace d'un run (module 13)

Le document brut, au format OpenAPI, est à /openapi.json : un développeur s'en sert pour générer un client dans le langage de l'application (Dart pour une application Flutter, par exemple).

À retenir

  • L'adresse et le port se règlent dans loom.yaml (server: {http: {host: …, port: …}}) ou par les options --host et --port de loom serve. Par défaut : 127.0.0.1 et 8000.
  • Un run lancé par l'API est écrit dans le même journal : loom inspect <run> --session rest-montant le relit.

Une requête HTTP ne peut pas rester ouverte des heures en attendant l'accord de Jean. L'application lance donc la relance en arrière-plan, suit son déroulé, et affiche un bouton « Approuver » quand le run s'arrête.

10.8 Protéger l'API par des clés

N3

Pourquoi

Une API ouverte accepte les requêtes de n'importe qui peut la joindre. Avant de la sortir de sa machine, Jean veut qu'elle exige une clé d'API : une chaîne secrète, que l'application envoie avec chaque requête, et qui dit ce qu'elle a le droit de faire.

Mise en place

loom keys create fabrique une clé. On en crée deux : celle de l'application, qui peut tout faire sauf administrer, et une clé de consultation, qui ne peut que lire :

$ loom keys create app-dupont --scope run --scope read --scope read_content --scope approve
Clé        : lk_l8dMJTafbBDywRn4EdLbhwqRiE_Dar3hGRuW7LgLT-M
Elle n'est affichée qu'ici : la config ne garde que son empreinte.

À ajouter dans la configuration :

security:
  api_keys:
    - id: app-dupont
      hash: sha256:8888b3fe3d3cfd7010fadc382e200a773d04c0f89734634e2ecd9cb63f60a854
      scopes: [run, read, read_content, approve]
$ loom keys create lecture --scope read
Clé        : lk_1bAK2_yEKsywcV4J04x8UnXiwyXbSd7a3TYOHMNqmao
Elle n'est affichée qu'ici : la config ne garde que son empreinte.

À ajouter dans la configuration :

security:
  api_keys:
    - id: lecture
      hash: sha256:5d9bb7982bb15bb097a77dd34c0d141b9af11fee5ec2fb7c8107a774a7a45ab1
      scopes: [read]

La clé (lk_…) n'est affichée qu'une fois : notez-la dans un endroit sûr, hors du dépôt (gestionnaire de mots de passe, configuration de l'application). La configuration n'en garde que l'empreinte (sha256:…), dont on ne peut pas retrouver la clé : un loom.yaml lu par quelqu'un d'autre ne livre aucune clé. Vos clés et vos empreintes seront différentes de celles-ci.

app-dupontLe nom de la clé dans la configuration et dans le journal (c'est lui qui apparaît comme auteur d'une action).
--scopeUne portée, c'est-à-dire un droit. Répétable ; par défaut run et read.
runLancer un run, l'annuler, appeler un webhook.
readLire les agents, les runs, les sessions, les traces, les rapports, mais sans les contenus (textes, arguments), qui sont masqués.
read_contentLire aussi les contenus.
approveApprouver ou refuser.
adminEffacer une session (RGPD).
--agent, --tenant, --expires, --rate-limitLimiter la clé à certains agents, la rattacher à un client (module 12), lui donner une date de fin (2027-01-01 ou 90j), limiter son débit en requêtes par minute (module 12).

On déclare les deux clés à la fin de loom.yaml. Seule la fin du fichier change ; le début est celui de l'exercice 10.4 :

lignes ajoutées

security:Les réglages de sécurité de l'accès.
api_keys:Les clés acceptées : pour chacune, son nom (id), son empreinte (hash) et ses portées (scopes), recopiés de la sortie de loom keys create.

Exécution

$ loom validate | grep -E 'Clés|monté'

2 agent(s) monté(s) sans erreur.

Relancez loom serve dans le premier terminal. Dans le second, gardez les clés dans des variables (en remplaçant par les vôtres) :

Sans clé, l'API refuse tout (code 401) :

La clé se donne dans l'en-tête Authorization: Bearer <clé> (ou X-API-Key: <clé>). La clé de consultation lit, mais ne lance pas de run (code 403) :

"assistant"

    -H "Authorization: Bearer $LECTURE" -H 'Content-Type: application/json' \

La clé de l'application peut lancer le run :

$ curl -s -X POST http://127.0.0.1:8000/v1/agents/assistant/runs \
    -H "Authorization: Bearer $CLE" -H 'Content-Type: application/json' \
    -d '{"message":"Quel est le montant du devis D-2026-042 ?","session_id":"rest-cle"}' | jq -c '{status, text}'

À retenir

  • 401 : pas de clé, ou une clé inconnue. 403 : une clé valide, mais sans la portée demandée.
  • Avec des clés déclarées, l'avertissement « API REST sans clé déclarée » de l'exercice 10.6 disparaît. En profil prod (module 3), une API sans clé est une erreur.
  • La documentation /docs reste lisible sans clé en développement ; le profil prod la ferme.
  • Pour retirer une clé, on retire son bloc de loom.yaml et on relance le serveur.

Pourquoi

10.11 La latence, pour une interface vocale

I3

Pourquoi

Jean envisage un assistant au téléphone : le client parle, la voix est transcrite en texte, l'agent répond, et sa réponse est lue par une voix de synthèse. Au téléphone, un silence de deux secondes paraît une éternité. Ce qui compte n'est pas la durée totale du run, mais le délai avant le premier morceau de texte, que la synthèse vocale peut commencer à lire.

Mise en place

Le script latence.py mesure, pour deux runs de suite dans le même process, le délai avant le premier morceau de texte et la durée totale :

time.perf_counter() est un chronomètre précis de la bibliothèque standard de Python.

Exécution

$ python latence.py
1er run (à froid) : premier texte à 938 ms, run complet en 979 ms
2e run (à chaud)  : premier texte à 21 ms, run complet en 47 ms

Ce qu'il faut comprendre

  • Le premier run paie la mise en route : loom monte l'agent et lance le serveur MCP catalogue. Le second, dans le même process, ne paie que le travail. Un service vocal garde donc un process qui tourne (loom serve, ou une instance Loom ouverte une fois pour toutes), au lieu de lancer une commande par appel.
  • Avec le modèle simulé, le reste ne mesure que loom lui-même : quelques dizaines de millisecondes. Avec un vrai modèle, le délai avant le premier morceau dépend surtout du fournisseur et du modèle : un modèle léger comme Haiku répond plus vite qu'Opus.
  • Les délais du flux se règlent par modèle, avec le bloc timeouts (présenté au module 9) : first_token, l'attente maximale du premier morceau, et idle, l'attente maximale entre deux morceaux (60 secondes chacun par défaut). Pour la voix, on les abaisse, et l'on prévoit un modèle de secours (fallbacks, module 9) : mieux vaut basculer vite que de laisser le client dans le silence.

Variante vrai modèle

Avec model: HAIKU (rappel), latence.py mesure le vrai délai de premier morceau du fournisseur. Si ce délai dépasse first_token, l'appel est interrompu et compté comme une erreur passagère : il est réessayé, puis passé au modèle de secours s'il y en a un (module 9).
