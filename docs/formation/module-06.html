Module 6 : Rôles, sous-agents et vision

Un modèle rédacteur écrit l'e-mail de relance, un modèle capable de voir décrit la photo envoyée par un client, et un second agent, complet, traduit pour les clients anglophones.

6.1 Déléguer la rédaction à un rôle

C1C2

Pourquoi

Jean veut que l'assistant relance Mme Martin. Rédiger un e-mail court à partir d'un devis est une tâche bien délimitée : un modèle léger et peu cher la fait très bien, à condition de recevoir le devis et la demande, et rien d'autre. Le modèle principal, lui, reste libre pour décider quoi faire.

Ce qu'est un rôle

Un rôle est un modèle spécialisé, avec son propre prompt, que l'orchestrateur appelle comme un outil. Il a trois particularités :

  • il peut être servi par un autre modèle que l'orchestrateur, par exemple un modèle moins cher ;
  • il ne reçoit pas toute la conversation, seulement ses arguments et le contexte que vous déclarez : c'est une économie de tokens, et le rôle n'est pas distrait par ce qui ne le concerne pas ;
  • il ne fait qu'un appel de modèle et rend un texte : il n'a ni outils ni boucle.

L'orchestrateur lui-même est un rôle particulier, nommé main (exercice 6.7).

Mise en place

1. Le prompt du rédacteur. Comme le prompt système de l'agent, il va dans le dossier prompts/ :

$ cat > prompts/rediger_relance.md <<'EOF'
Tu rédiges les e-mails de relance de la Plomberie Dupont, pour des devis
restés sans réponse.
Écris un e-mail court et poli : une ligne « Objet : … », puis le message,
signé « Jean Dupont, Plomberie Dupont ».
N'utilise que les informations reçues : n'invente aucun montant, date ou délai.
EOF

2. Le rôle, dans l'agent. Les rôles se déclarent dans une liste roles :

lignes ajoutées

roles:La liste des rôles de l'agent.
name: rediger_relanceLe nom du rôle : c'est le nom de l'outil que voit l'orchestrateur. main est réservé.
description: …Ce que l'orchestrateur lit pour savoir quand appeler ce rôle, comme la docstring d'un outil Python. Obligatoire.
model: REDACTEURLe modèle qui sert le rôle, déclaré dans loom.yaml. Il peut différer de celui de main.
system_file: rediger_relance.mdLe prompt système du rôle, dans prompts/ (ou system: pour un prompt en ligne).
input_schema:Les arguments que l'orchestrateur doit fournir, en JSON Schema (type: object obligatoire). Ici un seul, ton. Des arguments hors schéma sont refusés avant l'appel, comme pour un outil Python (module 2).
context:Ce que le rôle reçoit en plus de ses arguments. user_input : la demande de l'utilisateur, mot pour mot ; {tool_results: [chercher_devis]} : les résultats de cet outil dans le run. D'autres éléments existent : session_state (le state, module 4), {last_turns: N} (les derniers tours de la conversation), caller_context (qui appelle, module 10), attachments (exercice 6.4).
input_template: |-Le message que reçoit le rôle, construit à partir de {{ args.… }} (ses arguments) et de {{ context.… }} (son contexte). Tout élément de context doit y être cité. Sans gabarit, loom écrit les blocs de contexte puis les arguments. |- introduit un texte sur plusieurs lignes, en YAML.

3. Le modèle du rédacteur, et le script. Dans loom.yaml, on déclare un second modèle simulé, REDACTEUR, qui joue l'e-mail. Le script de SIMULE est remplacé, pour ce module, par la scène de relance : retrouver le devis, puis appeler rediger_relance comme n'importe quel outil. On réactive aussi la capture des échanges bruts (vue au module 3), pour voir ce que reçoit le rôle.

lignes ajoutées ou modifiées

text: |- permet d'écrire une réponse sur plusieurs lignes, ici un e-mail entier.

4. Une consigne dans le prompt de l'agent, pour qu'un vrai modèle sache quand déléguer :

Piège : la réponse finale ne contient pas l'e-mail

La réponse du run est « Le projet d'e-mail de relance pour Mme Martin est prêt. », sans l'e-mail. Le rôle a rendu son texte à l'orchestrateur, qui a répondu ce que son script prévoyait. Un vrai modèle recopierait l'e-mail dans sa réponse, en dépensant des tokens de sortie, les plus chers, et en risquant de le modifier. L'exercice 6.3 règle cela.

Variante vrai modèle

Avec un vrai modèle (rappel), donnez à main le modèle OPUS et au rôle le modèle HAIKU : le modèle cher décide, le modèle léger rédige. C'est l'orchestrateur qui choisit d'appeler le rôle et avec quel ton, en lisant sa description.

6.2 Passer un résultat d'outil par référence

C2

Pourquoi

En 6.1, c'est la configuration qui donne le devis au rôle, par context. Parfois, c'est l'orchestrateur qui doit choisir quoi transmettre. S'il recopie un résultat dans les arguments du rôle, il paie des tokens de sortie et peut se tromper en recopiant. Une référence évite la recopie.

Mise en place

Le rôle reçoit maintenant le devis dans un argument devis, de type objet, et n'a plus que la demande en contexte :

lignes modifiées

Dans le script, l'orchestrateur passe {"$ref": "result:1"} au lieu du devis :

lignes modifiées

Exécution

$ loom run assistant "Relance Mme Martin pour le devis D-2026-042, sur un ton cordial." --session relance-ref
Le projet d'e-mail de relance pour Mme Martin est prêt.

Statut     : completed · itérations : 3 · tokens : 4697/299 · coût : 0.0000 $
Run        : 01a16e1d-750a-7735-9fbe-d32f39eae751
$ jq -r 'select(.type=="model.exchanged" and .role=="rediger_relance") | .payload.request_body | fromjson | .messages[0].blocks[0].text' data/default/relance-ref.jsonl
Demande de l'artisan : Relance Mme Martin pour le devis D-2026-042, sur un ton cordial.
Devis : {"numero": "D-2026-042", "client": "Mme Martin", "email": "martin@example.fr", "objet": "Remplacement du chauffe-eau", "montant_ht": 1533.33, "taux_tva": 20, "montant_ttc": 1840.0, "date": "2026-09-03", "statut": "envoyé"}
Ton : cordial

Ce qu'il faut comprendre

  • result:1 désigne le résultat du premier appel d'outil du run, ici chercher_devis. loom remplace la référence par la valeur avant d'appeler le rôle : le devis complet arrive, sans que le modèle l'ait recopié.
  • loom ajoute lui-même au prompt de l'orchestrateur une consigne qui explique les références : un vrai modèle sait s'en servir.
  • Une référence fonctionne pour tout outil, pas seulement pour un rôle.

Piège : une référence transmet un objet, pas un texte

Si le champ devis est déclaré type: string, l'appel du rôle est refusé, et le run continue sans lui. Il faut lire loom inspect --full pour le voir :

    appel rediger_relance — refusé avant exécution
      · résultat  : (erreur) Arguments non conformes au schéma de l'outil :
                    - devis : la référence result:1 (chercher_devis) transmet un objet JSON ; ce champ attend du texte. Une référence passe le résultat tel quel : si le champ attend autre chose, écris la valeur toi-même.
  étape 5

Le champ qui reçoit une référence doit avoir le type du résultat : ici type: object.

Pour la suite, revenez à la version de 6.1 : le contexte tool_results suffit pour un devis.

6.3 Un rôle terminal : sa sortie devient la réponse

C3

Pourquoi

Quand le rôle a rédigé l'e-mail, il n'y a plus rien à décider : sa sortie est la réponse. Inutile de la repasser à l'orchestrateur.

Mise en place

On repart de l'agent de 6.1 et on ajoute une ligne au rôle :

ligne ajoutée

terminal: trueLa sortie du rôle devient la réponse finale du run, telle quelle, sans dernier appel à l'orchestrateur. Par défaut : false.

Remettez aussi le script de 6.1 dans loom.yaml (la scène sans référence). Le fichier est alors identique à celui de 6.1.

Ce qu'il faut comprendre

  • La réponse est l'e-mail du rédacteur, mot pour mot.
  • 2 itérations au lieu de 3 : au retour du rôle, le run passe directement de awaiting_tools à completed. La troisième réplique du script n'est plus jouée.
  • Un rôle terminal est un des cas d'arrêt de la boucle, avec la réponse sans outil et la borne max_iterations (module 2).

6.4 Un rôle vision et les pièces jointes

C4B9G1

Pourquoi

Un client envoie la photo de son chauffe-eau. Il faut un modèle capable de voir une image. Mais seulement quand il y a une image : proposer ce rôle à l'orchestrateur quand rien n'est joint n'aurait pas de sens.

Mise en place

1. Un modèle qui voit. Chaque modèle déclare ses capacités, sous capabilities. loom s'en sert pour décider ce qu'il lui envoie : une image n'est envoyée qu'à un modèle qui a la capacité vision. Dans loom.yaml, on déclare le modèle simulé VISION, et on ajoute au script de SIMULE la scène de la photo :

lignes ajoutées

capabilities: {vision: true}Le modèle sait lire les images. Sans cette capacité, un modèle reçoit une simple mention de l'image.
with_tool: decrire_photoDans un script simulé : cette réponse n'est jouée que si l'outil decrire_photo est proposé au modèle. without_tool fait l'inverse. C'est ainsi qu'on simule un modèle qui n'appelle le rôle que s'il est disponible.

Les autres capacités qu'un modèle peut déclarer : tools (il sait appeler des outils), thinking (il produit un raisonnement), native_json (il accepte un schéma de sortie), forced_tool_choice (vu au module 3 pour Opus), context_window (module 3).

2. Le rôle vision. Un rôle dont le contexte contient attachments reçoit les pièces jointes du run :

lignes ajoutées

context: [attachments]Le rôle reçoit les images jointes à la demande. C'est ce qui en fait un rôle vision : il est masqué quand le run n'a pas de pièce jointe.
system: …Un prompt en ligne, plus court qu'un fichier pour une consigne d'une ligne.

Et une consigne dans le prompt de l'agent :

ligne ajoutée

3. Une photo. Fabriquez une image PNG de 640 × 480 pixels, avec la fonction png_uni écrite au module 2 dans outils.py :

$ python -c "from outils import png_uni; open('chauffe-eau.png', 'wb').write(png_uni(640, 480, (190, 190, 200)))"
$ ls -l chauffe-eau.png | awk '{print $5, $9}'
1948 chauffe-eau.png

Avec un vrai modèle, utilisez plutôt une vraie photo, en JPEG ou PNG.

Les contrôles des pièces jointes

Avant le run, loom vérifie chaque pièce jointe. Il reconnaît le format au contenu du fichier, jamais à son nom : un fichier texte renommé en .png est refusé.

$ echo "Ceci n'est pas une image." > facture.png
$ loom run assistant "Voici une photo de mon chauffe-eau." --attach facture.png --session photo-faux

6.6 Appeler un agent comme un outil : le sous-agent

C5

Pourquoi

Jean ne veut pas changer d'agent pour traduire : il veut demander à l'assistant, qui confiera la traduction au traducteur.

Rôle ou sous-agent ?

Un sous-agent est un agent complet, appelé par l'orchestrateur comme un outil. À la différence d'un rôle, il a sa propre boucle, ses propres outils, et son appel ouvre un run enfant, avec son journal et son coût. Un rôle convient à une tâche d'un seul appel de modèle ; un sous-agent, à une tâche qui demande elle-même des outils ou plusieurs étapes.

description: …La description de l'outil. Par défaut, celle de l'agent.

Un sous-agent prend un seul argument, message : la demande que l'orchestrateur lui transmet. Le script de SIMULE gagne la scène de traduction, et le prompt une consigne :

Ce qu'il faut comprendre

  • Le run enfant a son identifiant et son statut ; il est écrit dans le journal de la même session. Sa consommation remonte au run parent : le total compte les trois appels.
  • L'enfant ne reçoit que le message : ni la conversation du parent, ni ses pièces jointes, ni son state de session.
  • Profondeur. Un sous-agent peut lui-même avoir des sous-agents. La clé max_depth d'un agent (par défaut 1) borne cette imbrication : à 1, un run racine de l'agent appelle ses sous-agents, mais un run de cet agent lancé comme sous-agent ne le peut pas. Cela évite qu'une chaîne d'agents tourne sans fin.
  • Budget. La clé budget_share d'un sous-agent lui accorde une part de ce qui reste au budget du run parent. Elle exige un budget de run, que vous verrez au module 9 ; sans lui, la configuration est refusée :
Configuration : /home/jean/plomberie-dupont/agents/assistant.yaml: Agent 'assistant', sous-agent 'traduire' : budget_share demande un budget du run (max_cost, max_tokens ou max_calls)

6.7 L'orchestrateur est un rôle comme les autres

C6

Pourquoi

main, l'orchestrateur, accepte les mêmes réglages qu'un rôle : son modèle, son prompt, son contexte, mais aussi des réglages d'appel propres et des modèles de secours. Les connaître évite de toucher au modèle lui-même quand on veut changer le comportement d'un seul rôle.

Mise en place

On limite la longueur des réponses de l'orchestrateur, sans changer celle du rédacteur :

ligne ajoutée

llm: {max_tokens: 1024}Réglages d'appel propres à ce rôle. max_tokens remplace celui du modèle ; params se fusionne sur les params du modèle. La même clé existe sur chaque rôle et sur un juge (module 7).

main accepte en tout : model, fallbacks, system ou system_file, llm et context (déjà utilisé au module 4 pour le state). Le contrat de sortie et le juge de la réponse finale, eux, se déclarent au niveau de l'agent, par les clés output et judge (module 7). Pour main, context n'accepte que le state de session : l'orchestrateur reçoit déjà toute la conversation.

Exécution

$ loom run assistant "Relance Mme Martin pour le devis D-2026-042, sur un ton cordial." --session reglages
(l'e-mail de relance, comme en 6.3)
$ jq -c 'select(.type=="model.exchanged") | {role, max_tokens: (.payload.request_body | fromjson | .max_tokens)}' data/default/reglages.jsonl
{"role":"main","max_tokens":1024}
{"role":"main","max_tokens":1024}
{"role":"rediger_relance","max_tokens":null}

Les deux appels de main partent avec max_tokens: 1024 ; l'appel du rôle rediger_relance garde celui de son modèle (aucun pour REDACTEUR).

Les modèles de secours

fallbacks donne, sur main ou sur un rôle, la liste des modèles à essayer si le modèle principal est en panne. Le module 9 les met en œuvre. Retenez dès maintenant qu'un modèle de secours doit être utilisable dès le démarrage : avec fallbacks: [HAIKU] sur main et sans clé Anthropic, la configuration est refusée :

$ loom validate
…
Demande refusée : Modèle 'HAIKU' : la variable d'environnement ANTHROPIC_API_KEY est absente ou vide

Retirez fallbacks et la ligne llm avant de passer au bilan.

Bilan du module

Pour garder un projet lisible, on retire les réglages d'expérience : la capture des échanges bruts et la ligne llm de main. Le rôle rediger_relance reste terminal. Le projet ressemble maintenant à ceci :

agents/traducteur.yaml, prompts/rediger_relance.md, outils.py et serveurs/catalogue.py sont ceux des exercices. La relance finale donne l'e-mail du rédacteur en 2 itérations.

L'e-mail est rédigé, mais rien ne garantit encore qu'il ait la bonne forme, ni qu'il n'invente pas un montant. Au module 7, des contrats et un juge contrôlent la sortie du rédacteur, et des politiques encadrent l'agent.
