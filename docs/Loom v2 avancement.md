- **Relire un run lisiblement** : `loom inspect <run_id>` est prévu en J6 (6.2) ; possibilité d'en faire une version minimale plus tôt (étapes, appels de modèle par rôle, outils avec durée et résultat, sous-runs, fichiers, réponse finale, bilan). Denis : « pas encore ».

## Restes connus

- Deux appels d'outil avec le même `call_id` dans une réponse ne sont pas gérés.
- Cycle de vie d'un run (délai maximal, `run.cancelled`, API `cancel`) : J4.2 (backlog #006).
- Un rôle interrompu après son `model.responded` est rappelé à la reprise (les deux coûts sont comptés).
- Portée MCP `run` : après une reprise, nouvelle connexion ; l'état d'un serveur à état est perdu.
- Rien n'oblige le modèle à répondre à toute la question : un contrat (3.2) contrôle la forme, un juge (3.3) le fond, selon ses critères ; un appel d'outil peut être imposé (`loom.require_tool`, 3.1).
- Réponse finale = dernier message : seul le prompt protège d'une réponse répartie entre plusieurs tours.
- `$ref` dans un argument de type chaîne : la référence est résolue en objet, puis refusée par le schéma de l'outil avec un message qui recopie l'objet (vu avec MiniMax-M3 en 3.3, corrigé par le modèle au tour suivant).
- `Loom.stream()` ne diffuse pas les morceaux du modèle d'un sous-run (ses événements, si) ; les morceaux d'un rôle terminal (#009, 3.2) ne sont pas attribués au rôle (bus `model.delta`, J4).
- Sous-agents : une réponse d'enfant inutilisable (texte parasite) passe pour un succès, sauf si l'agent appelé déclare son propre contrat `output` (3.2 : il s'applique dans le run de l'enfant) ; pas de contrat sur la référence `subagents` ; `max_depth` propre à chaque agent (un sous-agent au `max_depth` élevé peut descendre plus loin que ne le voudrait la racine) ; les fichiers produits par un enfant ne sont pas dans `RunResult.artifacts` de la racine (seulement dans `ToolOutput.artifacts` de l'appel) ; un enfant ne reçoit pas les pièces jointes du parent.
- L'adaptateur `openai` ne renseigne pas `model_id` sur les blocs de raisonnement et ne renvoie pas le raisonnement (backlog #015) : à corriger au plus tard en 3.5.
- Les SDK lisent encore d'autres variables d'environnement (en-têtes `ANTHROPIC_CUSTOM_HEADERS`, `OPENAI_ORG_ID`, `OPENAI_PROJECT_ID`) : non neutralisées.
- `request_hash` des journaux antérieurs à l'ordre des résultats : un run passé dont les résultats sont arrivés dans le désordre ne redonne plus la même empreinte (rejeu, J6).
- Artefacts : fichier orphelin si l'événement n'a pas pu être écrit ; le rôle vision ne voit que les pièces jointes ; un orchestrateur vision renvoie les images à chaque appel ; seuil de déport en caractères.
- `loom validate` monte tous les agents : il échoue si une clé d'API manque.
- Accès 2.5 : les octets d'un fichier du run ne se téléchargent ni par REST ni par MCP (seulement l'URI ; MCP peut la réutiliser en lien) — avec les ressources `loom://` (5.4) ? ; un envoi REST sans `Content-Length` (chunked) n'est borné que fichier par fichier (Starlette l'écrit d'abord sur disque) ; `file_roots` vaut quel que soit le transport MCP ; un outil inconnu (serveur indisponible) n'a pas de `tool.called`, sa ligne de déroulé est seulement « … : fait (erreur) ».
- `api: responses`, secours, disjoncteurs (modèles et MCP), cache : phase 3.5.
- Politiques (3.1) : un `Retry` à `after_tool` sur un outil (pas un rôle) renvoie le résultat en erreur à l'orchestrateur ; en diffusion `live`, la réponse refusée est diffusée avant la réparation (puis `StreamReset`) ; après une reprise, une décision `after_model`/`on_output` non appliquée est réévaluée (son `policy.decided` peut apparaître deux fois)  ; `Pause` refusée jusqu'en J4.3 ; une politique synchrone s'exécute dans la boucle (pas d'entrée-sortie).
- Contrats (3.2) : schéma JSON natif du fournisseur non utilisé (B9, 3.5) ; un rôle interrompu pendant ses réparations est rappelé depuis le début à la reprise (tentatives comptées dans l'appel, pas dans le `RunState`) ; une sortie non terminale gardée `unverified` n'est marquée que dans son `tool.completed` (le run ne l'est pas, l'orchestrateur ne le voit pas) ; en `after_guards`, la réponse finale n'arrive qu'en un bloc, une fois le run clos ; `StreamReset` ne concerne que `on_chunk` (`Loom.stream()`, CLI) : SSE et MCP ne diffusent pas de morceaux ; un contrôle réussi sans remplacement écrit un `guard.checked` mais pas de `policy.decided`. La réponse REST contient `data` et `unverified` (champs de `RunResult`), pas encore le résultat MCP (3.6).
- Juges (3.3) : après une reprise, une décision `on_output` non appliquée est réévaluée et son juge rappelé (coût compté deux fois) ; un rôle interrompu est rappelé avec ses juges ; un verdict invalide est une erreur du juge (il ne répare pas son verdict) ; le tirage vaut pour tout le run (un rôle appelé deux fois est jugé les deux fois ou aucune) ; le juge ne voit pas l'historique de la session (`session_summary`, `last_turns` : J4.1) ; pas de juge sur un outil ni sur la référence d'un sous-agent (seulement celui de l'agent appelé, dans son run) ; un modèle juge avec raisonnement étendu chez Anthropic refuserait probablement le `tool_choice` imposé (à voir avec le raisonnement, 3.5) ; les événements d'un point d'accroche sont horodatés à leur écriture, après toute la chaîne (le `guard.checked` du contrat porte l'heure de fin du juge) ; forçage par REST et MCP, résultat du juge dans la réponse MCP : 3.6 ; erreurs en profil prod : J5.
- Outillage de vérification : depuis le J3, la copie est dans la VM de la session (hors du dossier de Denis), avec son propre environnement uv (`uv sync --all-extras --frozen`, et un second environnement sans extra pour la passe noyau) ; le code vérifié est recopié dans le dossier en fin de phase. Pyright reçoit l'environnement (`uv run --no-sync pyright`).
