## Points à revoir ensemble (demandé par Denis, 19/09)

- **Relire un run lisiblement** : `loom inspect <run_id>` est prévu en J6 (6.2) ; possibilité d'en faire une version minimale plus tôt (étapes, appels de modèle par rôle, outils avec durée et résultat, sous-runs, fichiers, réponse finale, bilan). Denis : « pas encore ».
- **Logs** (#45, §14.4) : en `INFO`, seules les transitions et la vie des connexions MCP sont loguées. Proposition : une ligne INFO par appel de modèle (rôle, modèle, durée, tokens, coût) et par appel d'outil (nom, durée, erreur).

## Restes connus

- Deux appels d'outil avec le même `call_id` dans une réponse ne sont pas gérés.
- Cycle de vie d'un run (délai maximal, `run.cancelled`, API `cancel`) : J4.2 (backlog #006).
- Un rôle interrompu après son `model.responded` est rappelé à la reprise (les deux coûts sont comptés).
- Portée MCP `run` : après une reprise, nouvelle connexion ; l'état d'un serveur à état est perdu.
- Rien n'oblige le modèle à répondre à toute la question (contrats et juge en J3.2 et J3.3) ; un appel d'outil peut être imposé (`loom.require_tool`, 3.1).
- Réponse finale = dernier message : seul le prompt protège d'une réponse répartie entre plusieurs tours.
- `Loom.stream()` ne diffuse pas la sortie d'un rôle terminal (backlog #009), ni les morceaux du modèle d'un sous-run (ses événements, si).
- Sous-agents : une réponse d'enfant inutilisable (texte parasite) passe pour un succès (contrat, J3.2) ; `max_depth` propre à chaque agent (un sous-agent au `max_depth` élevé peut descendre plus loin que ne le voudrait la racine) ; les fichiers produits par un enfant ne sont pas dans `RunResult.artifacts` de la racine (seulement dans `ToolOutput.artifacts` de l'appel) ; un enfant ne reçoit pas les pièces jointes du parent.
- L'adaptateur `openai` ne renseigne pas `model_id` sur les blocs de raisonnement et ne renvoie pas le raisonnement (backlog #015) : à corriger au plus tard en 3.5.
- Les SDK lisent encore d'autres variables d'environnement (en-têtes `ANTHROPIC_CUSTOM_HEADERS`, `OPENAI_ORG_ID`, `OPENAI_PROJECT_ID`) : non neutralisées.
- `request_hash` des journaux antérieurs à l'ordre des résultats : un run passé dont les résultats sont arrivés dans le désordre ne redonne plus la même empreinte (rejeu, J6).
- Artefacts : fichier orphelin si l'événement n'a pas pu être écrit ; le rôle vision ne voit que les pièces jointes ; un orchestrateur vision renvoie les images à chaque appel ; seuil de déport en caractères.
- `loom validate` monte tous les agents : il échoue si une clé d'API manque.
- Accès 2.5 : les octets d'un fichier du run ne se téléchargent ni par REST ni par MCP (seulement l'URI ; MCP peut la réutiliser en lien) — avec les ressources `loom://` (5.4) ? ; un envoi REST sans `Content-Length` (chunked) n'est borné que fichier par fichier (Starlette l'écrit d'abord sur disque) ; `file_roots` vaut quel que soit le transport MCP ; un outil inconnu (serveur indisponible) n'a pas de `tool.called`, sa ligne de déroulé est seulement « … : fait (erreur) ».
- `api: responses`, secours, disjoncteurs (modèles et MCP), cache : phase 3.5.
- Politiques (3.1) : un `Retry` à `after_tool` renvoie le résultat en erreur à l'orchestrateur (la réparation d'un rôle par son modèle arrive en 3.2) ; en diffusion `live`, la réponse refusée est diffusée avant la réparation (`after_guards` en 3.2) ; après une reprise, une décision `after_model`/`on_output` non appliquée est réévaluée (son `policy.decided` peut apparaître deux fois) ; `run.completed` reprend la consommation de l'état avant les décisions (sans effet en 3.1, à revoir avec le coût du juge en 3.3) ; `Pause` refusée jusqu'en J4.3 ; une politique synchrone s'exécute dans la boucle (pas d'entrée-sortie).
- Outillage de vérification : depuis le J3, la copie est dans la VM de la session (hors du dossier de Denis), avec son propre environnement uv (`uv sync --all-extras --frozen`, et un second environnement sans extra pour la passe noyau) ; le code vérifié est recopié dans le dossier en fin de phase. Pyright reçoit l'environnement (`uv run --no-sync pyright`). Sur le dossier de Denis, git seulement avec `--no-optional-locks` : un `git status` y a laissé un `.git/index.lock` impossible à supprimer sans autorisation (supprimé avec son accord le 19/09).
