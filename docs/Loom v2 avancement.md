Il remonte au lot comme un signal (`_Unknown`), solde l'appel sans le conclure, et c'est après le lot que la déclaration de l'outil s'applique — erreur au modèle, ou demande d'approbation, tenue comme les autres ou tranchée par l'approbateur en ligne. **Pas de boucle possible** : la décision déjà tranchée est lue avant tout, et un appel accordé repart avec `replay_unknown`, donc reprend la réservation au lieu de la re-signaler.

- **Phase 5.2b (le serveur MCP en HTTP) : terminée, commitée (`636b26c`).**
  - Décisions d'ouverture (23/09) : le MCP HTTP est **monté dans l'application REST** (un port, une authentification) ; `allowed_hosts` est **dérivé de l'adresse d'écoute**, la config ne servant qu'à l'étendre ; `read_content` vaut aussi en MCP — sinon une clé de supervision contournerait le masquage en passant par là ; et **sans clé déclarée, le MCP HTTP ne monte pas**.
  - **Ce que le transport change tient en une phrase : la clé arrive à chaque requête.** En stdio, rien dans le protocole ne dit au nom de qui on parle, donc un serveur sert un client choisi à son lancement. En HTTP, un **seul serveur sert tous les clients** : `list_tools` ne publie que ce que la clé ouvre, `call_tool` exige `run` pour lancer et `read` pour relire, et `run_status` est masqué sans `read_content`. La limite que 5.1a avait dû poser tombe.
  - **L'authentification a lieu avant le protocole.** Une couche ASGI identifie l'appelant et rend un **401 ordinaire** — avec son `WWW-Authenticate` — si la clé manque, est inconnue ou a expiré ; le LLM du client n'a pas à interpréter un refus d'authentification déguisé en erreur d'outil. L'appelant reconnu est posé dans une variable de contexte que les gestionnaires relisent.
  - Accès : `Caller` sort de `access/http/auth.py` pour `access/caller.py` — les deux accès à clé partagent la même description de l'appelant, et avec elle les mêmes règles ; `create_server(..., callers=…)` rend l'appelant par requête, le stdio gardant son client figé ; `access/mcp_server/http.py` (`McpHttp`) monte le gestionnaire de session du SDK, dont le cycle de vie est accroché à celui de l'application.
  - Config : `server.mcp.http`, `allowed_origins`, `allowed_hosts` — `LATER_MCP_ACCESS` se vide ; contrôle au chargement, `http: true` sans `security.api_keys` est refusé en nommant la clé qui manque.

- **Phase 5.3b (la file et les workers) : prête, runs simulé et réel faits, en attente du commit.**
  - Décisions d'ouverture (24/09) : `loom worker` est **seul** à consommer — une instance ordinaire ne fait plus que publier ; le **délai** est imité par une file d'attente à durée de vie qui retombe dans la file de travail (aucun plugin, et le plugin `delayed_message` n'est de toute façon pas livré avec RabbitMQ) ; **pas de déduplication** côté file, at-least-once assumé ; et le worker prend **une tâche à la fois** (`--jobs N`), acquitte après exécution, et **reprend au démarrage** ce qui traîne.
  - **Publier d'un côté, consommer de l'autre.** `storage.queue: {backend: rabbitmq, url_env: NOM}`. Le piège est qu'une file servie sans worker derrière laisse tout attendre : `loom validate` le dit sous la ligne `File`. Le port gagne `drain()` (une file qui publie n'a rien à attendre) et un raffinement `ServedQueue` (`serve`, `stop`) auquel `loom worker` s'adresse — pas de `getattr` pour savoir si une file se consomme.
  - **Ce qui manquait, et que seul le courtier révèle.** Un worker tué n'acquitte pas : le courtier redélivre **tout de suite**, alors que le bail du mort court encore. Le second pilote se faisait donc refuser par la concession (#27), et le run attendait la prochaine reprise au démarrage. Un travail qui bute sur un bail est maintenant **reposé pour l'après-bail** (délai = ce qui reste du bail, plus une marge, vingt fois au plus). C'est ce qui fait qu'un run passe d'un worker à l'autre sans que personne s'en occupe, et c'est la seule ligne de code que la phase ajoute au moteur.
  - `loom worker [--jobs N]` : reprise au démarrage pour chaque client, puis écoute ; `SIGINT`/`SIGTERM` demandent l'arrêt et la tâche en cours va au bout. `Loom.work()` / `Loom.stop_work()` à la façade, et `Loom.worker_id` exposé — c'est lui qui départage deux pilotes au journal.
  - Ce que le courtier ne sait pas dire, et qui était déjà prévu au port : `state` rend `unknown`, `cancel` rend faux. `submit(key=…)` ne dédoublonne plus — la clé devient l'**identifiant** du travail, et ce qu'elle protégeait l'est ailleurs. Une tâche en échec et un message illisible sont **acquittés** et journalisés : les rejouer sans fin serait pire.
  - Essais : 19 unitaires (config, câblage, message, CLI, refus d'un extra absent) et 8 d'intégration contre un vrai RabbitMQ, dont **le scénario du jalon** — deux `loom worker` en sous-process, l'un tué par `kill -9` en plein appel d'outil, le run mené au bout par l'autre. **Éprouvés par mutation** : sans le report après le bail, l'essai du bail et celui du `kill` tombent tous les deux (et l'exemple rend 1).
  - Exemple : `examples/j5/file_et_worker.py` (`--cas file|reprise|differe`, `--url`, `--reel`). Les trois instances vivent dans le même process, ce qui permet de tout montrer sans écrire un fichier de config quelque part ; le vrai `kill -9` est dans l'essai d'intégration, et l'exemple le dit.
  - **Deux pièges d'installation, mesurés.** `guest` ne se connecte que depuis la machine du courtier, donc un RabbitMQ en docker avec un port publié le refuse : l'aide de l'exemple crée un utilisateur. Et `asyncpg-stubs`, ajouté en 5.3a au groupe `dev`, **tire asyncpg** : la passe « noyau seul » n'éprouvait plus le refus d'un extra absent. Les stubs sont sortis dans un groupe `types` (vérification complète : `uv sync --all-extras --group types`), et deux essais neufs — qui ne tournent **que** sans l'extra — vérifient que le refus nomme l'extra à installer.
  - Docs : fonctions (réalisation 5.3b sous #27), conception (§12.1, §17.6), jalons (`file_et_worker.py` dans les exemples du jalon).
  - Vérifié : ruff, `ruff format --check`, pyright strict, 5 contrats d'import, **1363 essais** avec Postgres et RabbitMQ (1306 + 57 sautés sans eux), passe noyau seul (1054 + 147 sautés), les **28 exemples** de J1 à J5.
  - Run réel (lancé par Denis le 24/09, `file_et_worker.py --reel`, les trois cas) : **5.3b est validée en réel.** Le run soumis est piloté par le worker et jamais par le soumettant ; le run tenu par un mort passe à l'autre worker en 3,7 s, après son bail ; le travail différé arrive à 1,0 s et pas avant.
  - **Le run réel a trouvé une faute d'exemple, pas de code, et c'est le `Controle` qui l'a dite.** Le cas `file` attendait **une** concession et en a vu **neuf**, toutes du même worker : le bail se renouvelle par minuteur, et **chaque renouvellement écrit un `run.claimed` de plus**. En simulé le run est trop court pour renouveler, en réel il dure dix secondes avec le bail de 3 s que l'exemple pose. L'attendu était numérique là où il devait être structurel — la règle adoptée le 23/09 le disait, et je l'avais quand même écrit ainsi. Corrigé : l'exemple replie les renouvellements (`relais`) et vérifie **qui** pilote, pas **combien de fois**. `fonctions.md` (#27) dit maintenant qu'un run qui dure porte autant de concessions que de renouvellements, et que c'est la dernière qui tient.
  - Reste connu (5.3b) : le `consumer_timeout` de RabbitMQ (30 min par défaut) borne la durée d'une tâche — au-delà, le courtier ferme le canal et redélivre, donc un run plus long qu'un timeout non relevé tournerait en rond ; la file d'attente des travaux différés est une file, donc un message à longue échéance retient ceux qui le suivent (les délais de loom sont courts, et l'expiration d'une approbation est de toute façon relue au journal) ; les noms de files sont fixes (`loom.jobs`, `loom.jobs.delayed`), donc deux déploiements sur un même vhost se partagent la même file ; `--jobs N` mène N tâches de front dans un process, ce que les budgets et les quotas n'ont jamais éprouvé ; un travail dont le type n'a pas de traitement dans ce worker est acquitté et perdu (cas d'un worker plus vieux que le producteur).

- **Phase 5.3c (le bus et le SSE entre process) : prête, runs simulé et réel faits, en attente du commit.**
  - Décisions d'ouverture (24/09) : le bus transporte **une nouvelle**, pas les événements, et l'abonné relit ; il se branche comme **une source de plus** au journal notifiant, si bien qu'aucun accès ne change ; un abonné **rattrape par le seq** ce qu'il a manqué ; et la phase prend tout ce que la ligne du jalon annonce, idempotence Redis comprise.
  - **Pourquoi une nouvelle et pas l'événement.** Un `NOTIFY` de Postgres est borné à 8 000 octets, et un événement les dépasse souvent — un bus qui les porterait ne marcherait pas sur Postgres, ou pas toujours, ce qui est pire. Et le contenu ne sortant jamais du journal, la politique de lignes (5.3a) et le masquage (5.2a) gardent la main, puisqu'ils s'appliquent à la lecture.
  - **Ce que le module annonçait depuis 1.6 s'est réalisé sans le toucher.** `NotifyingEventStore` publie après écriture et suit le bus : ce qu'il relit va aux **mêmes abonnés** que ses propres écritures. SSE, `Loom.stream()`, la progression MCP et la CLI n'ont pas changé d'une ligne. Un abonné ne sait pas d'où vient ce qu'il reçoit, et c'est tout l'intérêt.
  - Trois précautions qui tiennent le suivi : une nouvelle porte la **source** (l'identité de l'instance, celle de ses concessions) et personne ne se réécoute ; chacun garde sa **position** par journal, donc une nouvelle perdue est rattrapée à la suivante ; et un process **sans abonné** ne relit rien — il avance sa position, ce qui laisse un `loom serve` au repos ne consommer que de minuscules nouvelles.
  - Un bus en panne **ne fait pas échouer une écriture** : elle a eu lieu, et manquer la nouvelle coûte une notification. `memory` (défaut) ne monte aucun bus : dans un process, il n'y a rien à traverser.
  - Idempotence Redis : `reserve` en un **script Lua** — le même arbitrage par la date que le `ON CONFLICT … WHERE` des magasins SQL. Les appartenances (client, session) sont tenues dans un ensemble à part, sans quoi l'oubli RGPD devrait balayer la base. **Redis oublie tout seul** au bout de la rétention, réservation périmée comprise, là où SQLite et Postgres la gardent : c'est écrit en tête du module.
  - Essais : 20 unitaires (config, câblage, nouvelle, curseurs, bus en panne) sur le **bus en mémoire** — deux journaux notifiants au-dessus d'un seul journal, la forme de deux process sans les process — et 4 d'intégration sur les **deux vrais bus**, dont le SSE. La suite de contrat de l'idempotence tourne en plus sur Redis (21 essais). Le tout **éprouvé par mutation** : bus désactivé, les quatre essais d'intégration tombent en 36 s, et l'exemple refuse de jouer.
  - Exemple : `examples/j5/bus_et_sse.py` (`--cas traverse|sse|cles`, `--bus postgres|redis`, `--reel`). Le cas `sse` ouvre son flux **avant** que le run soit repris ailleurs : tout ce qui arrive ensuite est venu du bus, sans supposition sur qui a été le plus rapide.
  - **Trois pièges trouvés en le branchant.** `NOTIFY` n'accepte pas de paramètre — c'est `pg_notify($1, $2)` qu'il faut, sans quoi la charge utile serait à échapper à la main. Le SDK Redis laisse des `Unknown` dans ses signatures asynchrones : trois règles pyright sont levées pour ses deux modules, en tête de fichier et en le disant. Et surtout : **un bus posé en code n'existe que pour le process qui le pose** — le sous-process de l'exemple charge la config du dépôt, qui ne déclare pas de bus, donc il le pose aussi, à partir de ses arguments. En production c'est le fichier de config qui le dit, et les deux le lisent ; l'exemple l'explique là où il le fait.
  - Docs : fonctions (réalisation 5.3c sous #27, où vit le bus), conception (§9.3, §12.1, §17.6), jalons (contenu de 5.3c, `bus_et_sse.py` dans les exemples).
  - Vérifié : ruff, `ruff format --check`, pyright strict, 5 contrats d'import, **1408 essais** avec les trois services (1326 + 85 sautés sans eux), passe noyau seul (1072 + 176 sautés), les **29 exemples** de J1 à J5.
  - Run réel (lancé par Denis le 24/09, `bus_et_sse.py --reel`, les trois cas) : **5.3c est validée en réel, sans rien à corriger.** Les quatre événements écrits par une instance arrivent à l'autre ; le run laissé en plan est repris par le sous-process et mené au bout, et le flux ouvert **avant** la reprise reçoit **27 événements** dont `run.completed` — autant qu'en simulé, ce qui est le point : le bus ne change rien à ce qui s'écrit, il dit seulement où regarder. Les clés Redis se partagent entre deux magasins et s'effacent avec leur session.
  - Reste connu (5.3c) : un bus ne garde rien, donc une nouvelle publiée avant qu'un abonné soit établi est perdue — elle est rattrapée à la suivante, mais un process qui démarre peut manquer le tout début d'un run déjà en cours ; le suivi ne démarre qu'à l'entrée du contexte (`async with Loom(...)`), donc une instance construite sans lui écrit et lit normalement mais ne voit rien des autres ; les canaux sont fixes (`loom_events`, `loom:events`), donc deux déploiements sur la même base ou le même Redis se partagent les nouvelles — sans effet, chacun relisant son propre journal, mais le trafic est doublé ; le bus Postgres ouvre **deux** connexions de plus par instance (une pour écouter, une pour publier) et ne les met pas en commun avec le pool du journal ; une nouvelle illisible est journalisée et ignorée, sans compteur ; et l'exemple n'imprime pas ce qu'un run réel a coûté, contrairement aux autres du jalon.

La ligne reste dans `jalons.md` avec sa mention, et ne compte plus dans le critère de sortie du jalon.

Un run repris ailleurs (5.3b) n'y retrouverait ni ses pièces jointes ni ses résultats déportés, et **rien ne le disait** : `storage.queue: rabbitmq` avec des artefacts `local` se chargeait sans un mot.

- **Phase 5.4a (les lectures REST) : prête, runs simulé et réel faits, en attente du commit.**
  - Décisions d'ouverture (24/09) : 5.4 en **trois sous-phases** — 5.4a les lectures REST, 5.4b les ressources MCP `loom://runs`, 5.4c les déclencheurs ; `run_summaries` devient une **requête sur le journal** et non une projection ; la planification est confiée à la plateforme, qui appellera le webhook ; le webhook sera protégé par une clé d'API. La ligne 5.4 de `jalons.md` est devenue trois.
  - **La projection `run_summaries` est écartée, et c'est le point de la phase.** `fonctions.md` #32 la décrivait tenue à jour à chaque `run.transitioned`. `Loom.runs()` lit le journal à la place : session par session, de la plus récemment écrite à la plus ancienne, et replie chaque run à la lecture. Trois raisons. Les chiffres sont **exactement** ceux de la fiche d'une session, puisqu'ils sortent du même repli. Il n'y a **rien à reconstruire** — ni après un import, ni après une migration, ni après un `DELETE` RGPD. Et il n'y a **rien à resynchroniser** quand deux process écrivent le même journal : une projection matérialisée aurait ajouté un second état à garder juste, pour une lecture qui n'est pas dans une boucle chaude.
  - **Le prix est dit, pas caché.** Une lecture par journal ouvert. Deux bornes le tiennent — `limit` runs rendus (50 par défaut, 200 au plus), `sessions` journaux ouverts (idem) —, et la page rend ce qu'elle a coûté (`scanned`) et si une borne l'a arrêtée (`truncated`). Un filtre **ne baisse pas** ce prix : il s'applique après le repli, ce que l'exemple montre en comparant les deux `scanned`. C'est là que la projection reviendra si le nombre de sessions par client l'exige ; `truncated` est déjà le crochet qui l'absorbera.
  - **Une liste ne porte aucun contenu** : ni réponse, ni message d'erreur, seulement son **type**. Donc pas de `masked()` à écrire, et une clé de supervision (5.2a) la lit entière. Elle se filtre aussi **honnêtement** pour une clé limitée à certains agents, là où `/sessions` doit refuser : chaque run dit de quel agent il est. Nommer un agent qu'on n'a pas le droit de lire donne 403, pas une page vide — sinon un vide apprendrait que l'agent existe.
  - `GET /events` expose `EventQuery` en paramètres d'URL, `after` compris, et **le client vient de la clé**. Les facettes libres ne sont pas interrogeables par l'URL : les deux que `EventQuery` nomme (`tool_name`, `model_id`) le sont, et inventer une syntaxe de facette dans une chaîne de requête aurait été un choix de langage, pas une réalisation. À rouvrir si un besoin le demande.
  - Document OpenAPI : chaque route porte un résumé et une **famille** (`agents`, `runs`, `sessions`, `journal`), chaque famille est décrite, la version du paquet y est, et les **deux façons de présenter une clé** sont déclarées (`Authorization: Bearer`, `X-API-Key`) — la page de l'API devient utilisable. Les deux schémas ne refusent rien eux-mêmes (`auto_error=False`) : c'est `identify` qui décide, comme avant.
  - Essais : 7 unitaires sur la façade (liste, filtres, bornes, sous-run nommant son délégant, isolation des clients, recherche et pagination), 6 sur les routes (liste, bornes refusées, clé limitée, recherche, isolation, requête invalide), 1 sur le masquage d'une recherche, et **2 sur le document lui-même** — résumé, famille déclarée, schéma d'authentification sur chaque route, critères annoncés par les deux nouvelles routes : une route ajoutée sans résumé fera tomber la suite.
  - Exemple : `examples/j5/lectures_rest.py` (`--cas runs|traces|openapi`, `--reel`), nommé par Denis. Les attendus sont **structurels** : le journal de la config garde ce que les exemples précédents y ont écrit, donc le cas `runs` borne ses recherches par un `since` pris avant de lancer, et le cas `traces` par sa session. Le cas `openapi` vérifie le document plutôt qu'il ne l'imprime.
  - Docs : fonctions (#32 réécrit — la projection devient une requête), conception (§18.1, §18.2 : deux routes, trois paragraphes), jalons (5.4 devient 5.4a–5.4c, `lectures_rest.py` dans les exemples).
  - Vérifié : ruff, `ruff format --check`, pyright strict, 5 contrats d'import, **1428 essais** avec les trois services, passe noyau seul (1082 + 178 sautés), les **30 exemples** de J1 à J5. Éprouvé par mutation : une route sans famille, le client non forcé sur `/events`, la liste non filtrée par agent, `truncated` toujours faux, l'ordre inversé — cinq mutations, cinq suites qui tombent.
  - Run réel (lancé par Denis le 24/09, `lectures_rest.py --reel`, les trois cas) : **5.4a est validée en réel, sans rien à corriger.** Les trois runs de Dupont sont rendus dans l'ordre de leur dernière écriture, et eux seuls ; les cinq filtres rendent exactement les identifiants attendus ; la pagination rend les 30 événements de la session en 8 pages, sans doublon ni trou et dans l'ordre des identifiants ; les deux bornes de date partagent le journal 15/15 ; la recherche masquée rend les mêmes 30 types sans une occurrence du devis (25 côté bureau, 0 côté supervision) ; et la clé de Martin, cherchant la session de Dupont, ne trouve rien.
  - **Ce que le run réel ajoute au simulé : le prix d'une page, mesuré sur un vrai dossier.** Chez Denis, Dupont a **17 journaux** — la page en ouvre donc 17 pour rendre 3 runs, et **ne se dit pas tronquée**, la borne par défaut (50) n'étant pas atteinte. Dans mon clone de vérification, le même client en a 96 et la même page **est** tronquée. Les deux branches de la règle sont donc constatées, chacune sur un dossier réel, et la seconde est bien celle qu'un service verra : **le nombre à surveiller est le nombre de journaux par client, pas le nombre de runs rendus.** Le filtre ne le change pas (17 ouverts avec, 17 sans), ce qui est le fond de l'arbitrage.
  - Sur le journal lui-même : **15 des 30 événements d'un run sont de catégorie `run`** (concession, transitions, étapes) — la moitié d'un journal est la mécanique du run, pas son contenu. C'est ce que `GET /events?category=…` permet d'écarter d'un paramètre, et c'est l'argument le plus simple pour la recherche plutôt que l'export entier.
  - **Réserve honnête : `error_type` n'a jamais porté de valeur dans ce run.** Les quatre runs ont réussi, donc `?status=failed` et `?status=error` rendent 0 — les filtres ne sont éprouvés en réel que du côté vide, et le champ `error_type` d'une liste n'est couvert que par les essais unitaires. Un run échoué en réel le montrerait ; aucun cas de l'exemple n'en fabrique.
  - À noter, déjà consigné en 5.1b et 5.2b et inchangé : l'avertissement « juge corrélé » revient au montage de `relance_reel` pour Martin, dont la correspondance `GLM_FLASH → HAIKU` replie le juge sur le modèle qu'il évalue.
  - Reste connu (5.4a) : une page ouvre un journal par session, donc son coût suit le nombre de sessions du client et non la taille de la page — un client à quelques milliers de sessions demandera la projection écartée ici ; `since` et `until` filtrent **après** le repli, donc ils ne font économiser aucune lecture ; le tri par dernière écriture se fait sur ce que la recherche a déjà trouvé, si bien qu'une borne atteinte peut laisser dehors un run plus récent d'un journal non ouvert (la page le dit par `truncated`, elle ne le corrige pas) ; les facettes libres ne sont pas interrogeables par l'URL ; `GET /events` cherche sur tout le client quand aucune session n'est nommée, sans index autre que celui du magasin ; et une liste rendue à une clé limitée à certains agents est filtrée après coup, donc sa borne `limit` a compté des runs que l'appelant ne verra pas.

- **Phase 5.4b (les ressources MCP et l'arrêt) : prête, runs simulé et réel faits, en attente du commit.**
  - Décisions d'ouverture (24/09) : **index et gabarits** — `resources/list` rend `loom://runs` et `loom://sessions`, `resources/templates/list` les cinq gabarits ; les **octets d'un fichier** deviennent lisibles ; **pas d'abonnement** (`resources/subscribe` reste dehors) ; exemple `ressources_mcp.py`.
  - **Ce que la phase a coûté en code neuf est petit, et c'est le résultat qu'on cherchait.** Les règles de lecture n'ont pas été réécrites une seconde fois : une ressource demande `read`, elle est masquée sans `read_content`, son client vient de la clé, et `loom://sessions` est refusé à une clé limitée à certains agents là où `loom://runs` se filtre honnêtement. Ce sont, mot pour mot, les règles des routes de 5.4a et de 5.2a — un module de lecture les applique, il n'en invente aucune. `loom://runs` **est** la page de `Loom.runs()` : l'exemple le vérifie en comparant la ressource à l'accès Python.
  - **Une session est un paramètre, pas un segment** (`loom://runs/{run_id}{?session_id}`). Trouvé en essayant : un run d'une session nommée ne se retrouve pas par son seul identifiant, et REST avait déjà tranché de la même façon (`GET /v1/runs/{id}?session_id=…`). Les gabarits le disent en RFC 6570.
  - **Les octets d'un fichier se lisent enfin, et sous l'URI que le journal publie.** Le manque venait de 2.5 : un `resource_link` rendu par loom portait une URI `artifact://…` que le client ne pouvait pas lire — un lien mort. `resources/read` accepte donc cette URI telle quelle, et `loom://artifacts/{client}/{session}/{fichier}` en est l'alias déclaré au gabarit. Le client de l'URI est **vérifié** contre celui de la clé, et un fichier d'un autre client est « introuvable », comme un fichier absent.
  - **La borne de lecture est celle des pièces jointes** (`execution.attachments.max_bytes`, 5 Mio par défaut), faute d'une borne de lecture à part. C'est un emprunt assumé : un fichier plus gros est refusé avec un message qui nomme le réglage, plutôt que d'envoyer des mégaoctets en base64 dans le contexte d'un client.
  - **Le vocabulaire a dû sortir du module MCP.** `loom serve` et `loom validate` annoncent les ressources, et la CLI ne peut pas importer le SDK MCP — c'est un extra. Les URI et les gabarits vivent donc dans `access/resources.py`, sans une ligne de MCP, et le lecteur dans `access/mcp_server/resources.py`. Exactement la raison qui avait sorti `Caller` de l'accès REST en 5.2b.
  - **Pas d'abonnement, et le serveur le dit lui-même** : déclarer les ressources suffit à ce que le SDK écrive `subscribe: false` dans les capacités. L'exemple le lit sur la poignée de main plutôt que de le supposer.
  - **`cancel`** complète les outils de contrôle : portée `run` sur l'agent **du run**, lu d'abord pour le connaître ; un run déjà terminé rend `cancelled: false` sans être une erreur ; faute d'un `by`, la clé d'API signe la décision au journal. Il porte le nom que #40 lui donne depuis J1, hors de la famille `run_status`/`run_report` — à renommer d'un mot si tu préfères la paire.
  - Essais : 6 en stdio (les deux index et les cinq gabarits, la page comparée à l'accès Python, un run et sa trace par URI, une ressource inconnue, les octets d'un fichier et son alias, la borne de lecture, le fichier d'un autre client) et 5 en HTTP (le client vient de la clé, `read` exigé et masquage sans `read_content`, la clé limitée qui obtient les runs mais pas les sessions, `cancel` signé par la clé, `loom validate` qui annonce les ressources).
  - Exemple : `examples/j5/ressources_mcp.py` (`--cas index|fichiers|arret`, `--reel`), nommé par Denis, avec un vrai client MCP sur un vrai serveur. L'image du cas `fichiers` est bâtie **en code** (signature PNG et des octets quelconques) : rien n'est écrit sur le disque. L'attendu du cas `arret` est **structurel** — avec de vrais modèles l'arrêt tombe pendant le premier appel, en simulé le run peut finir d'abord ; ce qui ne doit jamais varier, c'est que la réponse de l'outil dise ce que le journal porte. La session MCP est ouverte **avant** le lancement, pour que l'arrêt ne coûte qu'un aller-retour.
  - Docs : fonctions (réalisation et reste connu 5.4b sous #32, N5 passe à trois outils de contrôle, le reste connu de 5.2b corrigé), conception (§18.3 : deux paragraphes, §18.4), jalons (contenu de 5.4b, table d'exécution, `ressources_mcp.py` dans les exemples).
  - Vérifié : ruff, `ruff format --check`, pyright strict, 5 contrats d'import, **1442 essais** avec les trois services, passe noyau seul (1082 + 178 sautés), les **31 exemples** de J1 à J5. Cinq mutations essayées, cinq suites qui tombent — le client d'un fichier non vérifié, la liste des runs non filtrée, une lecture non masquée, le droit sur l'agent d'un run qu'on arrête, l'index non listé.
  - **Deux essais ajoutés parce que la mutation les a réclamés, et c'est le meilleur usage qu'on en ait fait.** (1) « le fichier d'un autre client est introuvable » passait **sans** la vérification du client : il visait un fichier qui n'existait pas, et l'absence donnait le même message que le refus. Il crée maintenant le fichier, chez l'autre client **et** chez soi, et exige les deux réponses. (2) Rien ne tombait quand `cancel` cessait de vérifier le droit sur l'agent du run : un essai le fixe, clé limitée à un autre agent contre clé complète sur le même run.
  - Run réel (lancé par Denis le 24/09, `ressources_mcp.py --reel`, les trois cas) : **5.4b est validée en réel.** Les deux index listés et les cinq gabarits annoncés, `subscribe=False` lu sur la poignée de main ; un run lancé par l'outil et relu par ses ressources — 37 événements d'arbre pour 38 au journal de la session, la page identique à celle de l'accès Python ; la trace masquée rend les mêmes 38 types sans une occurrence du devis (22 côté bureau, 0 côté supervision) ; les octets de la pièce jointe rendus à l'identique sous l'URI du journal **et** sous l'alias ; le fichier de Dupont introuvable pour la clé de Martin ; et l'arrêt d'un run d'arrière-plan **abouti**, journal clos sur `run.cancelled`, signé `dupont`.
  - **Ce que le réel ajoute au simulé : l'arrêt arrive à temps.** En simulé le run finissait parfois avant la requête, et l'attendu structurel s'en accommodait ; avec de vrais modèles l'arrêt tombe pendant le premier appel, et c'est bien `run.cancelled` qui clôt le journal. La prédiction écrite dans l'exemple est donc constatée, et non supposée.
  - **Le run réel a trouvé une faute d'exemple, dans son commentaire et non dans son contrôle.** La ligne de la clé limitée affichait « 10 run(s) (aucun : son agent n'a rien lancé) » — dix runs, et une parenthèse qui dit zéro. Le contrôle, lui, était structurel (« aucun run de l'agent qu'on lance ») et tenait : le journal de la config garde les runs `relance` des exemples précédents, et la clé bridée sur `relance` les voit à bon droit. C'est la **troisième fois** que le même défaut se présente sous une forme nouvelle — attendu numérique en 5.3b, titre qui annonce autre chose que la ligne en 5.2a, et ici une parenthèse qui commente un chiffre qu'elle n'a pas lu. Corrigé : la ligne dit désormais ce que la page porte (« N run(s), agent(s) : … »), calculé sur la réponse.
  - **Réserve honnête :** la borne de lecture d'un fichier (`max_bytes`) n'est éprouvée que par un essai unitaire — aucun cas de l'exemple ne fabrique un fichier assez gros. Et `subscribe: false` est une déclaration statique : le run la lit, il ne prouve pas qu'un abonnement serait refusé, puisqu'il n'y a rien à refuser.

## Restes connus

- **Blocage intermittent d'un pilote du test d'idempotence partagée (CI, 22/09).** Deux fois de suite, puis plus : un des deux sous-process écrit son résultat sur stdout, ne laisse rien sur stderr, et ne rend pas la main — le test expire au bout de 120 s. Le blocage est donc **après le run**, dans `aclose()` ou à la sortie de l'interpréteur. Une fois `atelier-deux`, une fois `atelier-un` : ce n'est pas lié au rôle dans la course. Jamais reproduit en local (une trentaine de tentatives : deux pilotes épinglés sur un cœur, avec et sans couverture dans les sous-process, la commande exacte de la CI `uv run --locked pytest --cov`, `TMPDIR=/tmp`). Cause inconnue — la troisième exécution est passée sans rien changer. Une trace est armée d'avance dans le pilote (`faulthandler.dump_traceback_later`, 60 s, `exit=True`) : la prochaine occurrence videra la pile de tous ses fils dans le message d'échec. Piste non confirmée : le fil de travail d'aiosqlite n'est pas un fil démon, donc un magasin laissé ouvert retiendrait le process à la sortie — essayé, il meurt quand même ici.

- Sessions (4.1a) : le journal est toujours relu en entier à chaque run — le snapshot supprime le rejeu, pas la lecture (backlog #017) ; un snapshot n'est écrit que pour un run racine terminé d'une session nommée (un run anonyme n'en aura pas d'usage) ; sa position s'arrête avant le premier événement d'un run en cours, donc deux runs lancés en parallèle n'en produisent qu'un, à la fin ; le registre d'écrivains oublie le moins récemment utilisé au-delà de 256 sessions (deux écrivains peuvent alors coexister sur une même session, et se reprennent l'un l'autre) ; l'export d'une session ne rend que ses événements, les fichiers restant désignés par leur URI ; la suppression retire les fichiers puis le journal, et un plantage entre les deux laisse un journal dont les artefacts sont partis ; le journal SQLite n'a été essayé que sur une seule machine, sans concurrence entre process.
- Sessions (4.1b) : le contrôle de fidélité est purement lexical et à sens unique — il vérifie que les repères du segment (références, e-mails, nombres d'au moins trois chiffres) sont dans le résumé, jamais que le résumé s'en tient au segment, donc il ne voit pas un résumé qui en rajoute ; il ne comprend pas ce qu'il compte, et peut crier au loup (un nombre cité dans un résultat d'outil coupé à 800 caractères, par exemple) ; une compaction n'est déclenchée qu'à la fin d'un run racine (une session laissée en plan reste grosse jusqu'au run suivant, où le filet `ensure_fits` la taille par `session.trimmed`) ; le snapshot rafraîchi après une compaction est sauté si un autre run est en cours (le marqueur de compaction reste seul, ce qui est correct mais moins réduit) ; un plantage entre l'écriture de `session.compacted` et le snapshot rafraîchi laisse la session juste mais non réduite ; le segment envoyé au modèle est rendu en texte (les images et les fichiers n'y sont que par leur URI) ; le run de compaction est reconnaissable à son agent `_compaction` et à `kind: compaction`, mais son appel de modèle reste de rôle `main` ; les tokens sont toujours estimés en caractères/4, donc les seuils sont approximatifs ; la déduplication par clé ne retient que 256 états de travaux ; `loom validate` ne monte que les agents déclarés, donc pas `_compaction` — une clé d'API manquante pour son modèle ne se verrait qu'au premier résumé, dans une tâche de fond qui n'échoue pas le run ; un `tool_results` en `scope: session` lit l'historique projeté, donc un résultat déjà résumé n'y est plus et le rôle redemande l'outil (repli correct, mais un appel de plus) ; aux seuils de l'exemple la compaction coûte plus qu'elle n'économise — c'est le rôle d'`over_tokens` (12 000 par défaut) et d'un modèle de résumé bon marché.
- Deux appels d'outil avec le même `call_id` dans une réponse ne sont pas gérés.
- Cycle de vie d'un run (délai maximal, `run.cancelled`, API `cancel`) : J4.2 (backlog #006).
- Un rôle interrompu après son `model.responded` est rappelé à la reprise (les deux coûts sont comptés).
- Portée MCP `run` : après une reprise, nouvelle connexion ; l'état d'un serveur à état est perdu.
- Rien n'oblige le modèle à répondre à toute la question : un contrat (3.2) contrôle la forme, un juge (3.3) le fond, selon ses critères ; un appel d'outil peut être imposé (`loom.require_tool`, 3.1).
- Réponse finale = dernier message : seul le prompt protège d'une réponse répartie entre plusieurs tours.
- `$ref` dans un argument de type chaîne : la référence est résolue en objet, puis refusée par le schéma de l'outil avec un message qui recopie l'objet (vu avec MiniMax-M3 en 3.3, corrigé par le modèle au tour suivant).
- `Loom.stream()` ne diffuse pas les morceaux du modèle d'un sous-run (ses événements, si) ; les morceaux d'un rôle terminal (#009, 3.2) ne sont pas attribués au rôle (bus `model.delta`, J4).

- `request_hash` des journaux antérieurs à l'ordre des résultats : un run passé dont les résultats sont arrivés dans le désordre ne redonne plus la même empreinte (rejeu, J6).
- Artefacts : fichier orphelin si l'événement n'a pas pu être écrit ; le rôle vision ne voit que les pièces jointes ; un orchestrateur vision renvoie les images à chaque appel ; seuil de déport en caractères.
- `loom validate` monte tous les agents : il échoue si une clé d'API manque.
- Accès 2.5 : les octets d'un fichier du run ne se téléchargent ni par REST ni par MCP (seulement l'URI ; MCP peut la réutiliser en lien) — avec les ressources `loom://` (5.4) ? ; un envoi REST sans `Content-Length` (chunked) n'est borné que fichier par fichier (Starlette l'écrit d'abord sur disque) ; `file_roots` vaut quel que soit le transport MCP ; un outil inconnu (serveur indisponible) n'a pas de `tool.called`, sa ligne de déroulé est seulement « … : fait (erreur) ».
- Accès 3.6 : le rapport et les verdicts d'un résultat sont recalculés depuis tout le journal de la session, relu à chaque run et à chaque lecture (coût qui grandit avec la session) ; le `skip` des juges par REST n'est contrôlé qu'après lecture du corps (fichiers d'un multipart compris) ; le serveur MCP n'a pas de clés (stdio) : `run_report` et `run_status` lisent tous les runs de l'instance ; un échec inattendu a pour `error_type` le nom de l'exception (`RuntimeError`) ; les quatre cas de `acces.py` réussissent tous : le résultat d'erreur MCP n'y apparaît pas (il est couvert par les tests).
- 3.5b : l'adaptateur `api: responses` n'a jamais parlé à l'API réelle (pas de clé OpenAI) : l'envoi du raisonnement chiffré sans identifiant suit les retours publics (erreur « Item with id 'rs_…' not found » avec `store: false`) ; le cache explicite d'OpenAI (`prompt_cache_breakpoint`, modèles récents) n'est pas utilisé, `prompt_cache_key` peut passer par `params` ; `pricing.cache_write` n'a qu'un prix (celui du TTL choisi) et l'usage ne sépare pas les écritures 5 min et 1 h ; un prompt Anthropic sous le minimum du modèle n'est pas caché, sans erreur ; le schéma natif ne part pas pour un appel de l'orchestrateur qui peut appeler des outils ; `strict` seulement pour un schéma qui en suit les règles (celui de l'exemple, avec `minLength`, part sans) ; chez Together, le schéma natif fait perdre ses sauts de ligne au texte de GLM-5.3-Flash et ralentit fortement l'appel (run réel) : à n'activer qu'après essai, modèle par modèle ; plusieurs blocs de raisonnement d'une même réponse repartent réunis en un seul champ (API Chat).
- Politiques (3.1) : un `Retry` à `after_tool` sur un outil (pas un rôle) renvoie le résultat en erreur à l'orchestrateur ; en diffusion `live`, la réponse refusée est diffusée avant la réparation (puis `StreamReset`) ; après une reprise, une décision `after_model`/`on_output` non appliquée est réévaluée (son `policy.decided` peut apparaître deux fois)  ; `Pause` refusée jusqu'en J4.3 ; une politique synchrone s'exécute dans la boucle (pas d'entrée-sortie).

- Juges (3.3) : un juge de rôle voit les **arguments** de l'appel qu'il juge, donc un critère qui admet « ce qui est demandé » comme source de vérité accepte aussi ce que l'orchestrateur a écrit lui-même dans ces arguments — un fait inventé en amont se blanchit et passe le juge (vu en réel le 21/09 : un horaire de disponibilité absent du devis, demandé par les `consignes`, noté `fidele: 1`). Un critère doit nommer ses sources et exclure les arguments explicitement. - Juges (3.3) : après une reprise, une décision `on_output` non appliquée est réévaluée et son juge rappelé (coût compté deux fois) ; un rôle interrompu est rappelé avec ses juges ; un verdict invalide est une erreur du juge (il ne répare pas son verdict) ; le tirage vaut pour tout le run (un rôle appelé deux fois est jugé les deux fois ou aucune) ; le juge ne voit pas l'historique de la session (`session_summary`, `last_turns` : J4.1) ; pas de juge sur un outil ni sur la référence d'un sous-agent (seulement celui de l'agent appelé, dans son run) ; un juge Anthropic avec `params.thinking` activé est refusé au chargement (3.5a : l'API refuse un outil imposé avec le raisonnement étendu) ; les événements d'un point d'accroche sont horodatés à leur écriture, après toute la chaîne (le `guard.checked` du contrat porte l'heure de fin du juge) ; pas de forçage des juges par MCP (3.6 : REST seulement) ; erreurs en profil prod : J5.
- Budgets (3.4) : contrôlés seulement avant un appel de l'orchestrateur (les rôles, juges et sous-agents d'un lot peuvent dépasser, et la réponse forcée coûte encore une génération, plus ses réparations éventuelles) ; la consigne de réponse forcée ne garantit pas qu'un modèle n'écrive pas un appel d'outil en texte ; le budget de session ignore les runs de la même session qui tournent en même temps, et ne s'applique pas à un sous-run (le parent le voit à son contrôle suivant) ; la part d'un sous-agent se calcule sur l'état du parent au début du lot (les autres appels du lot ne comptent pas) ; `max_calls` ne compte pas les appels d'un sous-agent, alors que `max_cost` et `max_tokens` comptent sa consommation ; budgets par client et par période, erreur en profil prod pour un modèle sans tarif : J5 ; les secours comptent dans le contrôle #010 depuis 3.5a.
- Outillage de vérification : depuis le J3, la copie est dans la VM de la session (hors du dossier de Denis), avec son propre environnement uv (`uv sync --all-extras --frozen`, et un second environnement sans extra pour la passe noyau) ; le code vérifié est recopié dans le dossier en fin de phase. Pyright reçoit l'environnement (`uv run --no-sync pyright`). Sur le dossier de Denis, git seulement avec `--no-optional-locks` : un `git status` y a laissé un `.git/index.lock` impossible à supprimer sans autorisation (supprimé avec son accord le 19/09).
- **Ce que les exemples vérifient (mesuré le 23/09) :** sur vingt-cinq, **seize** finissent sur un verdict (`return 0 if … else 1` : `result.ok`, la comparaison des trois accès, ou l'attendu par cas de `j3/acces.py`, le plus complet) ; **deux** sont linéaires et ne tombent que sur une exception (`j1/journal.py`, `j1/moteur.py`) ; et **sept rendent 0 quoi qu'il arrive** — les cinq de J4 (`acces`, `approbation`, `compaction`, `durable`, `idempotence`, dont deux portent quelques `assert`), plus `clients.py` et `quotas.py`. La coupure est à **J4**, quand les exemples ont cessé de montrer un run qui réussit pour montrer un run qu'on annule, qu'on tue, qu'on met en pause ou qu'on refuse : `result.ok` n'y veut plus rien dire, et la vérification a été abandonnée au lieu d'être reformulée. À savoir en relisant les phases : la ligne « les N exemples passent » ne prouve, pour ces sept-là, que « aucun n'a planté ».
- **Règle adoptée (23/09, avec Denis) :** un exemple déclare le résultat attendu de chaque appel, marque les écarts dans sa sortie, en fait la liste à la fin et **rend 1** si l'un d'eux tombe — par une classe `Controle` **recopiée dans le fichier**, comme les aides HTTP (`serveur`, `appel`, `_http`) le sont déjà dans cinq exemples : rien de livré, rien à documenter, et chaque exemple continue de tourner seul. Les attendus sont **structurels, pas numériques** — en `--reel` le nombre de runs avant un refus dépend du coût des modèles, donc on exige « un refus qui nomme le plafond, et aucun journal pour le run refusé », jamais « le run 3 est refusé ». Adoption **au fil de l'eau** : tout exemple nouveau s'en sert (`securite.py` est le premier), un exemple ancien est repris quand une phase le touche. Un essai de CI qui lancerait les exemples en simulé est reposé à plus tard : il ne vaudrait rien tant que sept d'entre eux rendent 0 quoi qu'il arrive.
  - **Complément constaté trois fois (5.2a, 5.3b, 5.4b) : la règle vaut aussi pour ce qu'un exemple *raconte*.** Un attendu structurel qui tient ne protège pas d'un titre, d'une parenthèse ou d'un commentaire qui affirme un chiffre que la sortie contredit — et c'est le lecteur, pas le `Controle`, qui se fait tromper. Une ligne qui commente un nombre doit donc le calculer sur la réponse, jamais l'annoncer d'avance.
- Secours (3.5a) : les disjoncteurs vivent en mémoire, dans l'instance `Loom` (ni partagés entre processus ou workers, ni gardés au redémarrage) ; après une pause, plusieurs runs simultanés peuvent faire l'essai en même temps ; pas d'événement de fermeture (le retour d'un modèle se voit à l'absence de bascule) ; l'adhérence vaut pour un run, le run suivant de la session repart du modèle principal (s'il n'est pas écarté) ; une requête remplacée par une politique `before_model` garde ses messages et ses outils sur le secours, mais ses `params` sont ceux du secours ; `before_model` (budget) voit la requête du modèle courant, pas celle d'un secours atteint pendant l'appel ; `context_overflow` ne bascule que si les deux fenêtres sont déclarées ; côté MCP, seules les connexions à l'ouverture d'un run comptent (pas une connexion perdue pendant un appel d'outil) ; le cache de prompt est perdu à la bascule ; `secours.py` construit son modèle en panne en code (`model_copy`, sans les contrôles du chargement) ; `model.retried` et `model.responded` portent le nom du modèle chez le fournisseur (`MiniMax-M3`), pas son identifiant dans la config : deux définitions du même modèle (`M3_PANNE`, `M3_MAIN`) se confondent dans ces événements et dans le rapport par modèle (le `model.fell_back` qui suit, lui, les nomme).
